# Atelier 기반 Auto-Codex 확장 구현 가이드

작성 기준: 2026-10-29, 현재 작업 트리의 소스와 로컬 문서. 실제 Atelier 소스 루트는 `atelier/atelier/`다.

이 문서는 이후 코딩 에이전트에게 단계별 구현을 지시하기 위한 설계·작업 가이드다. **통합 후 제품은 Atelier의 디자인과 설계 작업 흐름을 기본으로 사용하며, Auto-Codex의 기존 실행·대화·승인·시각화 기능을 모두 포함한다.** UI/UX 디자인 생성은 여기에 추가되는 기능이다. 이 문서를 작성한 시점에는 해당 통합을 구현하거나 실행 검증하지 않았다.

진행 기록: [0단계 기준선](atelier/STAGE0_BASELINE.md), [기능·메시지·테스트 보존표](atelier/FEATURE_PRESERVATION.md), [단계별 계약 v1](atelier/CONTRACTS.md), [1단계 공통 셸](atelier/STAGE1_IMPLEMENTATION.md), [2단계 도메인](atelier/STAGE2_IMPLEMENTATION.md), [3단계 저장소·WS·백업](atelier/STAGE3_IMPLEMENTATION.md), [4단계 수동 React 작업실](atelier/STAGE4_IMPLEMENTATION.md), [5단계 읽기 전용 AI 제안](atelier/STAGE5_IMPLEMENTATION.md). 공통 셸·순수 도메인·저장소·수동 작업실과 네 목적의 명시적 제안 적용을 구현했다. 실제 모델 호출은 미검증이며 합성 프로토콜 검증과 구분한다. 제작·산출물 연결과 통합 AI 백업은 후속 제안이다. [로컬 도메인 계약](atelier/DOMAIN_CONTRACT.md)과 각 단계의 지원 필드·한도·검증 기록을 따른다. 기본 npm test의 러너 검색 범위 충돌은 해결했다.

## 1. 제품 방향과 완료 모습

### 1.1 통합 원칙

1. **화면과 사용 경험의 기준은 Atelier다.** 흰색 바탕, 타이포그래피, 여백, 좌측 탐색, 중앙 작업 영역, 우측 근거 패널, 가이드/상세 편집 구조를 공통 기반으로 삼는다.
2. **실행의 기준은 Auto-Codex다.** Node 브리지가 Codex App Server, 프로젝트 경로, 실제 이벤트, 승인, Team/Solo 실행과 이력을 계속 관리한다.
3. **기존 일반 작업은 독립적으로 유지한다.** 버그 수정·문서 작성·조사 등은 디자인 프로젝트나 브리프 없이 바로 실행할 수 있어야 한다.
4. **Atelier의 수동 기능도 유지한다.** AI 연결 없이 설계·확정·프롬프트 작성·ZIP 내보내기·결과 등록·검토가 가능해야 한다.
5. **AI는 제안과 제작을 돕는다.** AI가 작성한 설계는 제안으로 들어오며, 사용자 확정을 대체하지 않는다. 프롬프트 생성, 실제 제작, 결과 검토의 완료를 구분한다.
6. **픽셀 월드는 계속 제공한다.** 공통 앱 외관은 Atelier로 바꾸되 기존 픽셀 공간·캐릭터·활동 센터는 실행을 관찰하는 전용 화면으로 유지한다.

### 1.2 사용자가 거치는 대표 흐름

```text
홈 / 작업실
  ├─ 일반 Codex 작업 → 프로젝트 또는 폴더 없는 조사 → Team/Solo → 결과·이력
  └─ 디자인 작업
       → 아이디어 / 이미지 / 확정 컨셉 / 기존 결과로 시작
       → 설계·흐름·레퍼런스·컨셉·스타일 정리
       → 필요하면 AI 제안 받기 → 사용자가 편집·확정
       → 브리프 검사·의도 확인 → 프롬프트 스냅샷 고정
       → 수동 내보내기 또는 Codex로 제작
       → 실제 실행·승인·중단·결과 확인
       → 결과를 원래 스냅샷에 연결
       → 기준별 검토 → 수정 계획 → 새 스냅샷 → 수정 제작 → 재검토
```

디자인 작업 중에도 대화·작업 결과·픽셀 화면·활동 센터와 승인 요청에 접근할 수 있어야 한다. 탭을 바꾸거나 패널을 닫는 동작은 실행 중단이나 재실행을 일으키지 않는다.

### 1.3 이번 통합의 범위

- 포함: 공통 디자인 적용, Atelier 도메인·파일·백업 기능 이식, AI 설계 제안, Codex 기반 UI 코드 생성·수정, 실제 결과와 검토 연결.
- 후속 선택 기능: 외부 이미지 모델, Figma 등 외부 서비스, 스크립트를 실행하는 실시간 웹 미리보기, 반복 자동 개선.
- 기본 범위 밖: 계정·원격 DB·클라우드 저장·외부 호스팅·자동 배포·유료 이미지 API 연결.

첫 제작 MVP의 결과는 **선택한 로컬 프로젝트의 UI 코드와 실제 생성·수정 파일, 수행된 검사 기록**이다. PNG 시안 생성이나 이미지 이해는 설치된 모델·스킬의 실제 지원을 확인한 경우에만 노출한다. `visual` 역할이 있다는 이유만으로 이미지 생성 기능이 있다고 표시하지 않는다.

## 2. 현재 소스에서 확인한 출발점

다음은 현재 구현이고, 이후 절의 디렉터리·메시지·데이터 계약은 제안이다. 구현을 시작할 때 변경된 소스와 하위 지침을 다시 확인한다.

| 영역 | 현재 상태와 근거 | 통합 시 처리 |
|---|---|---|
| Auto-Codex UI | React 19·Vite·TypeScript, `src/App.tsx`, `src/hooks/useBridge.ts` | 공통 셸과 디자인 영역을 확장한다 |
| 실행 브리지 | `server/index.ts`, `codex-app-server.ts`, `runtime-registry.ts` | 실행·승인·경로 검증 책임을 유지한다 |
| Team 실행 | `task-planner.ts`, `orchestration.ts` | 계획 검증·최대 8개 Task·읽기 최대 3개 동시 실행·쓰기 독점을 유지한다 |
| 대화 저장 | `server/conversation-store.ts`, `.local-data/history.json` | 기존 형식과 복원 동작을 보존한다 |
| 현재 화면 | PixelOffice, OperationsPanel, ResultView, 각종 선택기·승인 대화상자 | 공통 셸에서 모두 접근할 수 있게 한다 |
| Atelier UI | 의존성 없는 ES 모듈, `public/app.js`, `easy-guide.js`, `panels.js`, `styles.css` | 디자인과 도메인 동작을 React 화면으로 이식한다 |
| Atelier 규칙 | `public/domain.js`, `structure.js`, `guide.js` | 결정 상태·범위·영향 전파·조립·검토 규칙을 우선 보존한다 |
| Atelier 저장 | `server.mjs`: SQLite, 프로젝트별 파일, 버전 충돌 검사 | 브리지 내부 저장소로 분리해 이식한다 |
| Atelier 검증 | `src/project-validation.mjs`, `resources.mjs`, `validation-image.mjs`, `zip.mjs` | 검증 의미와 실제 파일·ZIP 동작을 재사용한다 |
| AI 연결 | Atelier에는 SDK·큐·외부 AI 실행이 없다. `contracts.d.ts`의 HandoffDocument도 미래 연결 개념이다 | 새 어댑터로 실제 Auto-Codex 실행을 연결한다 |
| 버전 표기 | Atelier 패키지는 1.2.0, 일부 서비스 문서는 1.3, 가이드·템플릿은 1.3.2 | 이 번호들을 통합 앱 버전으로 합치지 않는다 |
| 실행 환경 | Auto-Codex README는 Node 20+, Atelier는 내장 SQLite 때문에 Node 22.13+를 명시한다. 조사 환경은 v22.20.0 | 통합 기본안은 Node 22.13+로 문서·런처·실제 호환성을 맞춘다 |

## 3. 기능 보존표: 삭제·축소 없이 옮길 것

각 항목에 대해 기존 진입점, 새 진입점, 상태 소유자, 회귀 검증을 기록한다. 이 표가 완료되기 전에는 기존 화면을 제거하지 않는다.

| 기능 | 통합 후 위치·동작 | 보존 조건 |
|---|---|---|
| 프로젝트 폴더 선택·직접 경로 입력·신뢰 | 공통 작업실 설정 | 실제 경로 검증과 명시적 신뢰를 유지한다 |
| 폴더 없는 조사·웹 접근 설정 | 일반 Codex 작업 | readOnly와 네트워크 기본 차단을 유지한다 |
| 새 대화·대화 선택·프로젝트별 이력 | 공통 대화 탐색 | 대화 선택 시 프로젝트 연동·재시작 후 복원·Solo thread 재개를 유지한다 |
| 모델·추론 강도 | 공통 실행 설정 | 현재 App Server가 제공한 목록과 지원 범위를 사용한다 |
| Manual/Auto 스킬 | 공통 실행 설정 | 프로젝트 스킬/전체 스킬 구분과 결정적 라우터를 유지한다 |
| Team Auto/Solo | 일반 작업과 디자인 제작의 실행 설정 | 검증된 계획·쓰기 독점·실패 후 보고를 유지한다 |
| 실행·중단·스트리밍 | 공통 실행 바·대화/결과 | 버튼 중복 클릭으로 실행이 복제되지 않는다 |
| 명령·파일·추가 권한 승인 | 전역 ApprovalDialog | 어느 화면에서도 표시하고 pending ID만 처리한다 |
| 픽셀 월드·캐릭터 선택·애니메이션 설정 | 실행 관찰의 픽셀 화면 | 기존 자산·매핑·역할/스킬 구분·동작 축소 설정을 보존한다 |
| 활동 센터·작업 상태·타임라인 | 실행 관찰 | 실제 정규화 이벤트에 연결한다 |
| 결과 읽기·Markdown/원문·복사 | 공통 결과 화면 | 긴 본문·대화별 결과·키보드 동작을 유지한다 |
| 오늘/7일 토큰 집계·연결 오류 | 공통 상단 또는 실행 상세 | 로컬 집계라는 의미와 bridge/App Server 상태 구분을 유지한다 |
| Atelier 네 가지 시작점 | 홈의 디자인 작업 | 입력과 시작 의도를 보존하고 적절한 첫 행동으로 연결한다 |
| Atelier 여덟 작업 탭 | 디자인 작업실 | 가이드/상세 편집이 같은 데이터를 사용한다 |
| 레퍼런스 원본·영역·크롭 | 레퍼런스 연구 | 실제 파일·좌표·출처·적용 이유·소유 관계를 보존한다 |
| 흐름·분기·복구·결정 영향 | 사용자 흐름 및 편집 상세 | 잘못된 연결 차단과 관련 결정 재검토 표시를 유지한다 |
| 범위별 출력·결정 추적·실제 ZIP | 프롬프트 스튜디오 | 전체/흐름/화면/리소스 선택과 근거/제작 범위 구분을 유지한다 |
| 로컬 서체·문서·데이터 등 첨부 | 스타일과 리소스 | 형식·해시·프로젝트별 분리와 실제 파일 전달을 유지한다 |
| JSON 백업·새 프로젝트로 복원 | 작업실 설정 | 자체 백업과 전달용 handoff.json을 구분한다 |
| 결과 수동 등록·검토·수정·재검토 | 자가 진단과 수정 | 과거 스냅샷·판정 보존, 새 결과의 판정 초기화를 유지한다 |

## 4. 공통 UI/UX 기준

### 4.1 디자인 시스템

Atelier의 실제 CSS와 로컬 에셋을 출발점으로 사용한다. 다음 값은 현재 `atelier/atelier/public/styles.css`에서 확인한 기본값이다.

| 용도 | 기준 |
|---|---|
| 기본 배경 / 보조 표면 | `#ffffff` / `#f7f7f4` |
| 본문 / 보조 글자 | `#343432` / `#767671` |
| 구분선 | `#e9e9e4` |
| 강조 / 강조 배경 | `#ff365d` / `#fff0f2` |
| 영문 장식 제목 | 로컬 Instrument Serif |
| 본문·내비게이션 | 로컬 Instrument Sans + Malgun Gothic/시스템 한글 서체 |
| 기본 구성 | 얇은 구분선, 넓은 간격, 제한적인 카드·그림자, 작은 모서리 |

기존 Atelier의 작은 글자 크기를 모든 화면에 그대로 복사하지 않는다. 장문 결과·승인 상세·실행 로그는 읽기 쉬운 크기와 대비를 우선하고 확대·키보드·스크롤을 확인한다. 버튼의 성공/오류/제안/확정은 색과 문자를 함께 사용한다.

폰트·아이콘은 로컬로 제공한다. [라이선스 문서](../atelier/atelier/docs/LICENSES.md), OFL 파일, Streamline 표시를 함께 옮긴다. 로컬 `.woff2`의 개발·프로덕션 응답 MIME도 확인한다.

### 4.2 탐색과 화면 배치

```text
공통 상단: 작업실/프로젝트 · 연결 상태 · 실행 상태 · 토큰 · 실행 설정
좌측 탐색
  홈 / 일반 Codex 작업 / 대화·결과
  디자인 작업실
    01 프로젝트 설계      05 스타일과 리소스
    02 사용자 흐름        06 디자인 브리프
    03 레퍼런스 연구      07 프롬프트 스튜디오
    04 컨셉 탐색          08 자가 진단과 수정
  실행 관찰: 활동 센터 / 픽셀 화면
  작업실 설정 / 사용 방법
중앙: 현재 작업 또는 결과
우측: 근거·결정 상태·다음 행동 / 필요 시 실행 상세
전역: 승인 대화상자 · 오류/연결 안내 · 중단 제어
```

- 홈은 기존 Atelier의 네 시작 카드와 작업 목록 구성을 따른다. 일반 Codex 작업으로 바로 가는 명확한 진입점을 추가한다.
- 실행 설정은 접을 수 있지만 현재 모드·모델·진행 중 상태는 식별 가능해야 한다.
- 픽셀 화면의 월드 표현은 유지하고, 주변 헤더·탭·컨트롤에는 공통 디자인을 적용한다.
- 1440px·768px·390px를 기본 확인 크기로 삼는다. 좁은 화면에서 좌측 탐색은 열기 패널, 우측 근거는 접기 패널로 바꾸며 입력을 보존한다.
- 승인 대화상자의 초점 이동·순환·복귀, Escape 동작, 읽기 순서, 동작 축소를 검증한다. Escape나 배경 클릭을 승인으로 해석하지 않는다.

### 4.3 버튼과 상태의 의미

| 표현 | 실제 의미 |
|---|---|
| AI 제안 받기 | 현재 확정값을 유지하면서 편집 가능한 후보를 요청한다 |
| 제안 적용 | 선택한 후보를 편집 데이터에 반영한다. 확정과 별도다 |
| 확정 | 사용자가 해당 결정의 내용과 적용 범위를 확인했다 |
| 프롬프트 만들기 | 확정 입력을 고정 스냅샷으로 조립한다. 제작 실행은 없다 |
| Codex로 제작 | 고정 스냅샷과 선택 프로젝트로 실제 작업을 시작한다 |
| 실행 완료 | App Server의 작업 종료를 확인했다 |
| 결과 확인 필요 | 파일·화면·실행 근거와 설계 기준 비교가 남아 있다 |
| 검토 완료 | 해당 회차·기준·검토 범위의 근거와 판정을 갖췄다 |

진행률의 근거가 없으면 백분율을 표시하지 않는다. 애니메이션·프롬프트 생성·모델의 완료 문장은 실제 파일 생성이나 디자인 일치의 증거가 아니다.

## 5. 목표 아키텍처와 파일 책임

### 5.1 하나의 앱, 하나의 실행 브리지

```text
React/Vite 공통 셸 — Atelier 디자인 기반
  ├─ 일반 Codex 화면 / 결과 / 활동 센터 / 픽셀 화면
  └─ 디자인 작업실 / 제안 편집 / 프롬프트 / 검토
                    │
             ws://127.0.0.1:4781/ws
                    │
Node bridge
  ├─ 기존 프로젝트·대화·모델·스킬·승인·이벤트 처리
  ├─ Atelier 저장소·첨부·검증·백업·ZIP
  └─ 디자인 실행 어댑터 → 기존 실행 진입점·스케줄러
                    │ stdio JSONL
              codex app-server
```

프로덕션은 기존 `npm start`의 4781, 개발 UI는 기존 4780을 유지한다. Atelier의 4317 서버를 통합 제품의 필수 프로세스로 추가하지 않는다. 별도 AI API 키나 두 번째 Codex 실행기를 만들지 않는다.

애플리케이션 명령·설계 데이터·파일 전달은 기존 WS 경계를 확장한다. 기존 정적 UI·번들·공개 에셋 제공과 health 응답은 유지한다. Atelier의 `/api/*`를 그대로 공개하거나 브라우저에서 SQLite·원본 App Server 출력·셸을 직접 다루지 않는다.

### 5.2 권장 코드 배치 — 새로 만들 경로

실제 파일명은 구현 시 조정할 수 있지만 책임 분리는 유지한다.

```text
src/
  components/layout/           공통 셸·탐색·상태 바
  features/atelier/            여덟 탭·가이드·제안 비교·검토 UI
  hooks/useAtelier.ts          설계 요청·응답 상태; WS 연결은 기존 것을 공유
  styles/atelier-tokens.css    공통 토큰·폰트
shared/
  atelier/                    DOM/Node에 의존하지 않는 도메인·규칙·조립
  atelier-contract.ts         설계·제안·실행 연결 계약과 버전
server/
  atelier/store.ts             SQLite 저장·버전 충돌·트랜잭션
  atelier/files.ts             프로젝트별 바이트·해시·경로 검증
  atelier/validation.ts        프로젝트·스냅샷·백업·출력 검증
  atelier/bundle.ts            범위별 ZIP과 자체 백업
  atelier/handlers.ts          타입별 WS 요청 처리
  atelier/execution.ts         설계 요청을 기존 실행 계층에 연결
public/
  atelier-assets/              폰트·아이콘·라이선스
```

`atelier/atelier/`는 이식 중 기준 자료와 독립 회귀 검증용으로 보존한다. 최종 런타임이 이 폴더의 `server.mjs`를 import해 서버를 추가로 열거나 원래 DB를 자동 수정해서는 안 된다.

### 5.3 재사용·이식 방법

| 원본 | 이식 방법 |
|---|---|
| domain.js / structure.js | 순수 로직을 TypeScript 모듈로 이식하고 원본 픽스처로 의미 보존을 확인한다 |
| guide.js / easy-guide.js | 질문·예시·단계 규칙과 UI를 구분한다. 확인되지 않은 예시는 계속 제안이다 |
| panels.js / app.js | 화면과 조작 의도를 React로 옮긴다. 전역 DOM 교체·문자열 이벤트 바인딩은 옮기지 않는다 |
| server.mjs | 서버 부팅과 DB·파일·검증 책임을 분리한다. 기존 HTTP 라우트 대신 WS handler를 만든다 |
| resources / validation / zip | 실제 바이트·참조·해시 검증과 ZIP 의미를 보존한다. 확장자 검사만으로 축소하지 않는다 |
| styles.css | 토큰·레이아웃부터 옮기고 폼·목록·모달을 순차 적용한다. 전역 CSS 충돌을 차단한다 |
| contracts.d.ts | 개념 계약을 참고해 실제 런타임 스키마를 만든다. 타입 선언만으로 입력을 검증했다고 하지 않는다 |

현재 빌드는 JS 이식을 자동 처리하지 않는다. `allowJs: false`와 `tsconfig.server-build.json`의 include/outDir를 확인하고 새 shared/server 모듈이 실제 `build-server`에 포함되는지 검사한다. 전체 strict 검사를 끄거나 타입을 `any`로 바꾸는 방식으로 이식을 통과시키지 않는다.

## 6. 데이터·저장·연결 계약

### 6.1 식별자를 분리한다

| 개념 | 소유·의미 |
|---|---|
| designProjectId | Atelier 설계 프로젝트. 로컬 코드 폴더가 없어도 존재한다 |
| workspacePath | 브리지가 검증한 실제 코드 작업 폴더. 설계 프로젝트 ID와 다르다 |
| conversationId | 기존 Auto-Codex 사용자 대화 |
| snapshotId | 변경하지 않는 설계 입력·프롬프트·기준·파일 목록 |
| generationId | 설계 제안/제작 요청 하나를 추적하는 통합 앱 식별자 |
| runId / taskId | 기존 Team 실행이 실제로 만든 경우에만 연결한다 |
| threadId / turnId | 실제 App Server 응답으로 받은 식별자 |
| resultId / reviewId / planId | 결과·검토 회차·수정 계획을 연결하는 Atelier 식별자 |

Solo에 Team runId를 가짜로 만들지 않는다. 경로·파일명·가장 최근 대화만 보고 결과의 소속을 추정하지 않는다. 하나의 코드 폴더에 여러 설계 프로젝트가 연결될 수 있으며 실행마다 바인딩을 고정한다.

### 6.2 권장 데이터 계약

다음은 구현할 계약의 필수 필드다. 아직 존재하는 API가 아니다.

| 객체 | 필요한 정보와 규칙 |
|---|---|
| DesignBinding | 설계 프로젝트·검증 workspace·대화의 연결. 바꾸면 기존 실행 바인딩은 보존한다 |
| AIProposal | 대상 프로젝트, 요청 시점 revision, 목적, 대상 결정 ID, 후보 값, 근거, 가정, 출처, 제안 상태 |
| DesignGeneration | 계약 버전, generationId, project/snapshot/conversation, 목적, 실행 모드, 실제 런타임 ID, 시작·종료 상태, 재시도 연결 |
| InputManifest | 결정 ID·버전, OutputSelection, 스냅샷 텍스트 해시, 파일 ID·바이트 해시·크기·역할, 모델·스킬 선택 기록 |
| ArtifactManifest | 실제 확인한 파일 ID/프로젝트 상대경로·해시·종류, 생성/변경 구분, 출처 generationId, 검사 결과 |
| Result | 원본 snapshotId/generationId, 실제 결과 파일 또는 실행 기록, 환경, 출처, 알려진 한계 |

기존 `PromptSnapshot`의 text·criteria·decisions·selection·referenceFileIds와 과거 입력은 불변이다. 최신 편집 내용을 실행 시 몰래 섞지 않는다. 실행 중 편집해도 진행 중 요청은 고정본을 사용하고, 새 내용은 새 스냅샷과 요청으로 이어진다.

### 6.3 저장소 선택과 마이그레이션

권장 기본안은 **기존 대화 JSON 유지 + 별도 Atelier SQLite·파일 저장소 추가**다. 서로 다른 두 도메인을 하나의 거대한 JSON으로 합치지 않는다.

```text
.local-data/history.json                  기존 대화 저장소 그대로
.local-data/atelier/atelier.sqlite        설계·스냅샷·제안·실행 연결·검토
.local-data/atelier/files/<project-id>/   원본·크롭·리소스·결과 바이트
```

- Node 내장 SQLite를 재사용하므로 통합 지원 하한을 Node 22.13+로 맞추고, 기존 도구 체인이 요구하는 버전도 실제 검사한다. 런처는 단순 `where node`를 넘어 버전을 확인하고 미지원 환경에 명확한 메시지를 준다.
- 설계 도메인은 Codex CLI가 없거나 App Server가 실패해도 사용할 수 있어야 한다. CLI 오류로 전체 작업실 부팅을 막지 않는다.
- 모델이 DB·history.json·승인 상태를 직접 수정하게 하지 않는다. 파일 산출물과 구조화 응답을 브리지가 검증해 저장한다.
- SQLite와 대화 JSON 사이에는 단일 원자 커밋이 없다. generationId 기반 준비/실행 연결 기록과 복구 절차를 두고, 중간 종료로 끊긴 참조를 표시한다. 확인되지 않은 실행을 성공으로 복구하지 않는다.
- 기존 Atelier 데이터는 자체 JSON 백업을 **새 설계 프로젝트로 가져오는 방식**을 기본으로 한다. 원래 `atelier/atelier/data`를 자동 이동하거나 원래 DB를 열어 수정하지 않는다.
- 기존 백업의 format/version 의미를 보존한다. AI 연결 데이터는 명시적으로 버전 있는 확장 백업으로 제공하고, 구형 백업을 읽는 호환 경로를 둔다. 외부 실행 ID를 복원해도 재실행 권한은 생기지 않는다.
- 저장은 기존 Atelier의 optimistic version 검사와 스냅샷 변경 금지를 유지한다. 충돌 시 사용자 입력을 남기고 병합/재열기 선택을 제공한다.
- DB 마이그레이션 전 일관된 백업을 만든다. 실행 중 SQLite 본체만 복사하지 말고 연결 종료 또는 안전한 SQLite 백업 절차를 사용한다. 원본 파일도 함께 보존한다.
- 복원 직후 generation의 진행 중 상태는 interrupted로 정리한다. 승인 ID·신뢰·네트워크 허용은 복원하지 않으며 자동 실행하지 않는다.

### 6.4 WS 확장과 파일 전송

새 메시지는 `atelier.*`처럼 별도 이름 공간을 사용한다. 아래 이름은 **제안**이며 0단계에서 실제 스키마·허용 크기·오류 코드를 확정한다.

```text
요청: atelier.project.list/create/load/update
      atelier.snapshot.create
      atelier.file.begin/chunk/commit/read
      atelier.backup.export/import, atelier.bundle.export
      atelier.ai.propose, atelier.proposal.apply
      atelier.generation.start, atelier.result.register
      atelier.review.update, atelier.plan.create
응답: atelier.response, atelier.project.changed,
      atelier.proposal.ready, atelier.generation.state
```

- 기존 ClientMessage/ServerMessage와 `server/client-message.ts` 검증을 확장한다. 기존 메시지와 `useBridge` 이벤트 처리를 보존한다.
- 새 CRUD 요청은 clientRequestId와 성공/오류 응답을 연결한다. **clientRequestId는 App Server 승인 request ID가 아니다.**
- mutation은 expectedVersion을 사용한다. 모델 응답·브라우저에서 보내는 프로젝트 전체 객체를 권한 근거로 삼지 않는다.
- 실행 요청에는 중복 방지 키를 사용한다. 키를 프로젝트·스냅샷·목적·내용 해시와 묶어 같은 요청은 같은 generation을 돌려주고, 다른 내용으로 재사용하면 거부한다. 재시도는 새 키·새 generation이며 이전 요청에 연결한다.
- 파일당 15MB, 자체 백업 전체 90MB라는 기존 제한을 유지하되, 한 WS JSON 메시지로 base64 전체를 보내지 않는다. 제한된 chunk와 서버 발급 uploadId로 전달한다.
- 구현 기본값: 제어 메시지 256KiB, raw chunk 256KiB 이하, WS 프레임 1MiB 이하. base64 팽창까지 프레임 제한에 포함한다. 파일·백업·ZIP 총량은 별도 검증한다.
- 업로드는 연결·프로젝트·용도에 묶고 chunk 순서/총량/해시·만료·동시 업로드 수·미완료 정리를 검사한다. 내보내기/다운로드도 chunk와 backpressure를 적용한다.
- 모든 새 요청에 길이·배열 수·필드 허용 목록·소유 관계·속도/동시성 제한을 둔다. 대용량 파일 전송이 승인·중단 메시지를 오래 막지 않도록 전송과 제어 처리를 분리한다.
- 재접속은 상태 조회로 동기화한다. UI 재마운트·WS 재연결만으로 실행 요청을 재전송하지 않는다.

## 7. AI 연결 동작

### 7.1 설계 보조와 제작 실행을 구분한다

| 요청 | 입력·실행 | 결과 |
|---|---|---|
| 설계 제안 | 선택한 설계 정보·대상 ID, 도구 쓰기가 필요 없는 readOnly 작업 | 구조화된 후보. 사용자 선택 전 기존 결정은 보존 |
| UI 제작 | 확정 스냅샷·검증 workspace·선택 모델/스킬·Team/Solo | 실제 코드·파일·검사 기록과 원본 스냅샷 연결 |
| 결과 진단 보조 | 고정 기준·사용자가 제공한 결과 근거 | AI의 관찰/가설 제안. 근거 없으면 확인 불가 |
| 수정 제작 | 확정 수정 계획·원본 결과·새 수정 스냅샷 | 새 generation·결과·검토 회차 |

일반 Solo 프로젝트 작업은 현재 workspaceWrite를 사용하므로, 설계 제안을 그 경로에 단순히 프롬프트만 바꿔 보내면 안 된다. 공통 실행 진입점을 분리하고 **서버가 목적에 따라 readOnly 정책을 선택**하도록 확장한다. 제안만으로 프로젝트 쓰기나 셸 실행이 허용되어서는 안 된다.

첫 단계는 텍스트 기반 제안으로 완성한다. 이미지가 첨부됐지만 실제 이미지 입력 지원이 확인되지 않았다면 사용자의 관찰 메모를 사용하고 이미지 자동 분석은 미지원이라고 표시한다. 임의로 다른 모델·외부 API로 보내지 않는다.

### 7.2 제안 수신과 적용

1. 현재 편집 저장을 완료한 후 입력 revision과 대상 ID를 고정한다. 사용자가 어떤 내용을 보낼지 확인할 수 있게 한다.
2. 기존 실행 잠금·모델 검증·승인·이벤트 경로를 공유해 요청한다. 지원되는 structured output을 확인하고 출력 스키마를 검증한다.
3. 대상 밖 ID·다른 프로젝트·허용하지 않은 필드·과도한 크기·잘못된 형식은 거부한다. 원문 응답을 임의 JavaScript로 평가하지 않는다.
4. 응답을 별도 제안으로 저장한다. 요청 이후 사용자가 편집했으면 오래된 제안으로 표시하고 자동 덮어쓰지 않는다.
5. 사용자가 항목별 적용/제외/편집을 선택한다. 적용 시 기존 updateDecision·버전·영향 전파 규칙을 거친다. AI 출처와 근거를 남긴다.
6. 적용된 값의 기본 상태는 proposed다. 사용자 확정은 별도 동작이며, confirmed를 덮어쓰는 경우 변경 전후를 보여 준다.

출력 형식 오류나 모델 실패는 실제 오류로 표시한다. 내장 예시를 성공한 AI 응답처럼 대신 보여 주지 않는다. 예시를 사용할 수는 있지만 출처는 계속 내장 예시다.

### 7.3 Codex 제작과 첨부 전달

1. 필수 결정·의도 확인·선택 범위·파일을 서버에서 검사하고 스냅샷을 고정한다. draft/baseline은 진단용으로 사용할 수 있지만 확정 제작의 입력으로 자동 승격하지 않는다.
2. 설계 프로젝트와 코드 workspace를 연결한다. 제작에는 실제 프로젝트 디렉터리가 필요하다. 폴더 없는 조사 모드에서 파일 제작을 시작하지 않는다.
3. 프롬프트 스튜디오에서 목적·대상 범위·전달 파일·프로젝트·실행 모드·모델을 보여 주고 사용자의 제작 시작 동작을 받는다. 일상적인 로컬 제작에 추가 확인 단계를 중복해서 만들지 않는다.
4. 브리지가 시작 직전 경로 존재·실제 대상·프로젝트 신뢰·모델/스킬·동시 실행 가능 여부를 다시 검사한다. 프런트엔드의 disabled 버튼만으로 제한하지 않는다.
5. InputManifest를 저장하고 선택된 파일만 전달한다. 코드 프로젝트 전체나 `.local-data` 전체를 입력 묶음에 포함하지 않는다.
6. App Server가 파일을 읽어야 하면 검증 workspace 안의 `.auto-codex/atelier-inputs/<generation-id>/`에 서버가 고른 이름으로 staging한다. 원본은 수정하지 않고 해시를 대조한다. staging 경로·덮어쓰기·용량·종료 후 보존/정리 정책을 구현한다.
7. 모델에 DB 경로나 비밀 파일을 주지 않는다. 백업/ZIP 파일은 자료이며 자동 압축 해제·설치·실행하지 않는다. 출력도 프로젝트 범위 안에 제한한다.
8. 기존 실행 경로를 통해 Team 또는 Solo로 시작한다. 실행 잠금은 일반 작업과 디자인 작업, 여러 브라우저 창에 공통으로 적용한다.
9. 실제 thread/turn와 Team의 run/task ID를 generation에 연결한다. 브리지는 해당 식별자로만 이벤트와 결과를 귀속시킨다.
10. 완료·실패·중단 후 실제 파일 존재·해시·허용 경로와 실행 기록을 검사해 ArtifactManifest를 만든다. 모델이 나열한 경로만으로 산출물 존재를 인정하지 않는다.

설계의 화면/리소스 범위는 **제작 대상과 결과 검수 범위**다. 파일 권한은 별도 sandbox 정책이 강제한다. 설계 범위를 골랐다는 이유로 샌드박스가 그 화면 파일에만 접근할 수 있다고 주장하지 않는다. 요청 밖 공통 코드 변경이 필요하면 이유와 영향 파일을 기록한다.

Team 제작은 기존 Coordinator·Visual Designer·Builder·QA·Integrator 역할을 활용한다. 단순한 작업에 모든 역할을 강제로 만들지 않는다. 기존 최대 Task 수와 읽기/쓰기 스케줄링을 넘기거나 별도 병렬 writer를 만들지 않는다.

### 7.4 실행 상태와 결과 판정

generation 상태는 실제 작업에 맞춰 준비/실행/승인 대기/완료/실패/중단을 추적한다. UI에 보이는 승인 대기는 pending 요청에서, editing/running 등 활동은 실제 item 이벤트에서 파생한다. 로컬 준비 이벤트는 App Server 이벤트와 출처를 구분한다.

실행 완료 후에도 다음은 별개로 남는다.

- 실행 완료: App Server가 작업 종료를 알렸다.
- 산출물 확인: 허용된 위치에 실제 결과가 존재한다.
- 검사 통과: 기록한 검사 명령이 해당 결과에 대해 통과했다.
- 시각 검토 완료: 해당 스냅샷의 시각 기준을 근거로 판정했다.
- 동작 검토 완료: 실제 실행 근거로 동작 기준을 판정했다.

부분 실패·산출물 누락·검사 미실행을 구분한다. 실패한 제작에서 생긴 파일이 있으면 부분 결과로 표시할 수 있지만 전체 성공으로 바꾸지 않는다. 승인 거부/연결 종료/프로젝트 경로 소실 시도 같은 원칙을 적용한다.

## 8. 결과·미리보기·수정 루프

### 8.1 실제 결과 등록

- 자동 연결 결과와 사용자의 수동 등록을 모두 제공한다.
- 자동 연결은 서버가 확인한 generation·snapshot·파일·출처를 사용한다. 사용자가 다른 프로젝트의 결과 ID로 바꿔 보내면 거부한다.
- 코드 결과와 실제 실행 기록을 저장할 수 있게 기존 ManualResult를 호환 가능한 방식으로 확장한다. 이미지가 없는 경우 스크린샷을 만들어 냈다고 표시하지 않는다.
- 과거 스냅샷으로 실행한 결과는 그 과거 버전에 남긴다. 현재 편집본과 다르다는 안내를 제공하고 최신 결과로 몰래 재연결하지 않는다.

### 8.2 미리보기의 단계

1. 1차: 코드/파일 목록·검사 로그·실제 등록된 PNG/JPEG/WebP 결과를 보여 준다.
2. 정적 HTML이 필요하면 별도 보안 경계로 구현한다. 기본은 script/form/navigation/network가 제한된 sandbox iframe 또는 스크립트 없는 렌더링이며 부모 앱의 DOM·WS·저장소에 접근하지 못하게 한다.
3. Vite 등 생성 앱을 실행하는 실시간 미리보기는 후속 범위다. 필요해지면 범용 셸 API 없이 명시된 실행 유형·loopback 포트·종료·타임아웃과 실제 승인 정책을 설계한다.

생성 HTML/SVG를 부모 앱에 innerHTML로 삽입하지 않는다. 임의 npm 스크립트나 설치 명령을 브리지가 자동 실행하지 않는다. CSP 완화, 외부 CDN 자동 로딩으로 미리보기를 성립시키지 않는다.

### 8.3 검토·수정

Atelier의 beginReview → reviewProblems/finishReview → createPlan → 새 makeSnapshot 규칙을 유지한다. AI 검토 의견은 사용자 판정과 별도다.

- 각 항목에 기대·실제 관찰·대상·근거·판정을 남긴다. 근거가 부족하면 unverifiable을 사용한다.
- 스크린샷만으로 동작 기준을 match 처리하지 않는다. 시각 검토와 행동 검토의 완료 범위를 구분한다.
- 수정 계획에는 바꿀 것·범위·유지할 것·재확인 방법을 고정한다. 새 수정본에서도 이미 맞았던 항목을 다시 확인한다.
- 기준 변경은 이유와 새 버전으로 남긴다. 과거 판정을 지우거나 새 결과에 그대로 복사하지 않는다.
- 자동 반복 제작은 기본으로 넣지 않는다. 사용자가 수정 제작을 시작할 때마다 새 generation이 생기고 기존 승인 경계를 적용한다.

## 9. 보안·호환성·복구 기준

실제 통합 구현은 R2다. 현재 문서 작성 자체는 R0다. 작업 보고에 다음 위협 분석과 검증 근거를 짧게 남긴다.

| 항목 | 통합에서의 기준 |
|---|---|
| 보호 대상 | 로컬 코드·설계·원본 파일·대화와 Codex 실행 권한 |
| 비신뢰 입력 | 브라우저 WS, 백업, 첨부, AI 출력, 생성 코드, 레퍼런스에 들어 있는 문장 |
| 주요 오용 | 프로젝트/파일 ID 변조, 경로 탈출, junction 전환, 오래된 제안 덮어쓰기, 승인 재전송, 실행 중복, 악성 미리보기 |
| 방어 계층 | 브리지 런타임 스키마·소유 관계·실제 경로 검사·고정 스냅샷·pending 승인 상관·sandbox |
| 실패 증거 | 프로젝트 간 참조·큰 입력·잘못된 ID·해시 불일치·만료 승인·경로 소실·동시 실행 거부 테스트 |
| 적용/복구 | 새 저장소 추가 → 검증된 가져오기 → 새 화면 전환. 기존 기록·원본 데이터는 보존 |

공통 유지 규칙:

- 서버는 127.0.0.1만 수신한다. 허용 Origin·Host·WS 경로를 좁게 검증하고 외부 origin을 새 기능 때문에 허용하지 않는다. 필요 시 로컬 세션 검증을 보강하되 사용자 계정 서비스를 새로 도입할 필요는 없다.
- cwd·staging·입출력 파일은 실제 경로와 허용 루트로 검증한다. non-directory·소실 경로·다른 프로젝트 파일·심볼릭 링크/junction 이탈을 거부한다.
- `thread/shellCommand`와 일반 셸 실행 endpoint를 추가하지 않는다. 승인 응답은 기존 pending App Server 요청의 ID와 요청된 권한 집합 안에서만 처리한다.
- 설계 제안이나 제작 요청을 “모든 명령/네트워크 허용”으로 해석하지 않는다. Codex turn의 네트워크 접근은 기본 차단하며 기존 조사 모드의 명시적 설정을 유지한다.
- 여기서 로컬 전용은 클라이언트·저장·브리지의 범위다. Codex 모델 요청에 전달되는 내용이 모델 제공 경로로 전송될 수 있음을 구분한다. 완전한 오프라인 모델 추론이라고 안내하지 않는다.
- AI 입력은 해당 목적과 범위에 필요한 확정 결정·선택 자료만 구성한다. 원본 자료의 문장을 시스템 지시나 추가 권한으로 취급하지 않는다.
- 원문 파일·토큰·비밀·환경 전체를 로그에 남기지 않는다. 진단용 protocol 이벤트의 보존·표시는 비밀을 제거하고 범위·크기를 제한한다.
- SVG·문서·아카이브·폰트의 원본 보관과 실행 가능 여부를 분리한다. 가져온 원본을 코드나 설치 대상으로 자동 승격하지 않는다.

복구는 UI와 데이터로 나눈다. 기존 Auto-Codex 화면으로 돌아갈 전환 경로를 이식 기간에 유지한다. 새 디자인 DB를 중단해도 일반 작업과 기존 대화가 열려야 한다. DB 구조를 바꾼 뒤 구버전 실행 파일로 단순 교체하면 복원된다고 가정하지 않는다. 일관된 DB·파일 백업과 해당 스키마를 읽는 버전을 함께 사용한다. 사용자 코드 변경은 별도 diff로 추적하며 통합 기능의 되돌리기가 사용자 코드를 자동 삭제해서는 안 된다.

## 10. 단계별 구현 순서와 복사용 명령

한 번에 전체 앱을 다시 쓰지 않고 아래 순서로 진행한다. 각 단계는 선행 단계의 완료 기준을 확인한 뒤 시작한다. 새 파일 경로·메시지 이름은 이 문서의 제안이며, 실제 구현 결과로 계약 문서를 갱신한다.

### 모든 단계에 붙일 공통 지시문

```text
docs/ATELIER_INTEGRATION_GUIDE.md를 기준으로 지정한 단계만 구현해줘.
루트와 대상 경로의 AGENTS.md/AGENTS.override.md, 현재 브랜치와 변경을 먼저 확인해줘.
기존 미커밋 변경을 보존하고, Auto-Codex와 Atelier의 기존 기능을 축소하지 마.
실제 소스와 가이드가 달라졌으면 근거를 확인하고 변경 범위를 설명한 뒤 진행해줘.
Atelier는 공통 디자인·설계 흐름의 기반, Auto-Codex 브리지는 실행·승인의 기반으로 유지해줘.
구현된 상태와 아직 제안인 계약을 구분하고, 가짜 AI 응답·산출물·완료 상태를 만들지 마.
외부 서비스·유료 API·배포는 추가하지 마. 일반 로컬 구현에 불필요한 재승인은 요청하지 마.
의미 있는 변경은 npm run typecheck, npm test, npm run build와 관련 실패 경로를 검증해줘.
```

## 11. 검증 방법과 통합 수용 기준

### 11.1 현재 존재하는 명령

Auto-Codex 루트에서:

```powershell
npm run typecheck
npm test
npm run build
node tools/verify-conversation-restart.mjs
```

마지막 재시작 검사는 빌드 후 실행한다. 현재 스크립트는 합성 App Server와 격리 폴더·로컬 4785를 사용한다. 구현 시 스크립트 부작용·변경 여부를 다시 확인한다.

Atelier 원본 기준선은 루트에서:

```powershell
npm --prefix atelier/atelier run check
npm --prefix atelier/atelier test
```

Atelier의 브라우저 시나리오 JS는 일반 npm test로 실행되는 완성된 E2E runner가 아니다. 제공된 Playwright page와 일부 작업 공간 절대경로를 전제로 하므로, 통합 E2E runner·fixture를 별도로 준비한 뒤 실행 명령을 문서화한다. 아직 존재하지 않는 `npm run test:e2e`를 통과한 것으로 보고하지 않는다.

문서만 바꾼 경우는 diff·경로·내용 검토로 충분하다. 실제 구현 단계에서는 공통 필수 검사와 변경 관련 테스트를 실행한다. 실제 모델 테스트는 합성 테스트와 구분하고 전달 자료·프로젝트·작업 범위를 기록한다.

### 11.2 테스트 계층

| 계층 | 핵심 검증 |

| 브리지 계약 | unknown type/field, 배열·문자열 크기, ID/버전/소유 관계, 제안 목적 readOnly, 기존 메시지 호환 |
