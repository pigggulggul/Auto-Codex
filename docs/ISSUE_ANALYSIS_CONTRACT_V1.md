# Analysis output and execution boundary

The source session can retrieve a single segment for trusted server code only. The lookup checks the connection, project generation, snapshot ID and revision, and the source ID and digest bound into the snapshot. Source selection changes, grant expiry and disconnection invalidate access. The returned segment and additional user request are private input; no browser endpoint exposes the internal lookup.

`analysis-output.ts` describes and independently validates the model-facing JSON contract. Output is bounded, unknown fields and duplicate object keys (including escaped aliases) are rejected, and IDs and provenance are assigned by the server. A `source` candidate requires a nonempty, unique, exact quote in the specific captured segment; its offsets are in UTF-16 units within the captured source. An `ai-proposal` has no quote and must include an uncertainty. Both are model-generated candidates requiring user review: an anchored quote does not prove that the candidate's interpretation is correct or complete. No candidate can change permissions, run a command, or register an issue.

`analysis-draft.ts` implements a model-independent, in-memory segment state machine. Its transport and source loader are trusted server dependencies; neither is exposed to browser input. It accepts results only after reloading and comparing the snapshot identity and segment, preserves completed segments when another fails, never retries automatically, and ignores late results after interruption. A transport that ignores cancellation keeps this draft busy until it settles; a future runtime must ensure the App Server has actually stopped before releasing shared admission. Aggregate candidate count is bounded. Failure responses contain codes, not raw model or transport errors.

Before transport, the draft copies the documented primitive segment fields into a frozen input. Rechecking compares against that captured input even if a loader reuses and mutates its own object; extra loader fields are not passed to transport. This protects the in-memory comparison, not the trustworthiness of the loader, source authorization, filesystem state, or runtime tool policy.

Disposing a draft clears the candidate references it retains, drops its source loader, and forbids reuse; batch disposal also disposes its draft. Cancellation rejects late results, but cannot recall data already handed to a transport or copied elsewhere, and JavaScript garbage collection does not guarantee immediate physical erasure. Runtime owners remain responsible for disposing on grant expiry or disconnection and for waiting for actual termination before releasing shared admission.

`analysis-batch.ts` sequences that draft's pending segments under an explicit per-run limit. It stops on the first failed or interrupted segment, preserves earlier candidates, and requires an explicit retry before processing resumes. Interrupt and disposal reject subsequent work while the active transport settles; late results are discarded by the draft. The batch is internal only, owns no transport or authorization and must have exclusive ownership of its draft. Its running flag is not the application's shared admission lock: a future runtime must hold that lock until the actual App Server turn has stopped, independently recheck original file hashes and authorization, and release all session data on expiry or disconnect. This sequencing does not enable a model call or guarantee complete analysis.

The bridge's server-only `createAnalysisBatch` binds that controller to the current view grant, project identity/revision and prepared snapshot. Before each segment and again after its transport returns, it reopens all selected originals and compares their captured metadata and hashes, checks the grant and runtime-supplied admission predicate around asynchronous work, and rejects changed or unreadable inputs. This is a point-in-time check, not an atomic filesystem lock: an original may change immediately afterward. No browser operation invokes this method; it does not itself authorize dispatch or connect a model.

The bridge reserves at most one batch per connection, including asynchronous creation, and blocks source selection, removal and replacement of the prepared snapshot while that reservation exists. It rechecks the reservation after asynchronous picker and project lookups. View release, connection abort, grant expiry, reauthorization and explicit project-source clearing dispose the owned batch and clear its retained candidates. If a transport ignores cancellation, the reservation remains until it settles; disposal is not evidence that the App Server or its descendants have stopped. A caller that finishes using an undisposed batch must dispose it to release the reservation. The caller must still own the application's shared admission, enforce a verified tool policy, and wait for actual runtime termination independently of this connection-scoped reservation.

The shared App Server client ignores output and exit events from a detached child, rejects that child's outstanding RPCs on stop, and shares a single termination-confirmation promise across concurrent stop requests. Both `stop()` and `stopAndWait()` use the same confirmation latch; the former does not return a promise to its caller, but subsequent starts and exclusive stops still respect the pending or failed confirmation. Trusting a project waits for confirmed stop before restarting. Failed initialization triggers confirmed shutdown; an unexpected exit of a spawned wrapper latches termination as unconfirmed until bridge restart. On Windows, exclusive stop requires both the wrapper's exit and a successful exit from `taskkill /T /F` for the exact spawned PID. A helper error, nonzero exit, or timeout keeps restart blocked until the bridge is restarted; falling back to killing the wrapper does not count as confirmed tree termination. These are process events and a helper's reported outcome, not independent proof that every descendant has terminated in every environment, and they do not establish model tool isolation.

The issue bridge now supports a tool-disabled Windows analysis worker and real model calls. A fresh App Server is started per segment with plugin, hook, shell and app features disabled; reported managed requirements and hooks are checked and configured MCP servers are disabled before dispatch. `environments: []`, read-only sandbox and `approvalPolicy: never` provide additional restrictions. These settings and checks were exercised against synthetic fixtures, but do not prove that every possible managed hook, dynamically inherited tool or CLI version is isolated. See the residual risk and live-test scope below.

The worker also rejects nonempty or malformed effective `hooks` configuration both before and immediately before model dispatch. This is independent of `hooks/list`, which may be empty when hooks are disabled; it does not prove that unreported managed hooks cannot execute.

`tools/verify-issue-wsl-isolation.py` is an opt-in diagnostic for an existing WSL installation with Python and bubblewrap. It uses a synthetic workspace-cache file and a local listener: a host-side positive connection is followed by a sandboxed write and loopback connection attempt. On the checked Ubuntu/WSL2 host, the positive control succeeded, the sandboxed write and connection failed, and the synthetic file remained unchanged. The probe does not route App Server commands through bubblewrap, establish an all-command approval mechanism, prove protection against all Linux/WSL escape paths, or enable command execution. In particular, the sandbox mounts system runtime files read-only; the check does not establish their suitability for untrusted production execution.

`analysis-request.ts` constructs a bounded, structured request from one selected segment and the additional user request. It serializes them as data and does not include source paths or hashes. The request explicitly treats source instructions as data, but this wording is not a security boundary: the future runtime still has to enforce access and tool permissions. Output is handled by the independent validation described above.

`analysis-turn.ts` provides an internal event collector for one dedicated thread. It binds provisional notifications to the turn ID returned by `turn/start`, rejects inconsistent early IDs, multiple final messages and unknown explicit message phases, bounds output, ignores commentary and foreign-thread events, and keeps failure and interruption distinct from completion. An absent or null phase remains accepted for compatibility. This collector does not enforce a tool policy, confirm termination or authorize an analysis.

For observed item start and completion events, the collector accepts only known text and context item types. A tool, hook prompt, or unknown item type on the active analysis thread triggers shutdown even when its turn ID is unexpected, including while the turn-start response is pending. During exclusive thread startup, such an event is treated conservatively as unsafe even before its thread ID is known; a late event from another thread can therefore interrupt startup. This is detection after a notification, not prevention: a tool may already have run, notifications may be missing, and hook execution is not necessarily represented by an item. It does not justify enabling the production policy.

`analysis-transport.ts` starts an ephemeral read-only thread and structured turn, forwards events to the collector, rejects unexpected server requests, and holds caller-provided admission if process termination cannot be confirmed after an uncertain start or interruption. It requires the trusted owner to enforce a tool policy, provide the authorization and admission callbacks, route events exclusively, and own the App Server process. Its callbacks do not themselves prove isolation. The current production fallback uses it inside the separate tool-disabled worker. Cancellation while project-path validation is pending releases admission without dispatching or stopping the server, and a late validation result cannot start a request. Cancellation while a start RPC is pending begins server termination without waiting for the RPC response; admission remains held until termination is confirmed. Late RPC responses cannot dispatch a subsequent turn. Termination itself is not instantaneous or guaranteed.

On 2026-11-06 an attempted synthetic App Server integration of this transport failed at the analysis end-to-end phase. The probe's Windows process-tree termination helper returned a nonzero exit, so termination could not be confirmed and the isolated scratch directory was preserved. Cleanup masked the initial failure, so its cause is not established. The attempted probe integration was removed; the earlier passing probe does not establish that `AnalysisTransport` works against the real CLI. Do not enable it on the basis of the synthetic unit tests.

After improving error reporting and the fixture's termination handling, a new synthetic run on CLI 0.166.0 routed App Server notifications and server requests through `AnalysisTransport`, passed a selected synthetic segment through the loopback fake provider and `AnalysisDraft`, and validated its anchored output. This run completed and its own process tree was reported stopped by the probe's checks. It does not identify the cause of the earlier failure, establish termination of the earlier process tree, test a real model or verify arbitrary inherited tools and managed hooks.

`analysis-execution.ts` coordinates a single trusted session's batch and transport under caller-provided shared admission. It exposes progress counts without source or candidate text, keeps admission through preparation and processing, interrupts active work, and retains admission if transport termination is unconfirmed. The isolated worker owns its own App Server event routing; the separate command-capable factory remains disabled.

The runtime factory registers each transport with the bounded late-event router only after acquiring shared admission and preparing a batch, immediately before transport work. Failed admission and batch preparation attempts do not consume router entries. If the router is full, admission is released and no request is dispatched. Registered transports are retained to contain late events until the App Server reports confirmed termination; then the router is cleared, and each later attempt registers its transport again. Failed or unexpected termination does not clear it. The limit still applies while one process remains alive. These behaviors are covered by synthetic tests and do not verify tool isolation.

The bridge and screen support analysis start, status, interrupt and clear messages through a server-owned execution factory. Requests are scoped to the existing per-connection view grant and validated snapshot/revision; the client cannot supply configuration, permissions or project identity. The production bridge now falls back to `analysis-isolated-factory.ts` and `analysis-isolated-transport.ts`: these pass only the segment text, additional instruction and server-selected model to a fresh restricted worker. The worker checks requirements, hooks, provider and MCP configuration, rechecks a private configuration fingerprint before dispatch, validates model output, and confirms App Server termination before replying. The parent retains shared admission if termination cannot be confirmed. The existing command-capable policy provider remains unavailable, so the active fallback does not offer command approvals. Status counts are not evidence of semantic completeness, and clearing a finished session discards its in-memory candidates.

View grants also record the server-observed project ID. The bridge checks it before source operations, view queries, export and analysis, and revokes the grant and selected copies when it detects a different project. Authorization confirms the same ID before and after the native picker. Source selection checks identity again after the picker and before reading, and after reading before accepting a copy. View and export pass the trusted project ID to the project context, which rejects a different worker lookup before querying or exporting. A late response associated with an older grant cannot revoke a replacement grant. These checks reduce stale-project exposure but are point-in-time checks; they are not atomic locks against filesystem or database changes.

The same connection may read one segment's candidates in size-bounded pages and request an explicit retry of a failed or interrupted segment. User interruption retains completed segments; grant revocation still disposes the retained session. The bridge binds a prepared snapshot and an execution to the server-observed project ID as well as its revision; a changed identity at the same revision invalidates the snapshot and results. Batch creation checks the captured ID again before dispatch. Missing or unreadable project state interrupts active analysis. Each read and retry rechecks the selected project and project revision, and candidate reads re-open selected originals and compare their hashes before returning a page. These are point-in-time checks, not filesystem locks. Stale results are rejected. Candidate source references and exact quotes are shown as model-generated proposals requiring review, not verified interpretations.

The screen can transfer an individually selected candidate into the planning form after a second explicit action. It retains the proposal designation after editing and includes the selected source path, hash, quotation, offsets and uncertainty when present. Those fields are submitted by the untrusted renderer as document data, not used as authorization or proof that the interpretation is correct. The source can change after candidate retrieval; draft registration does not re-read or authenticate the recorded evidence. The screen warns about this and the user must review the source independently.

The shared-server notification and server-request handlers call a bounded analysis router before general conversation routing, and the client and server permit a separately correlated, rate-limited interrupt alongside another issue request. The command-capable router has no registered production transport while its policy provider returns no verified policy; the active isolated worker routes its own App Server events. Synthetic tests cover the factory, routing and out-of-order client responses; these tests do not establish production tool isolation or actual turn interruption.

The probe now records a bounded, sanitized primary failure category separately from cleanup failure and termination outcome, and narrows the synthetic end-to-end phase labels without printing exception messages or source data. These changes cannot recover the earlier masked failure. Its reporting logic was tested with synthetic failures.

The internal transport retains up to 4096 owned thread IDs so late notifications stay out of a fallback conversation timeline and late server requests are denied. During thread startup, before its ID is known, it consumes notifications and denies server requests under the required exclusive admission. Tests exercise the fallback routing with synthetic events only; the production router has no registered analysis transport while its policy remains unavailable. A failed attempt to send a denial still marks the active turn denied and triggers termination handling.

An optional command-approval path now exists behind a verified server-owned policy and a separate, server-owned command containment check; production implements neither and the path is disabled. It forwards only command approvals with a known active thread and turn, a nonempty bounded command and working directory, and no network approval context, network policy amendments or remote environment. The owning connection alone can respond; session-wide acceptance is reduced to a single acceptance and the UI hides that option. The one-time approval screen warns that acceptance may permit writes and network access outside the sandbox. Interrupt invalidates the owner's pending approvals immediately, and completion also clears them. A cleanup failure keeps admission latched and attempts to stop the server. Requests arriving before the turn ID is known are still denied; other tool types are still rejected. Synthetic unit and factory integration tests exercise these controls, but they do not prove that `on-request` forces approval of every command, that approving a command preserves the read-only/network boundary, or that managed hooks and inherited services are isolated. Those gaps must be resolved before enabling this path for production input. The tests do not perform an actual model call.

The factory additionally requires an independent server-owned every-command approval coverage check, and rechecks it while the execution is admitted. This is a fail-closed integration prerequisite only: no production implementation provides that evidence, and a synthetic test callback is not evidence that App Server enforces it. The installed CLI describes `on-request` as allowing the model to decide whether to ask; it cannot by itself provide the required coverage.

The 2026-11-08 CLI fixture showed that local command approval requests include an environment ID matching the thread's selected environment. The runtime factory now requires a server-verified command environment ID and an independent containment check. The transport requests exactly that environment, checks the thread-start response's ID and working directory, and accepts an approval only for the same ID; mismatches fail closed. Matching an ID alone does not establish that the environment is local, so the production verifier must establish locality and containment independently. No production verifier or containment check is currently supplied.

The same synthetic CLI probe passes a forced command approval through `AnalysisTransport` using the selected synthetic local environment. Both the accepted and declined paths completed structured analysis and invoked the fixture approval cleanup. The accepted case created only its synthetic marker; the declined case did not. These tests use a fake loopback provider and a synthetic approval callback, not the actual WebSocket approval screen, real model inference, or a verified production policy. The tested local environment included both synthetic global and project instructions in the provider request.

On 2026-11-08 explicitly requested live tests used the existing Codex login, newly created synthetic workspaces, disabled feature overrides, managed-requirements and hook-list checks, and fixed synthetic input. A test through `IssueBridgeApi` and the production isolated factory received and validated one candidate from `gpt-6.1-sol`, queried it through the bridge, and observed admission release after the worker reported termination. Configured global Codex instructions may also have reached the provider. No user document or model output was printed. This validates the bridge path under that synthetic setup; it does not verify a browser/native-picker interaction, arbitrary CLI versions, or isolation of all user configurations. `tools/verify-issue-app-analysis.mjs` and direct smoke invocation can make real network requests and may incur usage; they are not part of the automatic test suite.

If denial, cancellation or policy revocation races with a terminal turn notification, the transport checks those conditions before treating the turn as terminal. It requests confirmed shutdown and retains admission if termination is unconfirmed. This avoids accepting the notification as a substitute for shutdown after a denied request; it does not prevent a tool that already started or establish production isolation.

Hooks remain a separate boundary. The [hooks documentation](https://learn.chatgpt.com/docs/hooks) describes managed hooks that can be forced on by policy; this probe does not establish that a thread-level override prevents them from running at startup. Similarly, enumerating real inherited MCP servers could itself start them. The fixture's `features.plugins` result does not authorize starting or inspecting a user's existing services as part of analysis.

The official hooks documentation explicitly states that administrator requirements can force hooks on even when disabled locally, and that `allow_managed_hooks_only` still allows managed hooks. Consequently, setting `features.hooks = false` on a thread is not a general guarantee that all hooks are disabled. This observation concerns possible managed configurations; it does not establish whether such a policy is present on this machine. A production implementation must account for enforced configuration without disabling or bypassing the user's policy, and cannot treat the synthetic probe as authorization to read or transmit real documents.

The installed CLI exposes `app-server --print-startup-config`. In a synthetic isolated home on CLI 0.166.0 the report parsed and contained a `configRequirements` response; the probe outputs only report shape, not configuration values. A subsequent negative-control attempt supplied a temporary `ProgramData` with a synthetic Windows requirements file requiring hooks, but that requirement was not reported. The test does not establish whether Windows ignored this environment override, the temporary file was not a supported policy source, or another condition applied. In particular, a null requirements report cannot yet be used as a verified test of the absence of managed hooks. The probe never changes the system policy. A separate one-time check of this shell found no file at the default Windows system-policy path and the CLI startup report indicated no requirements; that observation is scoped to that invocation and does not establish what the app's runtime or cloud-managed policy will load.

The later public [Codex loader implementation](https://github.com/openai/codex/blob/c3936b4b8a66b590b1ee4edd2276314899c87e8a/codex-rs/config/src/loader/mod.rs) resolves the Windows system requirements path through a machine policy registry entry or the Windows ProgramData known-folder API, rather than directly trusting the `ProgramData` environment variable. This explains why the temporary environment variable is not a reliable negative-control setup for that source revision. The public revision has not been matched to the installed binary; it does not prove how this installation resolves managed policy or authorize modifying system policy for a test.

`analysis-tool-policy.ts` builds an **unverified** candidate from effective configuration, complete paginated MCP replies, plugin metadata, and the reported managed requirements. It rejects discovery errors, incomplete pages, duplicate server identities, malformed records, overly large inventories, server names unsafe for dotted configuration paths, and known managed requirements that conflict with the candidate. It conservatively rejects every forced-on feature, including unknown future names, and non-null requirement fields it cannot interpret; this can reject harmless configurations. The probe checks those requirements and the effective hook configuration before installing its synthetic plugin or starting a thread. These checks do not prove the absence of every possible hook or tool. The builder keeps the full response data out of the returned policy, and maintains a private in-memory hash for comparing inventory snapshots; the hash can reflect credentials and must never be logged, persisted or sent to the browser. A mismatch means the inventory changed; matching hashes do not prove that undiscovered plugins or dynamically available tools cannot appear. The candidate is always marked `verified: false` and is not connected to model dispatch. Production enumeration itself could start inherited MCP processes, so the synthetic observations do not authorize querying a user's real services.

The candidate also requires a `hooks/list` response for the exact validated working directory, containing no hooks, errors or warnings. In the isolated CLI fixture the list was empty initially, detected an untrusted synthetic hook while it was present, and returned to empty after removal; the candidate rejected the positive control. This is evidence for that fixture and CLI version only. Managed policy, dynamically changing configuration and side effects of production plugin discovery remain unverified, so an empty list cannot by itself authorize dispatch.

The candidate includes additional deny settings based on OpenAI's [temporary structured request implementation](https://github.com/openai/codex/blob/57a808a3920f05f2d4b9eab2d0493e1df136ae6b/codex-rs/tui/src/temporary_structured_request.rs), including interactive input, extension tools and skill instructions. That source is a different revision from the installed CLI and is not a guarantee about this installation, managed hooks, or the completeness of tool isolation. The added options remain unverified and do not enable production dispatch.

The [official app-server behavior notes](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations) describe local shell and MCP tools as separate from hosted Responses tools. The [Agents API architecture](https://developers.openai.com/api/docs/guides/agents-api/architecture) describes remote MCP availability even without an environment, but it documents a different runtime and is not proof of App Server behavior. The [plugin documentation](https://developers.openai.com/plugins/build/plugins) also describes per-plugin MCP and lifecycle configuration. These sources do not establish a comprehensive App Server deny-all-tools switch. The worker's layered restrictions and monitoring therefore retain residual risk for untested CLI versions or inherited capabilities.

Further work must validate managed hooks and inherited connectors in the actual deployment environment, verify CLI-version compatibility, and independently enforce containment before enabling command-capable analysis. The current tool-disabled worker is limited to Windows and an OpenAI provider without proxy or base-URL environment overrides. Failures remain failures; they are not treated as completed analysis.
