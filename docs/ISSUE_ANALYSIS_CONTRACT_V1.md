# Analysis output and execution boundary

The source session can retrieve a single segment for trusted server code only. The lookup checks the connection, project generation, snapshot ID and revision, and the source ID and digest bound into the snapshot. Source selection changes, grant expiry and disconnection invalidate access. The returned segment and additional user request are private input; no browser endpoint exposes the internal lookup.

`analysis-output.ts` describes and independently validates the model-facing JSON contract. Output is bounded, unknown fields and duplicate object keys (including escaped aliases) are rejected, and IDs and provenance are assigned by the server. A `source` candidate requires a nonempty, unique, exact quote in the specific captured segment; its offsets are in UTF-16 units within the captured source. An `ai-proposal` has no quote and must include an uncertainty. Both are model-generated candidates requiring user review: an anchored quote does not prove that the candidate's interpretation is correct or complete. No candidate can change permissions, run a command, or register an issue.

`analysis-draft.ts` implements a model-independent, in-memory segment state machine. Its transport and source loader are trusted server dependencies; neither is exposed to browser input. It accepts results only after reloading and comparing the snapshot identity and segment, preserves completed segments when another fails, never retries automatically, and ignores late results after interruption. A transport that ignores cancellation keeps this draft busy until it settles; a future runtime must ensure the App Server has actually stopped before releasing shared admission. Aggregate candidate count is bounded. Failure responses contain codes, not raw model or transport errors.

Before transport, the draft copies the documented primitive segment fields into a frozen input. Rechecking compares against that captured input even if a loader reuses and mutates its own object; extra loader fields are not passed to transport. This protects the in-memory comparison, not the trustworthiness of the loader, source authorization, filesystem state, or runtime tool policy.

Disposing a draft clears the candidate references it retains, drops its source loader, and forbids reuse; batch disposal also disposes its draft. Cancellation rejects late results, but cannot recall data already handed to a transport or copied elsewhere, and JavaScript garbage collection does not guarantee immediate physical erasure. Runtime owners remain responsible for disposing on grant expiry or disconnection and for waiting for actual termination before releasing shared admission.

`analysis-batch.ts` sequences that draft's pending segments under an explicit per-run limit. It stops on the first failed or interrupted segment, preserves earlier candidates, and requires an explicit retry before processing resumes. Interrupt and disposal reject subsequent work while the active transport settles; late results are discarded by the draft. The batch is internal only, owns no transport or authorization and must have exclusive ownership of its draft. Its running flag is not the application's shared admission lock: a future runtime must hold that lock until the actual App Server turn has stopped, independently recheck original file hashes and authorization, and release all session data on expiry or disconnect. This sequencing does not enable a model call or guarantee complete analysis.

The bridge's server-only `createAnalysisBatch` binds that controller to the current view grant, project identity/revision and prepared snapshot. Before each segment and again after its transport returns, it reopens all selected originals and compares their captured metadata and hashes, checks the grant and runtime-supplied admission predicate around asynchronous work, and rejects changed or unreadable inputs. This is a point-in-time check, not an atomic filesystem lock: an original may change immediately afterward. The caller must actually own shared admission, enforce a verified tool policy and dispose/release the batch on expiry or disconnection. No browser operation invokes this method; it does not itself authorize dispatch or connect a model.

The shared App Server client ignores output and exit events from a detached child, rejects that child's outstanding RPCs on stop, and shares a single termination-confirmation promise across concurrent stop requests. On Windows, exclusive stop requires both the wrapper's exit and a successful exit from `taskkill /T /F` for the exact spawned PID. A helper error, nonzero exit, or timeout keeps restart blocked until the bridge is restarted; falling back to killing the wrapper does not count as confirmed tree termination. Ordinary best-effort stop does not provide this confirmation. These are process events and a helper's reported outcome, not independent proof that every descendant has terminated in every environment, and they do not establish model tool isolation.

No model transport or client operation is connected in this change. Local `codex-cli 0.166.0` generated schema describes an empty `environments` list as disabling environment access, and `shell_tool` is listed as a feature, but these observations alone do not demonstrate that every inherited MCP, app, plugin, web, or other tool is unavailable, nor do they prove the actual runtime enforces the selected-file boundary. Read-only sandbox and `approvalPolicy: never` alone do not establish that no unapproved tool call can occur. No real model was called while making these checks.

`analysis-request.ts` constructs a bounded, structured request from one selected segment and the additional user request. It serializes them as data and does not include source paths or hashes. The request explicitly treats source instructions as data, but this wording is not a security boundary: the future runtime still has to enforce access and tool permissions. Output is handled by the independent validation described above.

## Isolated App Server tool probe

`node tools/verify-issue-tool-boundary.mjs` exercises the Windows default `codex app-server` launch path with a temporary Codex home, synthetic project, synthetic MCP server and loopback-only fake Responses provider. It does not use the user's credentials, project, MCP configuration, or a real model. On `codex-cli 0.166.0`, with `environments: []`, a read-only sandbox, `networkAccess: false`, `approvalPolicy: never`, and several shell/app features disabled, the explicitly configured synthetic MCP server remained visible. Passing an empty `mcp_servers` map did not remove it. An individually disabled server disappeared from the model's tool list. Disabling the tested MCP server and the tested multi-agent, goal, image, shell, unified execution, and app features left `request_user_input` visible in this fixture.

On 2026-11-04 a sandboxed attempt did not produce a completed probe result and could not confirm termination of its synthetic CLI tree, so its isolated scratch directory was preserved. That attempt is not additional evidence of tool isolation. The probe cancels its turn polling and pending requests when the deadline expires, reports a sanitized failure phase, and preserves scratch data if tree termination cannot be confirmed. `node --test tools/issue-probe-control.test.mjs` checks timeout cancellation and late completion using synthetic inputs. On 2026-11-05 the revised full probe completed using an approved elevated run with `codex-cli 0.166.0-alpha.6`, the synthetic home and the loopback fake provider; its cleanup reported success. It repeated the described fixture controls, including disabled MCP and plugin tool calls and the structured segment round trip. It did not independently prove termination of every descendant, exercise managed hooks or establish a general deny-all-tools policy.

A later 2026-11-05 run, after adding the managed-requirements preflight, reached the `analysis-e2e` phase but failed to confirm termination of the synthetic CLI tree (`taskkill` helper exit 128). Its scratch directory `.cache/issue-tool-probe-NXx072` was preserved. The cleanup error obscured whether that phase had otherwise succeeded, so this run is not a completed probe or additional evidence of isolation. Subsequent changes classify the probe failure and wrapper exit separately without printing raw error details; they have not been verified against a failing CLI process.

The fake provider then emitted the same synthetic MCP function call twice. With the fixture MCP configured for automatic approval, the enabled case actually invoked the harmless fixture tool once. With that server disabled, the second invocation was rejected as unavailable and the fixture invocation count did not increase. This is a positive and negative control for that exact tool and configuration, not proof that arbitrary tools or other CLI versions are disabled. A forced `request_user_input` was also observed, but this probe does not establish a general denial policy for it. Only synthetic tool descriptors, outcome classes and counters are printed; prompts, file contents, credentials and raw diagnostics are not logged. The script asserts the observed fixture behavior so a future CLI change prompts review.

The probe now also creates two synthetic MCP servers, installs a synthetic plugin from a synthetic local marketplace into the temporary home, and enumerates all three MCP servers across three pages. A server-side candidate builder consumed those synthetic replies and created per-server disable overrides and a turn-level disabled plugin ID. Disabling only the ordinary servers left the plugin MCP visible. The generated candidate and plugin override left only `request_user_input` visible. A forced plugin MCP call reached the harmless fixture once when the plugin was enabled; with the plugin ID disabled, the same call was rejected and the invocation count did not increase. This verifies the tested plugin's tool behavior during a turn, not plugin startup, hooks, arbitrary plugins or managed/remote marketplaces. Only the local marketplace scope was queried.

For this same synthetic plugin, setting `features.plugins` to false at thread start also removed its tool and caused the forced call to be rejected. The probe adds synthetic global and project instruction markers: the global marker still reached the fake provider with `project_doc_max_bytes: 0`, while the marker in the untrusted synthetic project did not. This does not prove how trusted project instructions or other versions behave. The [global instructions documentation](https://learn.chatgpt.com/docs/agent-configuration/agents-md) describes the global instruction layer. Existing Codex configuration can therefore add context to a model request, and the UI must disclose it before dispatch.

The probe also passes a synthetic selected segment through the actual request builder and App Server to the loopback fake provider, receives a structured synthetic response, and validates it through `AnalysisDraft`. It checks that the selected text, additional request, and output schema reached the provider, that the source path did not, and that the returned quote is anchored to the selected segment. This is an integration test with no real inference, not a production transport or proof of tool isolation.

Hooks remain a separate boundary. The [hooks documentation](https://learn.chatgpt.com/docs/hooks) describes managed hooks that can be forced on by policy; this probe does not establish that a thread-level override prevents them from running at startup. Similarly, enumerating real inherited MCP servers could itself start them. The fixture's `features.plugins` result does not authorize starting or inspecting a user's existing services as part of analysis.

`analysis-tool-policy.ts` builds an **unverified** candidate from effective configuration, complete paginated MCP replies, plugin metadata, and the reported managed requirements. It rejects discovery errors, incomplete pages, malformed records, overly large inventories, server names unsafe for dotted configuration paths, and known managed requirements that conflict with the candidate, including enforced hooks or plugins. The probe checks those requirements and the effective hook configuration before installing its synthetic plugin or starting a thread. These checks do not prove the absence of every possible hook or tool. The builder keeps the full response data out of the returned policy, and maintains a private in-memory hash for comparing inventory snapshots; the hash can reflect credentials and must never be logged, persisted or sent to the browser. A mismatch means the inventory changed; matching hashes do not prove that undiscovered plugins or dynamically available tools cannot appear. The candidate is always marked `verified: false` and is not connected to model dispatch. Production enumeration itself could start inherited MCP processes, so the synthetic observations do not authorize querying a user's real services.

The [official app-server behavior notes](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations) describe local shell and MCP tools as separate from hosted Responses tools. The [Agents API architecture](https://developers.openai.com/api/docs/guides/agents-api/architecture) describes remote MCP availability even without an environment, but it documents a different runtime and is not proof of App Server behavior. The [plugin documentation](https://developers.openai.com/plugins/build/plugins) also describes per-plugin MCP and lifecycle configuration. These sources do not establish a comprehensive App Server deny-all-tools switch. The freshness-check UI and its file comparisons do not resolve that capability gap or enable a model call.

Before enabling real analysis, verify an enforceable deny-by-default tool and environment configuration for the installed App Server; validate it under prompt injection and tool-call attempts, including inherited connectors. Integrate the existing global admission, interrupt, exit and pending-request paths. Recheck the actual project and source hashes before dispatch, confirm the selected segment and additional request are sent to the model only after a clear user action, validate provider output, bound time and resources, and prevent late or stale results from applying. Clearly disclose that model inference transmits the selected data through the configured Codex provider. Until those conditions are met, the existing UI remains in preparation-only mode.
