# Analysis output and execution boundary

The source session can retrieve a single segment for trusted server code only. The lookup checks the connection, project generation, snapshot ID and revision, and the source ID and digest bound into the snapshot. Source selection changes, grant expiry and disconnection invalidate access. The returned segment and additional user request are private input; no browser endpoint exposes the internal lookup.

`analysis-output.ts` describes and independently validates the model-facing JSON contract. Output is bounded, unknown fields and duplicate object keys (including escaped aliases) are rejected, and IDs and provenance are assigned by the server. A `source` candidate requires a nonempty, unique, exact quote in the specific captured segment; its offsets are in UTF-16 units within the captured source. An `ai-proposal` has no quote and must include an uncertainty. Both are model-generated candidates requiring user review: an anchored quote does not prove that the candidate's interpretation is correct or complete. No candidate can change permissions, run a command, or register an issue.

`analysis-draft.ts` implements a model-independent, in-memory segment state machine. Its transport and source loader are trusted server dependencies; neither is exposed to browser input. It accepts results only after reloading and comparing the snapshot identity and segment, preserves completed segments when another fails, never retries automatically, and ignores late results after interruption. A transport that ignores cancellation keeps this draft busy until it settles; a future runtime must ensure the App Server has actually stopped before releasing shared admission. Aggregate candidate count is bounded. Failure responses contain codes, not raw model or transport errors.

Before transport, the draft copies the documented primitive segment fields into a frozen input. Rechecking compares against that captured input even if a loader reuses and mutates its own object; extra loader fields are not passed to transport. This protects the in-memory comparison, not the trustworthiness of the loader, source authorization, filesystem state, or runtime tool policy.

Disposing a draft clears the candidate references it retains, drops its source loader, and forbids reuse; batch disposal also disposes its draft. Cancellation rejects late results, but cannot recall data already handed to a transport or copied elsewhere, and JavaScript garbage collection does not guarantee immediate physical erasure. Runtime owners remain responsible for disposing on grant expiry or disconnection and for waiting for actual termination before releasing shared admission.

`analysis-batch.ts` sequences that draft's pending segments under an explicit per-run limit. It stops on the first failed or interrupted segment, preserves earlier candidates, and requires an explicit retry before processing resumes. Interrupt and disposal reject subsequent work while the active transport settles; late results are discarded by the draft. The batch is internal only, owns no transport or authorization and must have exclusive ownership of its draft. Its running flag is not the application's shared admission lock: a future runtime must hold that lock until the actual App Server turn has stopped, independently recheck original file hashes and authorization, and release all session data on expiry or disconnect. This sequencing does not enable a model call or guarantee complete analysis.

The bridge's server-only `createAnalysisBatch` binds that controller to the current view grant, project identity/revision and prepared snapshot. Before each segment and again after its transport returns, it reopens all selected originals and compares their captured metadata and hashes, checks the grant and runtime-supplied admission predicate around asynchronous work, and rejects changed or unreadable inputs. This is a point-in-time check, not an atomic filesystem lock: an original may change immediately afterward. No browser operation invokes this method; it does not itself authorize dispatch or connect a model.

The bridge reserves at most one batch per connection, including asynchronous creation, and blocks source selection, removal and replacement of the prepared snapshot while that reservation exists. It rechecks the reservation after asynchronous picker and project lookups. View release, connection abort, grant expiry, reauthorization and explicit project-source clearing dispose the owned batch and clear its retained candidates. If a transport ignores cancellation, the reservation remains until it settles; disposal is not evidence that the App Server or its descendants have stopped. A caller that finishes using an undisposed batch must dispose it to release the reservation. The caller must still own the application's shared admission, enforce a verified tool policy, and wait for actual runtime termination independently of this connection-scoped reservation.

The shared App Server client ignores output and exit events from a detached child, rejects that child's outstanding RPCs on stop, and shares a single termination-confirmation promise across concurrent stop requests. On Windows, exclusive stop requires both the wrapper's exit and a successful exit from `taskkill /T /F` for the exact spawned PID. A helper error, nonzero exit, or timeout keeps restart blocked until the bridge is restarted; falling back to killing the wrapper does not count as confirmed tree termination. Ordinary best-effort stop does not provide this confirmation. These are process events and a helper's reported outcome, not independent proof that every descendant has terminated in every environment, and they do not establish model tool isolation.

No model transport or client operation is connected in this change. Local `codex-cli 0.166.0` generated schema describes an empty `environments` list as disabling environment access, and `shell_tool` is listed as a feature, but these observations alone do not demonstrate that every inherited MCP, app, plugin, web, or other tool is unavailable, nor do they prove the actual runtime enforces the selected-file boundary. Read-only sandbox and `approvalPolicy: never` alone do not establish that no unapproved tool call can occur. No real model was called while making these checks.

`analysis-request.ts` constructs a bounded, structured request from one selected segment and the additional user request. It serializes them as data and does not include source paths or hashes. The request explicitly treats source instructions as data, but this wording is not a security boundary: the future runtime still has to enforce access and tool permissions. Output is handled by the independent validation described above.

`analysis-turn.ts` provides an internal event collector for one dedicated thread. It binds provisional notifications to the turn ID returned by `turn/start`, rejects inconsistent early IDs and multiple final messages, bounds output, ignores commentary and foreign-thread events, and keeps failure and interruption distinct from completion. This collector does not send a request, enforce a tool policy, confirm termination or authorize an analysis, and is not yet connected to a browser or production transport.

`analysis-transport.ts` is an internal, dependency-injected transport tested with a synthetic server. It starts an ephemeral read-only thread and structured turn, forwards events to the collector, rejects unexpected server requests, and holds caller-provided admission if process termination cannot be confirmed after an uncertain start or interruption. It requires the trusted owner to enforce a verified tool policy, provide the authorization and admission callbacks, route events exclusively, and own the App Server process. Its callbacks do not themselves prove isolation. It is not wired to the production bridge or the browser, and no real analysis is enabled by this module. Cancellation while a start RPC is pending begins server termination without waiting for the RPC response; admission remains held until termination is confirmed. Late RPC responses cannot dispatch a subsequent turn. Termination itself is not instantaneous or guaranteed.

`analysis-execution.ts` coordinates a single trusted session's batch and transport under caller-provided shared admission. It exposes progress counts without source or candidate text, keeps admission through preparation and processing, interrupts active work, and retains admission if transport termination is unconfirmed. The production runtime must still connect policy and exclusive event routing.

The bridge and screen support analysis start, status, interrupt and clear messages through a server-owned execution factory. Requests are scoped to the existing per-connection view grant and validated snapshot/revision; the client cannot supply configuration, permissions or project identity. Synthetic integration tests exercise the request and interruption paths. The production bridge now connects its factory to the App Server, shared admission and analysis event router, but its policy provider deliberately returns no verified policy. Start therefore returns `ANALYSIS_UNAVAILABLE` and no model is called. A real tool/hook verifier, production isolation validation and actual model execution remain unimplemented. Status counts are not evidence of semantic completeness, and clearing a finished session discards its in-memory candidates.

The same connection may read one segment's candidates in size-bounded pages and request an explicit retry of a failed or interrupted segment. User interruption retains completed segments; grant revocation still disposes the retained session. Each read and retry rechecks the selected project and project revision, and candidate reads re-open selected originals and compare their hashes before returning a page. These are point-in-time checks, not filesystem locks. Stale results are rejected. Candidate source references and exact quotes are shown as model-generated proposals requiring review, not verified interpretations. The bridge and screen paths are exercised with synthetic inputs; production execution and actual results are still unavailable.

The production notification and server-request handlers call a bounded analysis router before general conversation routing, and the client and server permit a separately correlated, rate-limited interrupt alongside another issue request. The router has no registered production transport while the policy provider returns no verified policy. Synthetic tests cover the factory, routing and out-of-order client responses; these tests do not establish production tool isolation or actual turn interruption.

The probe now records a bounded, sanitized primary failure category separately from cleanup failure and termination outcome, and narrows the synthetic end-to-end phase labels without printing exception messages or source data. These changes cannot recover the earlier masked failure. Its reporting logic was tested with synthetic failures.

The internal transport retains up to 4096 owned thread IDs so late notifications stay out of a fallback conversation timeline and late server requests are denied. During thread startup, before its ID is known, it consumes notifications and denies server requests under the required exclusive admission. Tests exercise the fallback routing with synthetic events only; the production bridge has not yet been connected to this router. A failed attempt to send a denial still marks the active turn denied and triggers termination handling.

The [Agents API architecture](https://developers.openai.com/api/docs/guides/agents-api/architecture) describes remote MCP availability even without an environment, but it documents a different runtime and is not proof of App Server behavior. These sources do not establish a comprehensive App Server deny-all-tools switch. The freshness-check UI and its file comparisons do not resolve that capability gap or enable a model call.

Before enabling real analysis, verify an enforceable deny-by-default tool and environment configuration for the installed App Server; validate it under prompt injection and tool-call attempts, including inherited connectors. Integrate the existing global admission, interrupt, exit and pending-request paths. Recheck the actual project and source hashes before dispatch, confirm the selected segment and additional request are sent to the model only after a clear user action, validate provider output, bound time and resources, and prevent late or stale results from applying. Clearly disclose that model inference transmits the selected data through the configured Codex provider. Until those conditions are met, the existing UI remains in preparation-only mode.
