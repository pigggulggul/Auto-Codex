# 이슈 실행 후보 판정 기반

`server/issues/execution-candidates.ts`는 선택된 이슈의 실행 후보를 계산하는 서버 내부 순수 함수다. 유효한 전체 이슈 그래프를 전제로 숫자 버전·순서·ID 순으로 정렬하며, 구조 오류가 하나라도 있으면 부분 후보를 반환하지 않는다. 기본 대상은 `ready`이고 `retryable`과 `failed`는 호출자가 명시해야 한다. 완료 조건 부재, 검토 필요, 로컬 완료 근거가 없는 선행 이슈는 제외 사유로 표시한다. 선택한 다른 이슈가 나중에 완료될 것이라고 가정하지 않는다.

이슈 상세는 현재 문서 전체의 저장된 이슈와 로컬 상태를 고정 revision에서 읽어 선택한 이슈 하나에 대한 기본 사전 점검을 표시한다. 기본 대상은 `ready`만이며 완료 조건 유무, `needs_review` 상태와 선행 이슈의 로컬 완료 여부를 확인한다. 현재 저장소에는 로컬 완료 근거가 없으므로 모든 선행 이슈를 미확인으로 취급한다. 제외 사유가 없어도 이 점검은 문서의 의미적 완전성이나 실제 실행 가능성을 보증하지 않는다. 이 응답은 기존 보기 권한·문서·revision에 한정되고 실제 실행 기능이나 인가·잠금·승인이 아니다. `locallyVerifiedComplete`는 규격 문서의 `completed` 값에서 유도하면 안 된다. 향후 실행 호출자는 신뢰할 수 있는 전체 프로젝트 스냅샷과 별도로 검증된 로컬 완료 근거를 제공해야 하며, 각 dispatch 전에 프로젝트·revision·선행 조건을 다시 검사해야 한다. 공유 admission, 실행 정책, 중단, 중복 방지 및 영속 시도 기록도 별도로 필요하다. 이 기반을 추가해도 데이터 이전, 모델 호출, 프로젝트 파일 변경은 발생하지 않는다. 상세 응답 계약이 확장되므로 브리지와 UI를 함께 갱신한다.

화면에서 같은 문서의 이슈를 최대 8개 선택해 한 번의 읽기 요청으로 점검할 수 있다. 브리지와 워커는 ID 형식·개수·중복을 확인하고, 워커는 선택한 모든 ID가 같은 문서에 속하는지 확인한다. 하나의 문서 읽기 결과로 후보를 판정하며, 저장소는 읽기 전후 revision을 검사한다. 이는 모든 외부 프로세스의 변경을 막는 원자적 잠금은 아니다. 요청 전후 소켓별 보기 권한을 확인하며 조회 실패나 화면 상태 변경 시 결과를 표시하지 않는다. 선택은 페이지와 필터 변경 시 유지하며 문서·프로젝트 revision·보기 권한 변경 시 지운다. 응답은 선택 순서로 ID·제목·버전·지정 순서·제외 사유를 반환하고 화면은 숫자 버전·지정 순서·ID로 정렬한다. 이 표시는 실행 순서를 확정하거나 다른 선택 항목의 선행 완료를 가정하지 않는다. 선택과 결과는 화면 메모리에만 존재하고 실행·승인·상태 변경을 시작하지 않는다. 조회 응답 계약에 맞춰 브리지와 화면을 함께 갱신하며 데이터 마이그레이션은 없다.

각 결과에는 미확인 선행 이슈 수와 문서에 기록된 순서의 앞 3개 ID·제목도 포함한다. 현재 로컬 완료 근거가 없으므로 문서에 완료로 표시된 선행 항목을 포함해 모든 직접 선행 이슈가 미확인이다. 화면에서 선행 이슈 상세를 열 수 있고, 3개를 초과하면 해당 이슈 상세에서 나머지를 조회한다. 모든 상세 조회는 기존 보기 권한·문서·revision 검사를 다시 적용한다. 이 정보는 이슈 실행이나 완료 판정이 아니다.

다중 점검은 기본적으로 대기 상태만 포함한다. 사용자는 재시도 필요와 실패 상태를 각각 명시적으로 포함해 다시 점검할 수 있으며, 결과에 적용된 옵션과 각 이슈의 로컬 상태를 반환한다. 옵션은 기본적으로 꺼져 있고 문서·revision·보기 권한이 바뀌면 초기화된다. 옵션 변경은 이전 결과를 지운다. 포함을 선택해도 완료 조건 누락·검토 필요·미확인 선행 이슈는 계속 제외 사유이며, 이 선택은 실행 권한·재시도 요청·자동 실행이 아니다. 브리지·워커는 명시된 두 불리언 외의 필드를 거부하고 화면은 요청과 응답 옵션의 일치 여부를 확인한다. 새 응답 계약을 위해 브리지와 화면을 함께 갱신한다.

## 시도 상태 표시 기반

`execution-attempt.ts`는 연결되지 않은 서버 내부 상태 전이 함수다. 신뢰된 실행 계층이 실제 발행한 thread/turn ID를 먼저 연결하고, 일치하는 시작 이벤트를 관찰해야 `running`이 된다. 승인 요청은 일치하는 turn과 요청 ID로 추적하며 여러 요청이 있으면 모두 해제될 때까지 대기 표시를 유지한다. 실행과 검증 중의 중단 요청은 각각 기록하되 실제 종료를 확정하지 않으며, 검증 종료 시 정상 종료·실패·중단·결과 불명을 구분한다. 검증 정상 종료는 절차가 끝났다는 표시일 뿐 이슈의 완료 조건이나 검증 근거가 충족됐다는 뜻이 아니다. 실제 turn 완료도 검증 단계로 넘어갈 뿐 이슈 완료를 결정하지 않는다. 전송 결과가 불명확하면 `outcome_unknown`으로 남기고 자동 재시도하지 않는다.

실행 중 중단을 요청한 뒤 실제 turn이 정상 종료되더라도 검증을 자동 시작하지 않고 `verification_not_started`로 남긴다. 이는 turn이 중단됐다는 뜻이 아니며, 실제 turn 종료와 검증 미실시를 별도로 보존해야 한다.

이 함수는 이벤트의 진위나 완료 근거를 검증하지 않고 승인·중단 요청을 보내지도 않는다. 향후 연동 시 호출자가 실제 App Server 요청/응답에 ID를 연결하고, ID 연결 전에 도착한 이벤트를 안전하게 처리해야 한다. `settled`나 `outcome_unknown`은 실제 프로세스 종료 또는 공유 admission 해제의 증거가 아니다. 저장·복구·중복 방지와 검증 근거에 따른 이슈 상태 변경 역시 별도로 구현해야 한다.

검증 결과는 이 시도에 연결된 thread와 turn에 일치해야 반영하며 제어 문자가 있는 프로토콜 ID는 거부한다. 승인 요청이 아직 해결되지 않은 상태에서 turn 종료가 관찰되면 검증을 자동으로 시작하지 않고 결과 불명으로 남긴다. 실행 후보의 이슈 ID도 교환 문서의 식별자 형식을 따라야 한다. 실제 요청의 진위와 승인 취소·프로세스 종료 여부는 여전히 호출자가 확인해야 한다.
