# 이슈 실행 저널 기반

`server/issues/execution-journal.ts`는 선택된 한 이슈 시도의 중복 방지 및 전송 경계를 저장하는 **서버 내부 기반**이다. 현재 앱의 SQLite 스키마·브리지·UI·App Server 실행 경로에는 연결되지 않는다. 제공된 SQL은 마이그레이션 초안일 뿐이며, 운영 또는 기존 사용자 DB에 적용하지 않았다.

- 동일 프로젝트의 동일 idempotency key와 동일 이슈·revision·서버 계산 요청 해시는 기존 시도를 반환한다. 같은 키에 다른 입력이 오면 충돌로 거부한다. 한 프로젝트에 `prepared`, `dispatching`, `running`, `verifying`, `outcome_unknown` 중 하나만 둘 수 있다. 서로 다른 프로젝트는 별도로 추적한다.
- 외부 전송 **전** `dispatching`을 SQLite 트랜잭션에 저장해야 한다. 실제 연결된 turn의 시작을 확인한 뒤에만 `running`으로 바꾸며 thread/turn ID는 기록이다. 종료가 실제로 확인됐거나 전송 전인 경우에만 호출자가 `settle`을 요청해야 한다.
- 검증을 시작하기 전에 `running`에서 `verifying`으로 변경하며, 실제 검증 종료를 확인할 때까지 같은 프로젝트의 다음 시도를 막는다. 정상 종료 기록인 `verification_finished`는 `verifying`에서만 허용하며 검증 절차의 종료 기록일 뿐 완료 조건 충족이나 이슈 완료의 근거가 아니다. 검증 미실시를 이유로 정상 완료하거나 잠금을 해제할 수 없다. 실패·중단도 호출자가 실제 종료를 확인한 뒤에만 기록해야 한다.
- 응답·종료 결과가 불명확하면 `outcome_unknown`으로 남겨 같은 키를 재전송하지 않고 다른 키도 막는다. 재시작 복구는 전송 전 `prepared`를 중단으로, `dispatching`·`running`·`verifying`을 결과 불명으로 변경한다. 알려진 thread/turn ID는 과거 기록으로 보존하며 활성 세션이나 승인 요청으로 복원하지 않는다.
- 결과 불명 해제 및 재시도는 아직 구현하지 않았다. 실행 환경·파일 변경·종료 상태를 사용자가 확인하고 복구할 수 있는 별도 계약이 필요하며, DB를 직접 수정해 잠금을 없애는 것은 안전한 복구 절차가 아니다.
- 초안 스키마는 시도 단계와 결과의 일관성, thread/turn ID 쌍과 필수 단계를 검사한다. 입력에 정의되지 않은 필드나 제어 문자를 포함한 프로토콜 ID는 거부한다. 조회와 재시작 복구는 기록을 다시 확인하며, 손상된 기록이 있으면 복구 전체를 중단한다. 이는 동일 OS 사용자가 DB와 제약을 바꾸는 공격에 대한 보안 경계가 아니다.

이 모듈은 호출자를 인증하지 않고 프로젝트 소유권·revision·선행 조건·요청 해시·turn 이벤트의 진위를 검증하지 않는다. 신뢰된 실행 계층이 고정된 입력으로 해시를 계산하고 실제 App Server 이벤트를 연계해야 한다. 저널의 프로젝트별 제약은 대화·아뜰리에를 포함하는 공유 admission, 실제 프로세스 종료 확인, 네트워크·도구 권한 또는 OS 수준 잠금을 대체하지 않는다. 재시작 복구는 다른 프로세스가 같은 저널을 사용하지 않으며 이전 런타임의 종료가 확인된 이후에만 호출해야 한다. 결과 불명인 동안 현재 런타임의 admission을 해제해도 안전하다고 추론하면 안 된다.

적용 전에 기존 DB 백업·버전 관리·트랜잭션 마이그레이션, SQLite의 `synchronous` 및 파일시스템 내구성, 다중 프로세스 소유권, 충돌·비정상 종료·복구 UI를 설계하고 검증해야 한다. 이번 `verifying` 단계는 미연결 스키마 초안의 변경이며 이전 실험용 저널 DB를 자동 이전하지 않는다. 이 초안은 자체적으로 스키마 설치나 DB 설정을 수행하지 않으며 저장 데이터를 암호화하지 않는다. DB를 쓸 수 있는 동일 OS 사용자의 악의적 변경을 방어하지 않는다. 테스트는 합성 DB에서만 실행한다.
