# 이슈 실행 저널 기반

상태 안내 (2026-11-09): `IssueExecutionRuntime`과 App Server 전송기의 내부 연결 및 합성 테스트가 추가되었다. 아래의 연결 전 설명은 사용자에게 노출된 실행 API가 없다는 뜻으로 읽어야 한다. 사용자 실행·중단·복구 UI, 실제 실행의 전 구간 검증은 아직 완료되지 않았다. 실행 런타임은 소유 연결이 끊기면 전송 후 종료를 요청하며, 종료나 저장이 불확실하면 결과 불명으로 남긴다.

`server/issues/execution-journal.ts`는 선택된 한 이슈 시도의 중복 방지 및 전송 경계를 저장한다. 이슈 저장소 스키마 v4와 연결별 프로젝트 보기 권한을 확인하는 읽기 전용 실행 기록 화면이 연결되어 있다. App Server 실행과 복구 전이는 아직 연결되지 않아 화면이 실행이나 복구를 시작하지 않는다. v1·v2·v3 저장소는 변경 전 각각 SQLite 일관 백업을 남기고 트랜잭션으로 v4를 설치한다. 구버전 앱은 v4 저장소를 열 수 없으므로 복구 시 앱을 중지하고 백업을 별도로 보존한 뒤 적절한 버전의 백업을 복원해야 하며, 백업 이후의 변경은 자동 복구되지 않는다.

`execution-approval-journal.ts`와 내부 저장소 워커는 프로젝트·시도·thread·turn을 대조해 요청 유형과 요청 ID의 해시, 사용자 결정 및 전송 상태를 기록한다. 응답 전 `responding`을 저장하고 전송 결과가 불명확하면 `outcome_unknown`을 남긴다. 결과 불명인 시도의 대기 요청은 `expired`, 전송 중 응답은 `outcome_unknown`으로 정리할 수 있으나, 이는 메모리에 남은 실제 요청을 취소하거나 프로세스 종료를 증명하지 않으며 시도 잠금도 해제하지 않는다. 이 내부 API는 아직 App Server 이벤트·승인 UI에 연결되지 않았으며, 호출자가 현재 요청 소유권과 admission을 별도로 확인해야 한다. 명령이나 파일 내용은 승인 저널에 기록하지 않는다.

시도 저널은 미응답·전송 중·전송 결과 불명인 승인이 남으면 검증 시작과 정상 종료를 거부한다. 시도를 결과 불명으로 변경하는 작업과 승인 상태 정리는 같은 SQLite 트랜잭션으로 수행한다. `execution-approval-relay.ts`는 신뢰된 런타임이 제공하는 연결·소유권 검사와 저장 콜백을 이용해 요청 표시 전과 응답 전송 전에 기록하고, 연결 중단·기록 실패·전송 불명 시 실패 콜백을 호출하는 내부 어댑터다. `execution-approval-router.ts`는 App Server 요청 처리와 소유 연결의 승인 응답 경로에 등록되어 있으나 이슈 실행 런타임이 아직 세션을 등록하지 않으므로 현재 활성화되지 않는다. 합성 SQLite·프로토콜 테스트는 실제 권한 검증이나 프로세스 종료의 증거가 아니다.

`CodexAppServer.respondAndWait`는 자식 프로세스의 stdin 쓰기 콜백 완료를 기다리고, 스트림 오류·종료·시간 초과·프로세스 교체를 전송 불명으로 처리한다. 성공은 로컬 스트림 쓰기의 완료만 뜻하며 서버가 응답을 처리했거나 승인된 작업이 실행됐다는 증거가 아니다. 합성 App Server 요청을 파서, 내부 중계기, SQLite와 이 메서드로 연결한 테스트가 있으나 실제 이슈 실행 경로에는 연결되지 않았다.

App Server 서버 요청 핸들러와 승인 응답 핸들러에는 이슈 실행 승인 라우터가 등록되어 있다. 신뢰된 서버 런타임이 시도·thread·소유 연결과 저장/중단 콜백을 등록한 경우에만 해당 경로가 활성화된다. `registerStarting`은 `turn/start` 전에 요청 채널을 선점하고 turn을 바인딩하기 전 요청은 거부하며 중단 콜백을 호출한다. 호출자는 실제 `turn/start` 응답과 저널 기록을 확인한 뒤에만 `bindTurn`을 호출해야 한다. 바인딩 후에는 실제 요청을 저장한 후 소유 연결에만 일회성 승인 화면을 보내고, 응답 전에도 기록하며, 다른 연결이나 다른 turn은 거부한다. 이슈 실행 런타임이 아직 이 세션을 등록하지 않으므로 현재 사용자 기능은 활성화되지 않는다. 등록된 콜백에서 실제 admission·프로젝트·현재 요청을 재검사해야 한다.

`registerLaunching`은 `thread/start` 전에 채널을 선점하며 thread·turn 식별자를 순서대로 한 번씩만 바인딩한다. 식별자가 아직 없거나 권한이 철회된 상태의 서버 요청, 잘못된 바인딩 및 소유 연결 종료는 거부·중단한다. 시작이 불명확하거나 승인 요청이 남은 상태에서 등록을 닫으면 라우터를 유지하여 늦은 서버 요청을 계속 거부하며, 같은 App Server의 종료 확인 이벤트에서만 이를 해제한다. 합성 프로토콜 시험은 이 순서와 저널·응답 연결을 확인하지만 실제 App Server의 종료나 운영 실행 런타임 등록을 증명하지 않는다.

저장소 워커의 내부 `execution.prepare`와 `execution.transition`은 저장된 이슈를 읽어 시도를 준비하고 전송·실행·검증·결과 불명·종료 단계를 기록한다. DB 쓰기 트랜잭션 안에서 프로젝트 revision을 다시 검사하며, 응답이 유실되면 변경 결과를 불명으로 취급한다. 이 내부 요청은 브라우저 API가 아니며 호출 자체가 프로젝트 권한, App Server 이벤트의 진위, 실제 sandbox·네트워크 정책 또는 공유 admission 소유권의 증거는 아니다. 실행 연결 전 브리지는 이 조건과 실제 요청 전체의 동일성을 확인해야 한다.

`IssueProjectContext`는 내부 시도 준비·상태 전이·승인 기록에서 선택된 프로젝트 ID와 revision, 호출자가 제공한 확인 조건을 검사하고, 비동기 쓰기 중 선택 또는 조건이 바뀌면 성공으로 표시하지 않고 `OUTCOME_UNKNOWN`을 반환한다. 입력 정책은 비동기 조회 전에 복사한다. 이는 현재 활성 실행을 직접 확인하는 브리지 런타임이나 재시작 후 프로세스 종료 확인기가 아니며, 아직 사용자 실행·복구 API에 연결되지 않았다.

- 동일 프로젝트의 동일 idempotency key와 동일 이슈·revision·서버 계산 요청 해시는 기존 시도를 반환한다. 같은 키에 다른 입력이 오면 충돌로 거부한다. 한 프로젝트에 `prepared`, `dispatching`, `running`, `verifying`, `outcome_unknown` 중 하나만 둘 수 있다. 서로 다른 프로젝트는 별도로 추적한다.
- 외부 전송 **전** `dispatching`을 SQLite 트랜잭션에 저장해야 한다. 실제 연결된 turn의 시작을 확인한 뒤에만 `running`으로 바꾸며 thread/turn ID는 기록이다. 종료가 실제로 확인됐거나 전송 전인 경우에만 호출자가 `settle`을 요청해야 한다.
- 검증을 시작하기 전에 `running`에서 `verifying`으로 변경하며, 실제 검증 종료를 확인할 때까지 같은 프로젝트의 다음 시도를 막는다. 정상 종료 기록인 `verification_finished`는 `verifying`에서만 허용하며 검증 절차의 종료 기록일 뿐 완료 조건 충족이나 이슈 완료의 근거가 아니다. 검증 미실시를 이유로 정상 완료하거나 잠금을 해제할 수 없다. 실패·중단도 호출자가 실제 종료를 확인한 뒤에만 기록해야 한다.
- 응답·종료 결과가 불명확하면 `outcome_unknown`으로 남겨 같은 키를 재전송하지 않고 다른 키도 막는다. 내부 재시작 복구는 신뢰된 확인 콜백이 독점 소유와 이전 런타임 종료를 확인한 경우에만 전송 전 `prepared`를 중단으로, `dispatching`·`running`·`verifying`을 결과 불명으로 변경한다. 콜백은 검사 전·트랜잭션 안·변경 후 재검사하며 실패하면 롤백한다. 이 콜백 자체는 실제 종료의 증거가 아니며 현재 운영 검증기와 연결되지 않았다. 알려진 thread/turn ID는 과거 기록으로 보존하며 활성 세션이나 승인 요청으로 복원하지 않는다.
- 내부 저널의 `reconcileUnknown`은 신뢰된 호출자가 독점 소유, 실제 런타임 종료, 프로젝트 권한과 사용자 검토를 확인한 경우에만 검토 사유를 같은 트랜잭션에 기록하고 `reconciled_unknown`으로 잠금을 해제한다. 이는 결과가 성공·실패였다는 판정이나 자동 재시도가 아니다. 이 함수의 콜백 자체는 종료나 권한을 증명하지 않으며 브리지·UI·실제 런타임에 연결되지 않았다. DB를 직접 수정해 잠금을 없애는 것은 안전한 복구 절차가 아니다.
- 초안 스키마는 시도 단계와 결과의 일관성, thread/turn ID 쌍과 필수 단계를 검사한다. 입력에 정의되지 않은 필드나 제어 문자를 포함한 프로토콜 ID는 거부한다. 조회와 재시작 복구는 기록을 다시 확인하며, 손상된 기록이 있으면 복구 전체를 중단한다. 이는 동일 OS 사용자가 DB와 제약을 바꾸는 공격에 대한 보안 경계가 아니다.
- 내부 `history` 조회는 프로젝트 ID에 한정해 한 번에 최대 32개 시도를 반환한다. 시도 ID·이슈 ID·고정 revision·상태·결과·런타임 ID 기록 유무와 승인 상태별 개수만 노출하고 요청 해시, 멱등 키, thread/turn ID는 반환하지 않는다. 런타임 ID의 기록 유무는 프로세스 종료나 실행 성공의 증거가 아니다. 커서는 시도 ID 순이며 시간순이 아니고 페이지 사이에 기록이 바뀌면 전체 결과가 하나의 스냅샷이라는 보장이 없다. 조회는 상태 변경·잠금 해제·재전송을 수행하지 않는다. 화면 조회는 기존 프로젝트 보기 권한을 확인한다.
- `execution-intent.ts`는 신뢰된 서버 호출자가 제공한 프로젝트·문서·이슈 ID와 revision, 지시문 및 정책 선언을 제한된 필드로 복사하고 동결한 뒤 버전이 구분된 SHA-256 해시를 계산한다. 네트워크는 `false`, 승인 방식은 `manual`만 선언할 수 있으며 알 수 없는 필드와 허용 범위를 벗어난 입력은 거부한다. `prepareExecutionIntent`는 이 해시를 저널에 전달해 같은 키의 다른 입력을 충돌로 처리하고 지시문 원문을 저널에 저장하지 않는다. 해시는 암호화나 위·변조 방지가 아니며 비밀이 포함된 입력의 해시도 공개 정보로 취급하지 않는다.

이 선언은 아직 실제 App Server 요청이 아니다. 경로·실대상·도구·모델·런타임 설정 등 실제 dispatch에 필요한 모든 입력이 확정되지 않았으므로 이 해시를 완전한 실행 요청의 지문으로 사용하면 안 된다. 정책 선언 자체는 sandbox·네트워크·승인을 강제하지 않으며, 호출자의 프로젝트 권한이나 지시문 출처도 검증하지 않는다. 실제 연결 전 신뢰된 계층에서 저장소와 정책을 다시 확인하고, 실제 전송에 영향을 주는 모든 필드를 버전 있는 스냅샷에 포함해 같은 값이 강제되는지 검증해야 한다. 기존 저널의 저수준 `prepare` 역시 호출자를 신뢰하므로 이 새 함수만으로 임의 호출을 차단하지 않는다.

`execution-stored-intent.ts`는 서버 내부에서 지정 프로젝트·문서·revision을 저장소로 다시 읽고, 대기 상태·완료 조건·검토 상태·선행 관계의 기본 후보 검사를 통과한 단일 이슈만 저널에 준비한다. 현재 로컬 완료 근거가 없으므로 선행 이슈가 있는 대상은 준비하지 않으며 재시도·실패 상태도 기본적으로 제외한다. 저장된 이슈·완료 조건·연결 요구사항의 제한된 정보를 JSON 데이터로 구성하고, 64 KiB 입력 한도를 넘으면 잘라서 진행하지 않고 거부한다. 정책 선언은 비동기 조회 전에 복사한다. 이 함수는 브라우저나 실행 경로에 연결되지 않았고, 다른 저널 DB와 저장소 조회는 원자적 트랜잭션이 아니다.

호출자는 현재 선택·승인 및 실제 공유 admission 소유 여부를 확인하는 신뢰된 `mayPrepare` 함수를 반드시 제공한다. 준비 전과 각 비동기 조회 뒤에 결과가 정확히 `true`인지 검사하며, 누락·거부·예외는 예약 전에 중단한다. 저널을 기록하기 직전 프로젝트의 실대상과 revision도 다시 확인한다. 이는 콜백이 실제 권한이나 잠금을 올바르게 검사한다는 증거가 아니며, 검사 이후 다른 프로세스가 변경하는 경합을 없애지 못한다. 저널이 기록되기 전까지만 취소를 보장하고, 실제 전송 전에도 별도 재검증이 필요하다.

저장 문서는 비신뢰 데이터다. JSON 직렬화는 모델의 프롬프트 인젝션 방어가 아니며, 이 함수는 내용의 의미적 완전성이나 AI 제안의 검토 여부를 판정하지 않는다. 실행 연결 시 신뢰된 계층이 사용자 의도·권한·공유 admission·원본과 정책 revision·프로세스 종료 상태를 별도로 검사하고, 실제 dispatch 직전에 다시 확인해야 한다. 이 준비 결과는 실행 권한이나 도구·네트워크 격리의 증거가 아니다.

이 모듈은 호출자를 인증하지 않고 프로젝트 소유권·revision·선행 조건·요청 해시·turn 이벤트의 진위를 검증하지 않는다. 신뢰된 실행 계층이 고정된 입력으로 해시를 계산하고 실제 App Server 이벤트를 연계해야 한다. 저널의 프로젝트별 제약은 대화·아뜰리에를 포함하는 공유 admission, 실제 프로세스 종료 확인, 네트워크·도구 권한 또는 OS 수준 잠금을 대체하지 않는다. 재시작 복구는 다른 프로세스가 같은 저널을 사용하지 않으며 이전 런타임의 종료가 확인된 이후에만 호출해야 한다. 결과 불명인 동안 현재 런타임의 admission을 해제해도 안전하다고 추론하면 안 된다.

실행 연결 전 다중 프로세스 소유권, 충돌·비정상 종료·복구 UI를 설계하고 검증해야 한다. 기존의 별도 실험용 저널 DB는 자동 이전하지 않는다. 저장 데이터는 암호화하지 않으며 DB를 쓸 수 있는 동일 OS 사용자의 악의적 변경을 방어하지 않는다. 테스트는 합성 DB에서만 실행한다.
