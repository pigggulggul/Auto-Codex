# 이슈 로컬 저장소 v5

v5는 프로젝트당 하나의 저장 초안과 검토 이력을 SQLite에 보관한다. 명시적 초안 저장만 디스크에 기록하며 프로젝트 보기 권한과 현재 revision을 재확인한다. 저장 세대 번호로 다른 창의 변경을 덮어쓰지 않고, 내용 해시와 스키마를 읽기·갱신 시 검사한다. 프로젝트 revision이 바뀐 초안은 보존하지만 현재 초안으로 자동 복구하지 않는다. 등록 후에도 저장된 초안은 남으며, 오래된 저장 초안의 삭제·정리 기능은 아직 없다.

구현 중인 초안 스냅샷은 기존 필드 외에 의미 검증 및 계획 대화 이력을 포함할 수 있다. 새 코드는 이전 스냅샷을 읽도록 작성했지만, 이전 v5 코드가 새 필드를 읽는 호환성은 보장하지 않는다. 이런 스냅샷을 저장하기 전 백업과 복구 경로가 필요하며, 관련 새 모델 실행 경로는 검증 전까지 비활성화되어 있다.

기존 v4는 이전 전 SQLite 일관 백업을 보관하고 트랜잭션으로 v5를 설치한다. v1~v3은 우선 기존 절차로 v4까지 이전한 뒤 v4 백업을 추가로 남기고 v5로 이전한다. v4 앱은 v5를 열 수 없다. 되돌릴 때는 앱을 중지하고 백업을 별도 보존한 뒤 v4 백업을 복원해야 하며, 백업 이후 저장된 초안이나 다른 변경은 그 백업에 포함되지 않는다. 배포 또는 실제 사용자 저장소에 대한 이전은 이번 테스트에서 수행하지 않았다.

현재 브리지는 이슈 프로젝트의 연결 상태 조회·최초 연결, 규격 문서 가져오기와 문서별 이슈 목록·상세 보기를 화면에 제공한다. 코드 실행은 아직 연결되어 있지 않다. ID를 갖고 있다는 사실만으로 권한을 부여하지 않는다. 프로젝트와 문서 경로는 브리지가 확인한 네이티브 사용자 선택에서만 제공하며 renderer 요청 값을 전달하지 않는다.

- SQLite와 문서 파싱은 전용 worker에서 순차 수행한다. 내부 client는 동시 대기 요청을 최대 8개로 제한하고 대기 중인 문서 바이트를 복사한다. 시작과 개별 요청에는 기본 30초 제한이 있다. worker가 응답 전에 종료되거나 시간 제한에 도달하면 이미 전달된 변경 요청은 `OUTCOME_UNKNOWN`으로 보고 자동 재전송하지 않는다. 읽기 요청은 사용 불가로 보고한다.
- 프로젝트 연결 컨텍스트는 호출자의 요청에서 경로를 받지 않고 브리지가 보유한 현재 선택의 경로·모드·generation을 사용한다. 연결 상태 조회는 새 연결을 만들지 않으며, 연결 생성은 별도 `bind` 호출에서만 수행한다. 비동기 처리 중 프로젝트가 바뀌면 결과를 현재 선택에 적용하지 않는다. 생성이 이미 완료됐거나 결과가 불명일 수 있으므로 이전 프로젝트의 연결 상태를 확인해야 한다.
- 브리지는 프로젝트 선택·대화 복원·조사 모드 전환 등 선택의 변경마다 서버 소유 generation을 증가시킨다. 같은 경로로 돌아와도 이전 generation을 재사용하지 않는다. 이 컨텍스트만으로는 사용자 인증이나 명시적 행위가 증명되지 않는다.
- 연결 생성은 Windows의 별도 폴더 선택창에서 사용자가 현재 프로젝트 폴더를 다시 선택한 뒤 수행한다. 브리지는 실제 경로·현재 선택·generation과 활성 작업을 재확인한다. 잘못된 폴더, 취소, 연결 종료, 다른 창의 선택 변경은 연결하지 않는다. 소켓 종료 시 이 요청이 연 선택창도 중단한다.
- 문서와 이슈 내용 보기는 별도 사용자 요청과 현재 프로젝트의 네이티브 폴더 확인을 필요로 한다. 브리지는 그 소켓과 선택 generation에만 최대 15분 동안 읽기 권한을 부여하고, 다른 소켓·프로젝트 전환·연결 종료·만료 후에는 내용을 반환하지 않는다. 화면도 만료 시 표시 데이터를 지운다. Origin과 문서 ID 자체는 인가 근거가 아니다.
- 문서 내보내기는 유효한 보기 권한 외에 네이티브 저장창의 명시적인 파일 선택이 필요하다. renderer가 경로·내용을 지정하지 못하며 브리지는 프로젝트 경로·선택 generation·저장소 revision·활성 작업을 재확인한다. 로컬 Windows 프로젝트 안의 새 `.md`만 허용하고 기존 파일은 덮어쓰지 않는다. 검증된 바이트를 같은 디렉터리의 임시 파일에 쓴 뒤 원자적인 새 이름 생성으로 게시한다. 같은 이름이 경합으로 먼저 생기면 실패하며 기존 파일을 보존한다. 대상 파일 시스템이 hard link를 지원하지 않으면 저장을 거부한다. 저장 도중 연결이 끊기거나 선택이 변경되어 결과를 확인할 수 없으면 자동 재시도하지 말고 선택한 위치를 확인해야 한다. 임시 파일 정리에 실패하면 폴더 확인이 필요하다.
- 원자적 게시 단계에서 파일시스템의 지원 부족 또는 권한 거부가 확인되면 저장 위치와 권한을 확인하라는 오류를 반환한다. 이 경우 부분 파일을 게시하거나 비원자적 쓰기로 대체하지 않는다. 표시 메시지는 OS 오류 원문이나 절대 경로를 포함하지 않는다.
- 저장창에서 새 대상이 선택되면 브리지 내의 대화·아뜰리에 실행 상태와 대기 요청을 확인하고 파일 게시와 임시 파일 정리가 끝날 때까지 예약한다. 이 구간에는 새 대화 작업·아뜰리에 실행·프로젝트 전환이 시작되지 않으며 승인·중단 요청은 계속 처리한다. 저장창을 연 상태에서 다른 작업이 시작되면 예약을 얻지 못해 저장하지 않는다. 연결이 끊겨도 실제 파일 작업이 끝나기 전에는 예약을 해제하지 않는다. 파일 작업이 멈춰 끝나지 않으면 결과를 확인하고 브리지를 재시작해야 한다. 이 예약은 단일 브리지 프로세스의 협력하는 경로만 포함하며 다른 프로세스나 다른 브리지를 잠그지 않는다. 추후 이슈 실행 경로도 같은 admission에 연결해야 한다.
- 링크·폴더 식별자는 저장 전 반복 확인하지만 Windows에서 Node의 경로 기반 API만으로 동일 OS 사용자 프로세스의 모든 검사/사용 경합을 원자적으로 막을 수는 없다. OS 권한 및 신뢰할 수 있는 로컬 사용자 환경이 필요하다. 외부 프로세스의 저장소 변경은 최종 revision 확인 이후에도 발생할 수 있으며 외부 파일과 SQLite를 하나의 트랜잭션으로 묶지 않는다.
- 규격 문서 가져오기는 별도 Windows 파일 선택창에서 선택한 `.md` 파일에 한정한다. 파일은 최대 4 MiB로 읽고 원본과 파싱 결과를 앱 로컬 DB에 보관한다. 원본 파일에는 쓰지 않는다. UNC·네트워크 드라이브와 경로의 심볼릭 링크·junction, `.env`로 시작하는 파일을 거부한다. 파일 ID·크기·수정 시각과 경로를 읽기 전후 확인한다. Windows 파일시스템의 동일 사용자 프로세스가 검사 사이에 경로를 교체하는 모든 경합을 Node API만으로 원자적으로 막을 수는 없으며, 엄격한 네트워크 격리가 필요하면 OS egress 정책이 추가로 필요하다.
- 가져오기 시작 시 서버가 확인한 프로젝트 ID와 revision을 고정하고, 파일 선택 후와 읽은 후 다시 확인한다. 워커도 실제 가져오기 전에 같은 ID와 revision을 다시 확인하고 저장 요청에 고정한다. 저장이 시작된 뒤 프로젝트 선택이 바뀌면 결과를 현재 프로젝트의 성공 또는 미실행으로 단정하지 않고 `OUTCOME_UNKNOWN`으로 안내한다. 점검은 시점별 확인이며 파일시스템과 저장소 전체를 잠그지 않는다.
- 이슈 요청은 기존 loopback Host/Origin 검사 외에 Origin이 있는 허용된 로컬 UI 연결만 받는다. Origin은 인증 수단이 아니다. 상태 응답은 현재 프로젝트의 연결 여부만 반환하고, 연결 생성의 사용자 행위는 별도 네이티브 선택창에서 확인한다. 동일 OS 사용자 권한을 가진 악성 프로세스는 Origin을 위조하거나 UI를 조작할 수 있으므로 이를 독립적인 보안 경계로 보장하지 않는다. 이 경로는 코드 실행·자동 승인·권한 변경을 제공하지 않는다. 이후 그런 행위는 별도의 사용자 행위·권한 검증을 설계하고 테스트해야 한다.
- worker 종료는 새 요청을 막고 이미 worker에 전달된 대기열을 마친 후 저장소를 닫는다. 시작 대기 중 아직 전달되지 않은 요청은 거부한다. 비정상 종료 후 SQLite 복구와 현재 revision을 확인해야 한다. worker 자체가 App Server 실행·승인·중단을 처리하거나 권한을 부여하지는 않는다.
- `npm run build:server` 후 `node tools/verify-issues-worker.mjs`는 격리된 합성 프로젝트에서 컴파일된 worker의 등록, 대기열 제한, 종료·재시작 및 종료 중 결과 불명 경로를 검사한다. 실제 브리지나 사용자의 프로젝트를 조작하지 않는다.

- 앱 루트의 `.local-data/issues/issues.sqlite`에 저장하며 사용자 프로젝트 안에는 저장소를 만들지 않는다. 고정된 디렉터리와 SQLite 파일·sidecar의 실제 경로를 검사하고 링크·hardlink를 거부한다. 비밀 저장소가 아니므로 선택 자료와 대화의 보관 권한 및 Windows ACL은 운영 환경에서 별도로 검토해야 한다.
- 저장소 v4는 프로젝트 연결, 교환 문서와 원본 사본, 이슈 상태, 실행·승인 저널 테이블을 보관한다. SQLite의 트랜잭션·foreign key와 `synchronous=FULL`을 사용한다. 상위 스키마 버전이나 내용이 있는 알 수 없는 v0 DB는 변경하지 않는다. v1·v2·v3은 변경 전 해당 버전의 SQLite 일관 백업을 `.local-data/issues/issues-vN-backup-*.sqlite`로 보존한 뒤 트랜잭션으로 v4를 적용한다. v1에서 이미 등록한 문서는 원본 바이트가 없으며 이를 생성했다고 표시하지 않는다. 실행·승인 저널은 아직 실제 이슈 실행과 연결되지 않았다.
- 프로젝트 최초 연결은 명시적인 선택 이후 호출하도록 한 내부 API다. 실제 경로와 장치·파일 식별자·생성 시각을 기록하며, 확인할 수 없는 환경은 거부한다. 경로가 사라지거나 대상이 달라지면 읽기·가져오기를 중지한다. 동일 경로가 다시 생겨도 기존 연결을 자동 재사용하지 않으며 이동/복사 후 사용자가 선택하는 재연결 기능은 아직 없다. 이 식별 정보는 재사용이나 경합 가능성을 없애는 운영체제 보안 경계가 아니므로 나중에 프로젝트 쓰기를 수행할 때 별도 검증과 OS 권한이 필요하다.
- 한 문서 전체를 검증한 뒤 단일 트랜잭션에서 저장한다. 같은 문서 ID와 정규화된 내용은 재가져와도 중복되지 않는다. 재가져오기 성공을 반환하기 전에 기존 문서·원본 사본의 해시, 문서 revision, ID 색인과 이슈 상태 연결을 확인하며 불일치는 오류로 반환한다. 이는 DB와 해시를 함께 바꿀 수 있는 동일 권한 프로세스에 대한 변조 방지는 아니다. 같은 문서의 변경이나 다른 문서의 동일 ID는 충돌로 중단하며 기존 데이터를 유지한다. 다중 창의 다른 변경은 기대 revision으로 감지한다.
- 문서 목록은 프로젝트 revision을 고정한 커서 방식이며 한 번에 최대 100개를 반환한다. 목록 조회 중 revision이 바뀌면 처음부터 다시 조회해야 한다. 정규화된 문서 JSON과 원본 사본 합계에 256 MiB 저장량 한도를 적용한다. 이 한도는 SQLite 인덱스·저널과 마이그레이션 백업 등을 포함한 전체 디스크 사용량 제한이 아니다. 한도에 도달하면 오류를 반환하고 이전 기록을 자동 삭제하지 않는다.
- 화면의 이슈 조회 응답은 요청한 종류·revision·상세 ID와 페이지 커서가 일치하는지 확인한다. 잘못된 페이지 진행이나 점검 결과 총수의 불일치는 표시하지 않고 오류로 처리한다. 이 클라이언트 검사는 서버의 보기 권한 검사나 저장소 무결성 검사를 대신하지 않는다.
- 문서에 기록된 상태와 로컬 상태는 분리한다. `completed`로 가져온 이슈와 완료 조건이 없는 이슈는 `needs_review`로 등록한다. 현 저장소 API에는 실행, 상태 변경, 로컬 완료 판정이 없다. 이를 추가할 때는 근거와 상태 전이의 별도 계약 및 마이그레이션이 필요하다.
- 목록과 상세는 완료 조건이 없거나 선행 이슈의 로컬 완료가 확인되지 않은 경우 기존 이슈 상태와 별도로 사유를 표시한다. 현재는 로컬 완료 상태가 없으므로 모든 선행 관계가 미확인이다. 이 표시는 실행 여부를 최종 판정하는 기능이 아니며, 실행 기능을 도입할 때 서버에서 최신 revision과 실제 선행 완료 근거를 다시 검증해야 한다.
- 선택한 문서에 한해 이슈와 요구사항의 연결·분류 누락, 이슈 설명·완료 조건 누락과 가져온 완료 표시를 읽기 전용으로 점검한다. 요구사항의 저장된 출처 유형·이름·위치와 연결된 요구사항 수/전체 수, 문서 및 프로젝트 revision을 표시한다. 결과는 동일 revision에 고정해 페이지로 반환하며 보관하지 않는다. 이는 원문을 다시 분석하거나 의미적 누락·실제 구현을 검증하지 않으며, 조치·보류 기록 및 AI 검토는 아직 없다.
- 교환 문서에 등록됐지만 어떤 요구사항에서도 참조하지 않은 자료를 읽기 전용 점검 항목으로 표시한다. 원본 파일을 읽거나 자료의 의미적 누락을 판정하지 않는다. 새 점검 코드를 처리하도록 브리지와 UI를 함께 갱신해야 하며 DB 이전은 없다.
- 연결된 요구사항과 이슈가 각각 분류돼 있으나 상위·하위 관계가 아닌 서로 다른 분류 가지에 있으면 두 항목을 확인할 수 있도록 표시한다. 여러 분류에 걸친 연결은 의도적일 수 있으므로 오류 판정이나 자동 변경은 하지 않는다. 두 항목 모두 같은 선택 문서와 revision에서 조회하며, 브리지와 화면을 함께 갱신해야 한다.
- 자료별로 문서에 기록된 요구사항 연결을 페이지로 표시하고 요구사항 상세의 연결 이슈로 이동할 수 있다. 연결이 없는 자료도 표시하며 요구사항의 출처 유형을 그대로 보여준다. 원본을 열거나 기록된 연결의 정확성·완전성을 판정하지 않는다. 조회는 기존 소켓별 보기 권한과 프로젝트 revision에 묶이고, 최대 32개 및 응답 크기 제한을 적용한다. 새 `sourceTrace` 조회를 위해 브리지와 화면을 함께 갱신하며 DB 이전은 없다.
- 말단 분류에 직접 지정된 요구사항과 이슈가 각각 있는지 점검한다. 하위 분류가 있는 상위 분류는 결과에 포함하지 않으며, 다른 분류의 요구사항과 연결된 이슈도 직접 지정된 요구사항으로 계산하지 않는다. 점검 결과에서 해당 분류의 이슈 목록으로 이동할 수 있고 기존 검색·상태·버전 필터는 유지된다. 결과는 누락 가능성을 살피는 기준이지 실제 요구사항의 의미적 누락이나 구현 여부의 증거가 아니다. 신규 finding 코드가 추가되므로 브리지와 화면은 함께 갱신해야 하며 저장 형식이나 데이터 마이그레이션은 변경하지 않는다.
- 교환 문서에 기록된 원본 자료 중 어떤 요구사항의 `sourceId`에서도 참조하지 않는 자료를 표시한다. 모든 출처 유형의 명시적인 `sourceId`를 참조로 계산하며, 원본 파일이나 현재 분석 입력 목록은 읽지 않는다. 참조 유무는 실제 원문 분석·내용 충실성의 증거가 아니다. 결과는 기존 보기 권한과 revision에 한정된 읽기 전용 페이지이며, 새 finding 코드에 맞춰 브리지와 화면을 함께 갱신한다. 저장 형식이나 데이터 마이그레이션은 변경하지 않는다.
- 같은 문서 안에서 요구사항 문구 또는 이슈 제목이 유니코드 NFC·대소문자·공백 정규화 후 같으면 비교 대상 ID와 함께 중복 가능성을 표시한다. 요구사항은 ID 순, 이슈는 버전·순서·ID 순의 첫 항목과 비교한다. 자동 병합·상태 변경이나 다른 문서와의 비교는 하지 않으며, 같은 문구가 의미적으로 중복이라는 판정도 아니다. 기존 조회 권한과 revision·페이지 크기 제한을 사용한다. 새 점검 코드와 `relatedEntityId`를 모르던 이전 UI는 해당 응답을 거부할 수 있으므로 브리지와 화면을 함께 갱신한다. 저장 형식이나 DB 이전은 없다.
- 같은 문서에서 개발 버전과 순서가 같은 이슈도 첫 이슈 ID와 함께 표시한다. 버전의 선행 0은 비교 전 정규화하며 이슈는 버전·순서·ID 순으로 정렬한다. 이는 순서 확인을 위한 읽기 전용 표시로 등록·실행을 차단하거나 순서를 바꾸지 않는다. 새 점검 코드를 처리하도록 브리지와 UI를 함께 갱신해야 하며 저장 형식 변경은 없다.
- 가져온 문서에서 출처가 `ai-proposal`로 표시된 요구사항은 연결 여부와 관계없이 내용과 근거를 확인할 항목으로 표시한다. 이는 문서에 기록된 출처를 보여주는 것이며, 실제 원문의 확인이나 제안의 오류 판정은 아니다. 요구사항 상세에서 연결된 이슈를 확인할 수 있다. 새 점검 코드를 처리하도록 브리지와 UI를 함께 갱신해야 하며 저장 형식 변경은 없다.
- 문서 점검에서 요구사항과 비교 대상의 내용·분류·저장된 출처 정보·연결된 이슈를 볼 수 있고, 연결된 이슈와 이슈 점검 항목에서는 설명·완료 조건·선행 관계를 열 수 있다. 실제 원본 파일은 다시 읽지 않는다. 요구사항의 연결 이슈는 응답 크기와 최대 32개 항목에 맞춰 페이지로 나누며, 비교·조회는 선택한 문서와 현재 revision 및 기존 보기 권한에 한정한다. 각 상세에서 이전 점검 또는 요구사항으로 돌아갈 수 있다. 새 읽기 전용 `requirementDetail` 조회는 브리지와 화면을 함께 갱신해야 하며 DB 이전이나 문서 상태 변경은 없다.
- 이슈 상세에서 같은 문서의 선행 이슈 상세를 열고 이전 상세로 되돌아갈 수 있다. 돌아갈 때 이전 이슈를 같은 revision에서 다시 읽으므로 완료 조건·연결 요구사항·선행 관계는 첫 페이지부터 표시된다. 보기 권한이 만료되거나 revision이 바뀌면 기존 보기 오류 처리를 따른다.
- 문서별 이슈 목록과 완료 조건·요구사항은 페이지 단위로 반환한다. 선택한 문서 전체에서 이슈 ID·제목·설명·분류 텍스트를 검색하고 로컬 상태 및 정확한 개발 버전으로 필터링한 후 페이지를 나눈다. 버전의 앞자리 0은 비교 시 정규화한다. 보기 결과는 프로젝트 revision에 고정되며 다른 변경이 감지되면 다시 불러와야 한다. SQLite 전체 디스크 사용량 제한, 기존 문서 덮어쓰기·수정·동기화, 백업·복원 UI는 아직 구현되지 않았다. 저장소와 외부 Markdown 파일은 하나의 원자 트랜잭션이 아니다.
- 프로젝트 전체 이슈 검색은 문서 ID 순으로 최대 8개 문서를 확인하고, 일치하는 첫 문서의 최대 32개 항목을 반환한다. 미처리 문서나 같은 문서의 다음 이슈가 있으면 재개 위치를 반환하며, 현재 범위가 비어 있어도 이어서 검색할 수 있다. 검색어·로컬 상태·정확한 버전을 함께 적용한다. 문서별 검색과 전체 검색은 문자열을 NFC 정규화하고 로캘에 의존하지 않는 소문자로 비교한다. 문서별 분류 ID는 문서에 속하므로 전체 검색에는 적용하지 않는다. 모든 페이지는 동일 프로젝트 revision과 소켓별 보기 권한을 확인하며 다른 문서의 이슈 상세도 해당 문서에 한정해 조회한다.
- 문서 안의 분류를 단계별로 탐색하고, 각 단계에서 같은 상위 분류에 속한 항목을 페이지로 반환한다. 분류 선택 시 해당 분류와 모든 하위 분류의 이슈를 포함하며 미분류만 별도로 선택할 수 있다. 검색·상태·버전 필터와 함께 적용되며, 다른 문서를 선택하면 이전 문서의 분류 선택은 해제된다. 분류 목록과 이슈 목록은 같은 프로젝트 revision과 보기 권한을 사용한다.

복구는 브리지를 종료하고 현재 데이터베이스와 관련 파일을 별도로 보존한 뒤 수행해야 한다. v1 백업으로 되돌리면 v2 이후 등록한 내용은 포함되지 않으므로 별도 보관·검토가 필요하다. 이 저장소는 사용자 프로젝트 파일 변경을 복구하지 않으며, 프로젝트 이동 시 기록을 자동 병합하지 않는다.
