# 작업실 생성 품질: 전체 설계·질문·제작 기준

2026-10-30. 이번 범위는 작업실의 공통 생성 경로다. DI/DO 시제품은 수정하거나 재생성하지 않았다.

## 바뀐 흐름

아이디어 입력 → 전체 디자인 설계 → 중요한 질문에 답변 → 답변을 반영한 설계 → 사람이 전체 검토·확정 → 제작 기준 고정 → 기존 Codex 제작 실행 → 실제 결과 검토.

- 새 설계의 기본 목적은 `blueprint`다. 사용자가 기능·화면을 미리 등록할 필요 없이 제품 답변 12개, 기능, 화면, 실제 흐름 연결, 컨셉, 시각 규칙, 자료 계획, 가정과 검토 기준을 하나의 후보로 만든다.
- 모니터·편집기·판매·콘텐츠·소개·게임·업무 흐름의 사용 목적을 구분한다. 첫 화면의 핵심 작업, 구체적인 배치·정보 밀도·타이포·간격·형태·색의 역할·움직임·모바일 규칙을 명시한다. 모든 서비스에 큰 소개용 히어로를 쓰도록 유도하지 않는다.
- 사용자 원문의 짧은 인용과 구현 계획·적용 화면을 연결한다. 원문에 없는 인용과 존재하지 않는 화면 연결은 거부한다. 이 구조적 검증이 의미상 모든 요구의 완전한 수용을 보증하지는 않는다. 사용자가 대응표를 검토할 수 있다.
- 설계가 달라질 중요한 질문을 최대 4개로 제한한다. 답변은 후보에 별도 저장하고, 다시 AI 설계를 요청할 때 서버가 저장된 질문·답변을 읽어 전달한다. 답변 저장 자체를 설계에 반영했다고 표시하지 않는다.
- 중요한 질문이 남았거나 답변을 저장한 뒤 아직 다시 설계하지 않았으면 반영·확정을 거부한다. 기존 확정 답변과 선택 항목의 제외를 자동으로 덮어쓰지 않는다.
- 전체 설계·가정·참고 자료 제한을 검토하는 체크와 명시적인 확정 버튼이 있어야 제작 기준으로 확정할 수 있다. 실제 제작은 다음 단계의 별도 버튼이다.
- 전체 초안은 설계 엔티티가 비어 있는 프로젝트에 제공한다. 기존 엔티티가 있는 프로젝트는 항목별 제안 경로를 유지한다. 자동 병합·중복 항목 생성으로 기존 설계를 훼손하지 않는다.

## 시각 품질을 제작·검토에 연결

계획은 단일 예쁜 문장으로 끝내지 않는다. 시각 시스템, 대표 뷰포트의 우선 정보, 긴 데이터·많은 항목·빈 상태·로딩·실패·완료·선택·포커스 등을 구체화한다. 생성한 본문/표면 대비 및 강조 버튼 글자 대비는 4.5 이상으로 검사한다. 이 검사는 실제 화면의 크기·가독성·미관·접근성 인증을 대신하지 않는다.

제작 요청에는 용도에 맞는 화면 구성, 기존 기술 스택과 디자인 시스템 활용, 실제 데이터 크기, 대표 데스크톱/390px 모바일 렌더 확인과 증거 기록을 포함한다. 단일 HTML이나 간단한 기능 시제품을 기본 품질 수준으로 강제하지 않는다. 브라우저를 사용할 수 없으면 미검증이라고 보고하도록 지시한다.

전체 설계의 전용 체크는 고정 스냅샷의 독립적인 검토 기준으로 복사된다. 새 결과 검토에서는 모두 `unverifiable`로 시작한다. 명령 종료·기능 검사 통과·AI의 자체 점수를 시각 검토 통과로 승격하지 않는다. 예전 설계의 기존 8개 검토 기준은 유지한다.

## 참고 자료에 대한 한계

URL만으로 원본을 실제 읽었거나 같은 서체·아이콘을 확보했다고 표시하지 않는다. 제안은 읽기 전용·네트워크 차단을 유지한다. 전체 초안은 참고할 점·제외할 점·미확인 범위·서체 대체안을 분리해 보여 준다. 정확한 참고 적용에 결정이 필요하면 질문하도록 한다. 자동 웹사이트 캡처·브라우저 렌더 비교·서체 다운로드 기능은 이번 변경에 포함하지 않았다. 기존 이미지·자료 등록 및 관찰 메모를 활용할 수 있다.

새 경로가 모든 결과물의 미적 완성도를 보장한다고 주장하지 않는다. 이 변경은 요구의 구조화, 디자인 결정의 깊이, 질문과 승인, 제작 지시, 결과 검토 기준을 개선한다. 실제 결과물 디자인의 수용 여부는 후속 실행·렌더 검토에서 판단한다.

## R2 위협 분석

- 보호 자산: 원본 설계와 확정 결정, 로컬 프로젝트 파일, 실행 권한, 고정 스냅샷. 브라우저와 모델 출력은 비신뢰 입력이다.
- 경계: `atelier.ai.propose` → 기존 App Server 읽기 전용 제안 → 서버 스키마·색 대비·원문 인용·그래프 검증 → 분리된 후보 저장 → `proposal.answer`/`proposal.apply` → SQLite 트랜잭션.
- 방어: 서버가 저장 ID를 생성하고 설계 내부 별칭만 실제 ID로 변환한다. 모델이 project·cwd·sandbox·approval·status·파일 ID를 삽입할 수 없다. 대상 프로젝트 소유권·버전·revision·후보 상태를 검사한다. 다른 프로젝트의 후보·기존 확정 값 변경·끊어진 흐름·권한 필드·낮은 대비·허구 인용은 거부한다.
- 질문 답변은 서버의 현재 후보에 존재하는 키만 받는다. 재설계는 서버 저장본의 질문·답변을 사용하며 다른 프로젝트·오래된 버전의 참조를 거부한다. 재전송으로 같은 후보를 두 번 반영할 수 없다.
- 네트워크·도구 권한 확대 요청은 기존 정책처럼 거부한다. 명시적 전체 검토는 설계 확정에만 적용하고, App Server의 실제 실행 승인과 혼용하지 않는다.
- 배포·복구: DB 마이그레이션과 외부 배포는 없다. 브리지와 UI를 함께 빌드·재시작해야 한다. 새 `blueprint` 제안 기록은 구버전 클라이언트에서 이해하지 못할 수 있으므로 복귀 시 DB를 먼저 보관하고 버전을 맞춘다. 구형 JSON 백업에 AI 제안이 포함되지 않는 기존 제한은 유지한다.

## 검증

- 단위/통합: 전체 후보가 확정 전 설계를 바꾸지 않는지, 명시적 검토 이후 제작 가능한 상태가 되는지, 중요한 질문 차단·답변 전달·외부 ID/권한·원문/그래프·대비·기존 확정·stale/replay 거부를 검사한다.
- `node tools/verify-atelier-blueprint.mjs --playwright=<패키지 경로>`: 격리된 실제 브리지·SQLite와 합성 App Server로 전체 생성, 질문 → 답변 → 재설계, 검토·확정, 제작 기준 고정, 전용 검토 기준, 390px 넘침과 페이지 오류를 확인한다.
- 같은 명령에 `--live`를 추가하면 실제 로그인 모델에 별도의 사진 편집 서비스 입력으로 읽기 전용 전체 설계만 요청한다. 실제 웹 결과물이나 DI/DO 결과를 제작하지 않는다.
- 실제 `gpt-6.1-sol` 실행에서 `editor` 용도, 답변 12개·기능 4개·화면 4개·흐름 1개·시각 규칙 6개·자료 계획 4개·전용 검토 기준 11개를 생성했다. 추가 질문 없이 검토 후 제작 기준 고정까지 통과했고 390px 넘침·페이지 오류는 없었다. 원문 10개 구절과 화면 연결도 생성됐다. 기능 편집 양식을 수동으로 채우지 않았다.
- 합성 모니터 사례에서는 질문에 “모바일”로 답한 뒤 그 답변이 새 설계에 표시되고 같은 확정·고정 흐름으로 이어졌다.
- 최종 `npm run typecheck`, `npm test`(31개 파일·198개 테스트), `npm run build`가 통과했다. 여러 차례 재설계할 때 이전 질문 답변도 유지되는 회귀 검사를 포함한다. 브라우저에서는 요약의 “이 설계를 제작 기준으로 고정하고 다음으로”를 통해 제작 준비까지 확인했다.
- 증거는 `.cache/blueprint-quality-live/`, `.cache/blueprint-quality-fixture/`의 evidence/proposal JSON, 고정 설계 Markdown과 스크린샷에 있다. 합성 결과와 실제 모델 결과를 분리한다.

초기 UI 검사에서 새 후보의 명시적 조회가 이전 후보에 대한 이벤트 조회에 밀리는 경합을 발견했다. 명시적 조회 시작 시 선택 ID를 먼저 갱신하여 뒤따르는 이벤트도 같은 후보를 조회하도록 수정했다. 저장 완료 전 버튼 상태를 읽던 검사는 실제 저장·전환 완료를 기다리도록 수정했고, 서버 확정 조건은 완화하지 않았다.
