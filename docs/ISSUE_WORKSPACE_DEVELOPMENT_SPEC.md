# 이슈 처리 작업실 개발 명세서

문서 상태: **구현 전 설계 명세** · 작성일: 2026-11-03 · 대상: Auto Codex 개발자 및 코딩 에이전트

이 문서의 기능과 메시지 이름, 파일 경로는 별도 표시가 없는 한 **구현 목표**다. 현재 동작하거나 검증된 기능이라는 뜻이 아니다. 구현 시 저장소의 `AGENTS.md`와 실제 코드·App Server 프로토콜이 우선이며, 차이가 있으면 보안 경계를 유지하는 방향으로 설계를 조정하고 변경 근거를 기록한다.

## 1. 목표와 완료된 사용자 경험

사용자는 로컬 프로젝트를 열고 **이슈 처리** 탭에서 프로젝트 파일, 선택한 문서와 자신의 추가 프롬프트를 기반으로 개발 요구사항을 분석한다. Codex와 대화하면서 대분류·소분류·요구사항·개발 이슈를 다듬고, 원본부터 이슈까지 누락과 충돌을 검증한다. 결과를 규격 문서로 내보내거나 가져와 이슈를 등록한다. 등록한 이슈 중 선택한 항목 또는 미완료 항목을 개발 버전과 선행 관계에 따라 **하나씩** 처리한다. 이후 완료 상태 갱신으로 실제 코드와 검증 증거를 확인한다. 사용자가 원하는 경우 명시한 범위의 승인 요청에만 자동 승인 정책을 적용한다.

핵심 원칙:

1. 기능·분류·이슈의 개수와 개발 버전의 최댓값을 제품 규칙으로 정하지 않는다. 처리 단위와 저장소·메시지 자원 제한은 별도이며, 제한에 도달하면 누락된 작업을 표시하고 이어서 처리한다.
2. 요구사항 출처 → 요구사항 → 분류 → 이슈 → 실행·구현 증거를 추적한다. 모델이 모두 파악했다고 주장한 것만으로 완전성을 보장하지 않는다.
3. 이슈 **생성 검증**과 현재 코드의 **구현 검증**은 별도 작업과 결과다.
4. 대화·분석·등록·실행·추가 승인·완료 판정은 서로 다른 사용자 행위와 권한이다.
5. 실패·중단·판단 불가·부분 처리·구버전 결과를 성공이나 완료로 표시하지 않는다.

### 1.1 범위

- 최상위 작업 모드 세 개: `Codex 대화`, `아뜰리에 디자인`, `이슈 처리`.
- 프로젝트별 자료 선택, 추가 프롬프트, 분석 범위 표시, 이슈 초안 생성 및 대화형 수정.
- 요구사항 추출·분류·이슈 매핑, 후보/검증 결과 검토 및 수정, 원본 출처 추적.
- 기계 검증 가능한 버전 있는 Markdown 이슈 문서의 생성·가져오기·갱신.
- 이슈 보드, 버전·선행 관계 관리, 수동·선택·최대 N개·조건부 자동 순차 실행.
- 실제 실행 이벤트, 이슈별 시도·변경·검증·승인 기록 및 상태 갱신.
- 사용자 설정에 근거한 좁은 범위의 자동 승인. 안전하게 표현·검증할 수 없는 유형은 수동 승인.
- 로컬 저장, 중단·재시작 복구, 경로·비신뢰 입력·동시성 보호, 테스트·운영 문서.

### 1.2 이번 범위 밖

- GitHub/외부 이슈 트래커 양방향 연동, 자동 댓글·push·PR·배포.
- 동일 프로젝트의 여러 이슈를 동시에 쓰기, 자동 worktree 생성·정리·병합.
- PDF/Word/이미지의 자동 분석은 초기 필수가 아니다. 초기 문서 입력은 UTF-8 Markdown/일반 텍스트이며 다른 형식은 지원하지 않는다고 표시한다.
- 완전 오프라인 모델 추론, 임의 셸 실행 API, 검증 없는 자동 완료 보장.
- 원본 기획 문서의 자동 수정. 별도로 내보낸 규격 이슈 문서만 명시적 저장/동기화 대상이다.

## 2. 현재 구조와 통합 기준

현재 저장소에서 확인한 사실:

- React/Vite renderer와 `127.0.0.1:4781` Node bridge, stdio JSONL 기반 Codex App Server를 사용한다. 브라우저는 신뢰되지 않는 표현 계층이다.
- `src/App.tsx` 및 `src/components/layout/AtelierNavigation.tsx`는 현재 Atelier 공통 셸, 여러 페이지 및 기존 화면 전환을 담당한다. 3개 탭은 기존 구조를 재편해야 하는 요구사항이며 현재 그대로 존재한다고 가정하지 않는다.
- `server/index.ts`가 프로젝트 선택·경로 검증·Codex 실행·단일 활성 실행 상태와 대기 승인 요청을 관리한다. `server/orchestration.ts`는 현재 팀 실행 내 최대 8개 작업 및 읽기 최대 3개 병렬, 쓰기 단독 실행 규칙을 가진다. 이는 이슈 총 개수 한도가 아니다.
- `server/approval-response.ts`는 현재 permission 요청을 승인할 때 요청된 권한 객체를 반환한다. 부분 권한을 안전하게 산출하는 자동 승인 구현이 이미 있다고 가정하지 않는다.
- 일반 대화는 `.local-data/history.json`, Atelier는 별도 SQLite와 파일을 쓴다. `server/atelier/proposals.ts`의 버전 검사·제안 선택 적용과 proposal runtime의 read-only 분석을 설계 참고 사례로 사용할 수 있다.
- 현재 App Server 자원과 활성 상태는 여러 기능이 공유한다. 이슈 전용 스케줄러를 기존 활성 실행과 병렬로 추가하기만 하면 안전하지 않다. **공유 실행 허가(admission)·작업공간 쓰기 잠금·전역 중단/승인 경로**를 통합한다.

실제 계약과 제약은 [ARCHITECTURE.md](ARCHITECTURE.md), [OPERATIONS.md](OPERATIONS.md), `shared/protocol.ts`, `server/index.ts`, `server/orchestration.ts`, `server/atelier/`에서 구현 직전 재확인한다. Node 요구 버전과 검사 명령은 루트 `package.json`을 따른다.

## 3. 사용자 시나리오

### 3.1 프로젝트 분석에서 등록까지

1. 사용자는 프로젝트 폴더를 선택하고 `이슈 처리` 탭을 연다. 폴더가 없거나 연구 모드면 안내와 폴더 선택을 표시한다.
2. `이슈 후보 만들기`에서 프로젝트 자료·명시적으로 추가한 문서·추가 프롬프트·제외 경로를 확인한다. 자동으로 모든 파일을 분석하거나 변경하지 않는다.
3. 브리지가 프로젝트 실제 경로와 입력을 검증하고 변경되지 않는 분석 입력 스냅샷을 만든다. 읽기 전용·네트워크 기본 차단으로 분석한다.
4. 문서 단위/구간 단위로 요구사항을 추출하고 대분류·소분류별로 후보 이슈를 생성한다. 발견된 사실, 모델 추정, 사용자 요청을 구분한다.
5. 검증에서 누락·미분류·매핑 없는 요구사항·중복·명세 부족·버전/선행 관계 충돌을 표시한다.
6. 사용자는 대화와 직접 편집으로 초안을 변경하고, 변경 전후를 확인해 적용한다. 변경 부분에 연결된 검증 결과는 최신이 아님을 표시한다.
7. 사용자가 후보를 확인하여 프로젝트 이슈로 등록한다. 생성된 **규격 문서**는 프로젝트의 사용자가 지정한 경로에 별도 내보낼 수 있다. 일반 문서의 자동 분석은 후보 생성이고 자동으로 코드 실행을 시작하지 않는다.

### 3.2 규격 문서 가져오기

1. 사용자가 파일 선택기에서 규격 Markdown을 고른다. 프로젝트 외부 파일도 가져오기 입력으로 선택할 수 있지만, 브리지는 파일 내용을 제한적으로 읽어 로컬 저장소에 복사하고 원본 파일에 쓰지 않는다. 외부 경로가 프로젝트 cwd나 쓰기 루트가 되지 않는다.
2. 파서·버전·스키마·참조·크기·중복 ID·순환 의존성을 검증한다.
3. 신규 문서면 검증된 데이터를 해당 프로젝트 이슈로 자동 등록한다. 동일 문서/같은 ID의 기존 데이터가 있으면 7.4절의 충돌 규칙을 따른다. 불완전하거나 위험한 입력은 부분 성공으로 숨기지 않는다.
4. 일반 Markdown/TXT는 AI 분석 후보로 취급한다. 규격 문서가 아니라는 이유와 다음 단계를 표시한다.

### 3.3 이슈 처리 및 재검증

1. 사용자가 이슈를 체크하여 선택 실행하거나, 대상 상태와 상한 N을 지정하여 미완료 순차 실행을 시작한다. 자동 실행을 켜더라도 최초 시작·범위·한도는 사용자가 명시한다.
2. 브리지는 선행 이슈·버전 순서·프로젝트 실제 경로·작업공간 잠금·설정된 정책을 확인한다.
3. 이슈 하나의 실행과 검증이 끝나거나 실패·중단될 때까지 다음 이슈를 시작하지 않는다. 승인 요청은 실제 App Server 요청과 연결한다.
4. `완료 상태 갱신`은 저장된 요구사항·이슈의 완료 조건과 현재 코드/증거를 비교하고 제안과 근거를 표시한다. 테스트 실행은 읽기 분석과 별도 승인·권한 범위다.

## 4. 화면 및 접근성

### 4.1 최상위 3개 탭

- `Codex 대화`: 기존 일반 Codex 작업·대화·결과 접근.
- `아뜰리에 디자인`: 기존 Atelier 프로젝트·8개 설계 단계·제작·산출물·검토 접근.
- `이슈 처리`: 이 문서의 신규 기능.

프로젝트/연결 상태, 실행 중 표시, 중단, 승인, 모델 선택 등 공통 기능은 세 탭에서 접근 가능해야 한다. 탭 전환은 작업을 시작·중단·중복 실행하지 않고 미저장 입력과 실행 상태를 유지한다. 기존 홈·설정·대화 기록·활동 센터·픽셀·기존 화면 전환은 접근 경로를 보존한다. 기존 화면 호환 레이아웃을 사용할 때도 이슈 처리 진입 경로를 제공한다. 탭별로 다른 프로젝트가 암묵적으로 선택되지 않도록 공유 프로젝트의 전환과 실행 중 제한을 보여준다.

### 4.2 이슈 처리 화면

상단 공통 버튼: `이슈 후보 만들기`, `이슈 문서 불러오기`, `완료 상태 갱신`. 세부 영역은 다음과 같다.

- **계획과 대화**: 프로젝트/문서 선택, 분석 진행·누락, 추가 프롬프트, 대화, 구조 트리, 변경 전후 비교, 선택 적용, 저장 상태.
- **요구사항 검증**: 자료별 처리 상태, 요구사항→분류→이슈 연결, 발견·미확인·제외 사유, 품질·선행 관계 오류, 근거와 수정 제안.
- **이슈 목록**: 대분류/소분류 트리, 검색·상태·버전 필터, 페이지네이션 또는 가상 목록, 다중 선택, 상세, 버전·선행 관계 수정, 실행 선택.
- **실행 기록**: 각 실행 묶음 및 시도별 실제 thread/turn·이벤트·변경 파일·검증·승인·오류·중단·미확인 결과.
- **설정**: 자료·경로·동기화, 실행 범위·최대 N·실패 정책, 승인 모드·범위·만료·철회.

모든 상태는 기호와 한글 텍스트를 함께 표시한다. 모바일에서는 패널을 탭/세로 배치로 전환하고, 키보드 접근·포커스 복귀·스크린리더 상태 알림을 제공한다. 로딩·빈 목록·CLI 없음·연결 끊김·저장 실패·진행 중단을 실제 상태로 표시한다. `prefers-reduced-motion`을 존중한다.

## 5. 도메인 모델 및 버전 규칙

### 5.1 식별 및 데이터

모든 ID는 서버가 만든 불투명한 안정 식별자다. 표시 버전이나 제목은 ID가 아니다. DB와 교환 문서에는 다음 개념을 둔다. 구현 타입의 정확한 파일명은 조정 가능하나 의미와 무결성은 유지한다.

| 개념 | 주요 필드 및 제약 |
| --- | --- |
| ProjectBinding | 앱 내부 projectId, 검증한 실제 프로젝트 경로, 경로 확인 시각, revision. 경로 자체를 브라우저 권한 근거로 사용하지 않음 |
| Source | sourceId, 종류(project-file/imported-text/user-prompt), 표시 이름, 상대 경로 또는 사본 식별자, 해시, 처리 상태, 크기, 수정 시각. 원본 내용을 불필요하게 로그에 남기지 않음 |
| AnalysisSnapshot | snapshotId, projectId, 선택 Source ID·해시, 제외 목록, 사용자 요청, 분석 설정, 생성 시각. 각 결과의 입력 근거 |
| Requirement | requirementId, 설명, 출처 위치/원문 구간 또는 사용자 프롬프트 연결, kind(source/user/ai-proposal), 분류, 상태·근거·검토 여부 |
| Category | categoryId, parentId 또는 null, 제목, 표시 순서. 기본 UI는 대분류→소분류를 제공하고 데이터는 필요할 경우 계층 확장 가능 |
| Issue | issueId, 제목, 설명, categoryId, requirementIds, version, order, dependencyIds, 완료 조건, 우선순위, status, revision |
| ValidationRun/Finding | 대상 snapshot/revision, 범위, 수행·미수행·오류, 규칙, 심각도, 관련 ID, 근거, 해결/보류와 사유 |
| IssueRun/Attempt | issueId, batchId, attemptId, 상태, 실행 스냅샷, 실재 runtime ID, 시간, 오류, 검증 결과·변경 증거 |
| Evidence | 출처, 시각, 실제 관찰 결과, 대상 revision/hash, 적용 범위. AI 의견과 사용자 판정과 실행 결과 구분 |
| ApprovalPolicy/Audit | 승인한 사용자 설정과 프로젝트/배치/만료 범위, 지원되는 유형·제약, 철회 상태, 실제 요청에 대한 정책 판단. 민감한 전체 원문은 불필요하게 저장하지 않음 |

필수 제약: ID 유일성, 참조 대상의 동일 프로젝트 소속, 순환 없는 선행 관계, 적어도 하나의 완료 조건(정보 부족 후보는 등록 가능하나 기본 자동 실행 제외), 낙관적 revision 충돌 감지. 분류·이슈 이름 변경과 버전 변경은 이슈 ID·과거 시도를 유지한다. 삭제는 실행 기록을 파괴하지 않도록 보관/비활성화로 처리하고 참조 중인 항목은 사유를 보여준다.

### 5.2 개발 버전

- 버전은 세 개의 0 이상의 정수 `major.minor.patch`로 표현한다. 각 값의 **제품상 상한은 없다**. 자원 보호를 위한 입력 길이/표현 제한은 명시적 오류를 반환하고 전체 데이터가 처리된 것으로 표시하지 않는다.
- `1.1.1 < 1.1.2 < 1.2.0 < 2.1.0 < 3.4.12 < 10.2.1`. 숫자 구성요소를 차례대로 비교한다. 사전식 문자열 비교, 부동소수점, 정밀도를 잃는 변환을 사용하지 않는다. 선행 0 표기는 정규화 규칙을 일관되게 적용하고 충돌을 감지한다.
- 같은 버전의 이슈는 order, 안정적인 ID 순으로 정렬한다. 분류 번호와 개발 버전은 별도다. 개발 버전 변경은 요구사항·이슈의 ID와 실행 기록을 바꾸지 않는다.
- 낮은 버전을 먼저 계획·실행하며 선행 관계를 확인한다. 선행 이슈가 더 높은 버전이면 계획 오류로 표시한다. 순환·존재하지 않는 의존성은 등록/실행을 차단한다. 미완료 선행 이슈는 blocked로 표시한다. 사용자가 상위 버전만 고른 경우에도 해당 선행 조건은 우회하지 않는다.
- 버전은 릴리스 배포 상태나 SemVer 호환성을 뜻하지 않는다. 사용자는 대화 또는 직접 편집으로 값을 변경할 수 있다.

### 5.3 상태

이슈의 지속 상태와 실행 시도 상태를 구분한다.

| 표시 | 이슈 상태 | 의미 및 주요 전이 |
| --- | --- | --- |
| `□ 대기` | `ready` | 등록되었고 실행 대기. 정보 부족/미완료 선행 관계는 별도 차단 사유 표시 |
| `▶ 진행 중` | `running` | 실제 이슈 실행 중. 중복 시작 금지 |
| `⏸ 승인 대기` | `waiting_approval` | 실제 pending 요청이 있음. 승인·거절·중단 후 상태 갱신 |
| `△ 재시도 필요` | `retryable` | 일부 진행 또는 중단 후 미완료. 변경 내역과 사유 보존, 재실행 가능 |
| `✕ 실패` | `failed` | 실행/검증 실패. 사유 보존, 수동 재시도 가능 |
| `? 검토 필요` | `needs_review` | 성공 여부를 판단할 근거가 불충분하거나 사용자 확인이 필요 |
| `✓ 완료` | `completed` | 완료 조건별로 허용된 검증 근거 또는 명시적 사용자 판정이 충족됨 |

후보는 등록된 Issue의 실행 상태가 아니라 별도 `draft` 상태다. `blocked`는 선행 관계 등의 실행 가능성 표시이며 원래 이슈 상태를 지우지 않는다. 사용자는 사유와 함께 완료 이슈를 다시 열 수 있다. 재시도 시 이전 Attempt는 불변으로 유지한다. `turn/completed`만으로 이슈를 `completed`로 바꾸지 않는다. 중단 시 실행 결과를 확인할 수 없으면 `retryable` 또는 `needs_review`와 불확실한 결과를 표시한다.

## 6. 자료 수집·분석·대화

### 6.1 입력과 경계

- 사용자가 프로젝트 내 파일과 업로드한 UTF-8 Markdown/TXT, 추가 프롬프트를 선택한다. 경로 후보 검색은 제한된 범위에서만 수행하며 선택된 파일·제외·총 크기를 시작 전에 보여준다.
- 기본 제외: `.env` 및 유사 비밀 파일, 자격증명·키 파일, `.git`, `.local-data`, `node_modules`, 빌드/캐시, 바이너리 및 실행 파일. 제외 목록을 설정하더라도 비밀 내용을 무작정 읽거나 출력하지 않는다.
- 프로젝트 자료는 canonical 경로와 실제 대상을 확인하여 루트 밖 탈출·junction/symlink를 거부한다. 읽기 전후 실대상·파일 종류·크기/해시를 확인하고 교체·삭제되면 해당 입력을 실패 또는 stale로 표시한다. 업로드는 브리지의 관리 사본으로 취급한다.
- 각 단계는 파일 수·크기·구간·시간·동시성·출력 크기 제한을 두고 화면에 처리 현황을 표시한다. 어떤 제한에도 임의 잘림을 전체 성공으로 보고하지 않는다. 한도 도달 시 중단 지점과 재개 방법을 제공한다.
- 모델로 전송될 선택 자료·추가 프롬프트와 기존 Codex 로그인 경로 사용을 UI에 설명한다. 로컬 저장/브리지와 외부 모델 추론을 혼동하지 않는다. 로그에 원문·비밀·환경 변수 전체를 기록하지 않는다.
- 모델·문서·코드·테스트 데이터의 지시문은 비신뢰 데이터다. 프롬프트 경계뿐 아니라 브리지의 스키마·권한·경로 검증이 강제한다. 모델이 프로젝트 선택·권한 확대·승인 결정·외부 전송을 스스로 확정할 수 없다.

### 6.2 분석 파이프라인

1. 사용자가 선택한 입력과 파일 해시를 고정한다. 각 문서·구간에 안정된 source/segment ID를 부여한다.
2. 구간별 요구사항을 추출한다. 원문 근거, 불확실성, `source/user/ai-proposal`을 구분하고 구조화된 출력과 크기 한도를 검증한다.
3. 요구사항 중복·충돌 후보를 제안한다. 의미가 비슷하다는 이유만으로 자동 병합하거나 원문을 지우지 않는다.
4. 기능을 대분류·소분류로 배치하고 각 요구사항을 매핑한다. 필요한 만큼 분류를 만들고 분류되지 않은 항목을 별도로 유지한다.
5. 분류별로 이슈를 생성한다. 이슈는 설명·완료 조건·개발 버전·선행 관계·요구사항 연결과 불명확한 가정을 가진다.
6. 전역 관계와 개별 자료 범위를 검증한다. 생성 단계에서 누락된 구간·실패한 모델 호출·미연결 항목을 표시한다.
7. 사용자가 수정·선택 적용한 뒤 현재 revision을 기준으로 유효한 검증 결과와 함께 등록한다. 일부 실패 시 부분 후보는 보존하되 전체 검증 완료로 표시하지 않는다.

대화는 프로젝트별 계획 대화로 보관하고 선택한 초안 revision과 연결한다. AI 제안은 해당 revision을 기준으로 작성한다. 사용자가 다르게 편집했거나 다른 창이 변경한 뒤 도착한 제안은 `STALE_INPUT`으로 거부하고 비교/재생성을 제공한다. 모델 결과는 서버에서 스키마·길이·ID·참조·DAG·버전·출처를 재검증한다. 대화 메시지는 도구 권한이 아니다.

### 6.3 변경 후 최신성

- 원본 해시·요구사항·분류·이슈·완료 조건·버전·선행 관계가 바뀌면 영향을 받는 검증 기록은 `stale`로 표시한다. 과거 기록은 지우지 않는다.
- 분석 중 자료가 변경되면 기존 스냅샷 결과임을 표시하고 신규 상태에 적용하기 전 재분석/충돌 확인을 요구한다.
- 검증 중인 revision과 저장할 revision이 다르면 결과 자동 적용을 중단한다.

## 7. 규격 이슈 문서 및 동기화

### 7.1 정본과 형식

앱 내부 SQLite의 현재 프로젝트 revision이 실행·권한 판단을 위한 정본이다. 이슈 문서는 명시적으로 내보내고 가져오는 **교환 스냅샷**이다. 문서의 편집 내용만으로 실행이나 승인을 시작하지 않는다.

v1 교환 형식은 UTF-8 Markdown에 기계 판독 가능한 fenced JSON 블록 **정확히 하나**를 둔다. 블록 언어는 `auto-codex-issues-v1`; 블록 안 JSON이 가져오기 대상이다. 다른 Markdown 설명은 읽기 편의를 위한 텍스트이며 정본 데이터가 아니다. 앱은 JSON 내용으로 이슈를 화면에 렌더링한다. 사용자가 JSON 바깥 텍스트만 바꾸었다면 이슈 변경으로 간주하지 않음을 안내한다. 파일은 사람이 편집할 수 있으나 적용 전 전체 스키마 검증을 받는다.

아래는 개념 예시이며 구현에서 각 객체의 필수/선택 필드와 크기 제한을 JSON Schema 또는 동등한 엄격한 서버 검증으로 확정한다.

````markdown
# 이슈 계획

아래 데이터 블록은 Auto Codex 이슈 교환 형식입니다.

```auto-codex-issues-v1
{
  "format": "auto-codex-issues",
  "formatVersion": 1,
  "documentId": "doc-example-1",
  "revision": 1,
  "sources": [
    {"id": "src-1", "name": "기획 문서", "contentHash": "sha256:example"}
  ],
  "categories": [
    {"id": "cat-account", "parentId": null, "title": "계정 관리", "order": 1},
    {"id": "cat-login", "parentId": "cat-account", "title": "로그인", "order": 1}
  ],
  "requirements": [
    {"id": "req-login", "categoryId": "cat-login", "text": "사용자가 로그인할 수 있다", "origin": "source", "sourceId": "src-1", "locator": "로그인 절"}
  ],
  "issues": [
    {"id": "issue-login", "categoryId": "cat-login", "requirementIds": ["req-login"], "version": "1.2.0", "order": 1, "title": "로그인 처리", "description": "로그인 요청과 결과를 처리한다", "acceptanceCriteria": ["로그인 성공과 실패를 구분한다"], "dependencyIds": [], "status": "ready"}
  ]
}
```
````

`sha256:example`은 형식 설명용 자리표시자다. 실제 문서는 유효한 전체 해시를 사용하고, 구현의 테스트 fixture에서도 올바른 값을 사용한다. 교환 문서에 절대 프로젝트 경로·승인 정책·자격증명·실행 가능한 설정을 넣지 않는다. 실행 기록은 기본 교환 문서에서 제외한다.

### 7.2 가져오기

- 지원 버전이 아니거나 블록이 없거나 복수인 경우 정확한 이유를 표시한다. 일반 텍스트 분석은 사용자가 별도로 선택한다. 이상한 필드, ID 충돌, 잘못된 UTF-8, 잘못된 참조, 순환, 프로젝트 간 참조, 길이/크기 제한을 거부한다.
- 이슈 상태는 문서가 주장한 **가져온 상태**로 표시한다. `completed`를 가져와도 이 로컬 프로젝트에서 검증됐다고 표시하지 않으며 자동 실행의 선행 조건을 충족한 것으로 간주하기 전 확인/재검증한다. 문서의 running/waiting 상태는 복원하지 않는다.
- 신규 규격 문서는 성공적인 전체 검증과 저장 트랜잭션 후 이슈를 자동 등록한다. 중복 documentId/issueId는 동일 문서의 재가져오기와 서로 다른 문서의 ID 충돌을 구분한다. 다른 프로젝트에 임의로 덮어쓰지 않는다.
- 실패 시 전체 롤백하고 경로·필드·오류 유형을 제공한다. 업로드 파일은 텍스트로 취급하고 HTML/스크립트를 실행하지 않는다.

### 7.3 내보내기

- 사용자가 프로젝트 내 목표 경로를 선택하고 실제 경로·상위 디렉터리·링크를 확인한다. 신규 파일 생성/기존 파일 덮어쓰기를 명확히 표시한다. 기존 파일 덮어쓰기는 파일 해시와 revision이 예상값과 같을 때만 수행한다.
- 전체 직렬화·검증 후 동일 디렉터리의 임시 파일과 원자적 교체를 사용한다. 저장 실패, 경합 또는 대상 변경 시 원본을 보존하고 사용자에게 오류를 표시한다. 성공은 실제 저장 완료 후에만 표시한다.
- 내보내기는 로컬 파일 쓰기이며 모델 분석·코드 실행과 별도 행위다. 원본 기획 문서는 자동 덮어쓰지 않는다.

### 7.4 변경 감지와 충돌

앱은 마지막으로 동기화한 documentId·문서 해시·기준 revision을 기록한다. 파일에서 변경을 감지해도 자동 덮어쓰지 않고 비교를 제공한다.

| 상태 | 처리 |
| --- | --- |
| 앱과 문서가 기준에서 변경 없음 | 아무 작업 없음 |
| 문서만 변경 | 유효성 검사 후 ID 기준 차이를 표시하고 사용자 적용 또는 설정된 안전 가져오기 |
| 앱만 변경 | 명시적 내보내기 대기 |
| 양쪽 변경 | 기준 revision을 이용해 충돌을 표시하고 항목별 선택. 자동 덮어쓰기 금지 |
| 문서 삭제/이동 | 연결 끊김으로 표시. 앱 이슈·실행 기록은 유지 |
| 다른 문서가 같은 ID 사용 | 식별 충돌. 새 문서로 복사/ID 재생성 등 명시적 선택 전 반영 금지 |

### 7.5 등록과 동기화의 원자성

새 문서의 검증·DB 등록은 트랜잭션으로 처리한다. 로컬 DB와 외부 파일은 하나의 원자 트랜잭션이 아니므로 저장 단계와 해시를 별도로 기록한다. 어느 한쪽 실패 시 성공으로 표시하지 않고, 재시작 후 현재 파일/DB 해시를 비교해 사용자가 복구하도록 한다. 불명확한 파일 쓰기를 자동 재시도하지 않는다.

## 8. 두 종류의 검증

### 8.1 생성 검증: 요구사항이 이슈로 빠짐없이 연결됐는가

검증 입력은 명시된 AnalysisSnapshot과 현재 프로젝트 revision이다. 아래 결과를 구조화하여 기록한다.

1. **자료 처리 범위**: 선택/제외/실패/미지원 문서와 미처리 구간. 미처리 자료가 있으면 전체 분석 완료라고 표시하지 않는다.
2. **원문→요구사항**: 각 분석 구간의 추출 결과와 누락 가능성. 원문 위치 및 판단 근거 표시.
3. **요구사항→분류**: 미분류 요구사항, 잘못된 분류 후보.
4. **요구사항→이슈**: 원문 기능에 해당 이슈가 하나 이상 있는지, 소분류에 정의된 기능이 빠지지 않았는지 확인. 단순 연결 개수는 의미적 완전성의 증명이 아니므로 모델 검토 및 사용자 확인 상태를 별도 표시한다.
5. **이슈 품질**: 출처 없는 이슈, AI 제안, 중복/충돌, 빈 설명·완료 조건, 과도하게 넓은 범위, 불명확한 가정.
6. **순서·무결성**: 중복 ID·유효하지 않은 버전·누락 의존성·순환·높은 버전 선행 이슈·동일 버전 순서 충돌.

기계적으로 확인 가능한 오류는 결정적 코드로 검사하고, 의미상 누락·중복은 AI가 후보와 근거를 제안한다. 각 finding은 `open/resolved/deferred`와 조치·사유를 기록한다. 사용자가 AI 제안을 적용하거나 보류할 수 있다. 검증 결과는 원문·이슈 revision에 고정하며, 변경 시 stale 처리한다.

**등록 기준**: 스키마·ID·프로젝트 참조·DAG 등의 구조 오류는 등록을 차단한다. 의미상 누락 가능성·불확실성은 확인/보류 사유를 남기고 등록할 수 있지만 해당 범위가 완전 검증됐다고 표시하지 않으며, 불명확한 이슈는 기본 자동 실행 대상에서 제외한다.

### 8.2 구현 검증: 문서에 있는 기능이 실제로 구현됐는가

`완료 상태 갱신`은 대상 전체 또는 선택한 분류·이슈를 현재 코드와 비교한다. 먼저 읽기 전용 분석으로 코드·기존 증거를 확인한다. 테스트/명령 실행이 필요하면 예상 권한과 부작용을 보여주고 별도의 실행 설정·승인 정책을 적용한다. 의존성 설치·네트워크·운영 데이터 사용을 암묵적으로 포함하지 않는다.

결과 항목: 요구사항과 완료 조건, 기존/제안 상태, 근거 유형(코드 발견/실제 명령 결과/사용자 관찰/AI 의견), 대상 파일·위치 또는 실행 ID, 확인 시각과 입력 hash/revision, 미확인 항목, stale 여부. 종료 코드와 모델의 서술은 실제 UI/외부 시스템 동작을 자동 증명하지 않는다.

기본은 변경 제안 후 사용자 적용이다. 조건부 자동 갱신을 켠 경우에도 모든 필수 완료 조건에 해당하는 유효한 증거가 있어야 한다. 사용자 관찰이 필요한 조건은 사용자 판정 전까지 `needs_review`다. 이전 완료 증거가 오래됐거나 모순되면 `재확인 필요`로 표시하고 이전 판정과 근거를 보존한다.

### 8.3 커버리지 표시

화면에는 `선택 자료 중 처리됨/실패/제외`, `추출된 요구사항 중 연결됨/미연결`, `이슈 완료 조건 중 검증됨/미검증`을 각각 표시한다. 분모와 기준 revision을 항상 함께 보여주며 `100%`를 문서 의미 전체 또는 실제 제품이 완전하다는 보장으로 표현하지 않는다. 모델 분석 실패, 누락 구간, stale 검증, 사용자 보류는 별도로 표시한다.

## 9. 실행 대기열과 복구

### 9.1 선택 및 순서

- 선택 실행은 사용자가 고른 집합만 대상으로 한다. 미완료 실행은 대상 상태·정렬·최대 **서로 다른 이슈 시작 수** N·실패/승인 처리·재시도 횟수·시간 한도를 명시한다. retry attempt는 새 이슈 시작 수로 세지 않는다.
- 기본 대상은 실행 준비된 `ready`다. `retryable`, `failed`는 각 선택 가능하되 실패는 기본 제외한다. `needs_review`, 불명확한 이슈, 미완료 선행 이슈는 기본 제외한다. `completed`는 재오픈 전 실행하지 않는다.
- 기본 정렬은 numeric version → order → stable ID이며, 선행 관계가 충족된 이슈만 시작한다. 동일 프로젝트에서 이슈 하나만 실행한다. 현재 단계에서는 읽기 분석도 기존 공유 실행과 충돌하지 않도록 admission 규칙을 따른다.
- 직접 선택했더라도 미완료 선행 조건·잘못된 프로젝트·구조 오류는 우회하지 않는다. 사용자는 먼저 선행 항목을 해결하거나 명시적으로 계획을 수정한다.
- 대상·우선순위·이슈 내용·검증 조건·정책 revision을 배치/시도 시작 시 고정한다. 실행 중 문서가 변경되면 다음 이슈 시작 전 최신성을 확인하고 필요 시 중단한다.

### 9.2 시도 흐름

`queued → dispatching → running ↔ waiting_approval → verifying → settled`. 실제 turn에 연계된 이벤트가 있어야 `running`으로 표시한다. 완료/실패/중단과 검증 결과를 각각 기록하며 합성 이벤트나 캐릭터 동작을 작업 증거로 사용하지 않는다. 이슈별 thread/turn을 정확히 연계한다. 기존 Team 내부 작업의 최대 8개 제한을 이슈의 총 개수 제한으로 확장하지 않는다.

코드 변경을 포함한 이슈의 경우 사용자가 가진 기존 미커밋 변경을 유지한다. 시작 전 가능한 범위에서 Git 상태 또는 파일 기준점을 기록하고, 이전 변경과 이슈 중 관찰된 변경을 구별한다. Git이 없거나 구분이 불확실하면 그 한계를 보여준다. 임의 stash/reset/삭제는 금지한다. 중단/실패는 이미 변경된 파일을 자동 복원하지 않으며 결과와 남은 변경을 표시한다.

### 9.3 실패·중단·재시작

- 기본값: 실패, 확인 불가, 승인 대기에서 배치를 일시 정지한다. 사용자 선택으로 다음 대상 진행 가능하나 선행 관계는 유지한다. 재시도 최대 횟수를 한정한다.
- 중단 버튼은 배치의 다음 dispatch를 즉시 막고, 실제 활성 turn에 `turn/interrupt`를 요청하며 pending 승인 요청을 취소한다. 인터럽트 요청과 실제 종료 상태를 구분한다.
- 실행 시작 전에 durable idempotency key와 dispatch journal을 저장한다. 수락 응답이 끊겨 시작 여부가 불명확하면 `outcome_unknown`으로 표시하고 자동 재전송하지 않는다.
- 재시작 시 실행 중 배치/시도는 `interrupted` 또는 결과 불명으로 정리한다. pending request ID·세션 승인·네트워크 권한을 복원하지 않으며 자동 재실행하지 않는다. 사용자가 현재 상태와 파일 변경을 확인한 후 다시 시작한다.
- 중복 클릭·WebSocket 재전송은 동일 idempotency key에 동일 결과를 반환한다. 서로 다른 키로 동시에 시작하는 요청은 프로젝트 실행 잠금으로 하나만 허용한다. 잠금은 프로세스 충돌 시 영구 교착되지 않도록 복구한다.
- 분석과 실행 모두 제한 초과·CLI 종료·모델 실패·저장 실패·프로젝트 삭제/실대상 변경 시 이유를 기록하고 진행하지 않는다. 다른 탭과 공용 App Server/activeRun에 대한 admission 및 stop 경로를 단일하게 적용한다.

## 10. 수동·자동 승인과 위협 모델

### 10.1 사용자에게 표시할 범위

실행 시작 전과 승인 설정 화면에서 현재 프로젝트, workspace-write/read-only, 실제 쓰기 루트, 네트워크 기본값, 샌드박스 안에서 별도 요청 없이 가능한 동작, **추가 승인 요청**의 수동/자동 정책, 적용 대상·만료·철회 방법을 표시한다. 프로젝트 신뢰와 자동 승인 정책은 별도다. 정책 기본값은 `manual`, 네트워크 기본값은 off다.

자동 정책은 사용자가 프로젝트와 실행 묶음, 요청 종류, 구체적인 범위, 만료를 명시적으로 설정했을 때만 적용한다. App Server 또는 호스트가 정확하게 나타내거나 강제할 수 없는 권한·명령 조건은 UI에서 자동 승인을 지원한다고 표시하지 않는다. 문서/모델 출력은 정책을 생성·수정·확대할 수 없다. 정책 변경은 낙관적 revision과 명시적 사용자 행위를 확인하고 즉시 철회할 수 있어야 한다.

### 10.2 서버 판정

1. App Server에서 수신한 실제 pending request ID·method·thread/turn·프로젝트·배치·정책 revision·만료를 확인한다.
2. 요청된 구조를 알려진 스키마로 완전히 해석하고 정확한 범위를 확인한다. 알 수 없는 필드/유형, 잘못된 경로·실대상, 범위 불명, 요청과 정책 불일치 시 수동 승인 또는 정지한다.
3. 프로토콜이 부분 권한을 안전하게 허용하는 경우에만 요청과 정책의 교집합을 계산해 요청의 부분집합만 부여한다. 그렇지 않으면 부분 허용을 주장하지 않고 수동 확인한다. 실제 프로토콜 버전·플랫폼에서 검증해야 한다.
4. 브라우저는 승인 ID와 사용자의 결정만 제출한다. 브라우저가 제출한 명령·경로·권한을 실제 요청으로 대체하지 않는다. 이미 처리·만료·취소된 요청, 다른 실행의 ID는 거부한다.
5. 명령 문자열의 접두사만으로 안전하다고 판정하지 않는다. 셸 연산자·스크립트/의존성·실행 파일 교체 등 의미를 확실하게 제한할 수 없다면 자동 승인하지 않는다. 광범위한 셸 승인과 `thread/shellCommand`는 제공하지 않는다.
6. 자동/수동 결정, 정책 ID·revision, 요청 종류와 최소한의 범위·시간·결과를 감사 기록으로 남긴다. 비밀·명령 원문을 무분별하게 로그에 남기지 않는다. 기존 진단 이벤트도 민감 정보 보호 규칙을 따른다.

### 10.3 위험 분석 및 운영

- **자산/공격자:** 로컬 프로젝트·개인 자료·명령/네트워크 권한을 악성 프로젝트 문서, 변조된 renderer 메시지, 잘못된 모델 출력, 오래된 요청으로부터 보호한다.
- **경계/오용:** 파일→모델→브리지→App Server→OS와 브라우저→브리지를 통과한다. 문서 프롬프트 주입, symlink/junction 변경, 재전송, 자동 승인 과대 범위, 모델 오분류, 실행 중 프로젝트 교체를 고려한다.
- **방어/증거:** 정규화된 경로와 실대상 확인, strict schema와 ID/revision 확인, pending 요청 상관관계, 정책 기본 거부, 프로젝트별 단일 쓰기, 중복 시작 방지·실패 테스트를 적용한다. 모델 프롬프트만을 보안 통제로 보지 않는다.
- **배포/복구:** 로컬 DB는 버전 마이그레이션 전 일관된 백업과 역호환 한계를 기록한다. 브리지 종료 후 DB/관련 파일과 사용자 프로젝트를 별도 백업한다. Git/파일 백업이 없는 변경은 자동 복구를 보장하지 않는다. 외부 배포·운영 변경은 이 기능의 구현과 별도다.

## 11. 저장소와 메시지 계약

### 11.1 저장

이슈 전용 SQLite를 `.local-data/issues/` 아래에 두는 것을 기본안으로 한다. Node의 기존 지원 버전과 `node:sqlite` 사용 가능 여부를 확인한다. 요구사항·출처 사본/해시·계획 대화·초안 revision·등록 이슈·검증·시도·정책·감사를 구분한다. 사용자 프로젝트 폴더에 내부 DB를 자동 생성하지 않는다.

- 스키마 버전과 migration, 트랜잭션, foreign key, 유일성, optimistic revision, durable 저장 후 응답을 적용한다.
- 변경 기록과 실행 근거의 크기를 제한하고 페이지네이션한다. 제한 도달 시 명시적 오류/보관 방법을 제공하며 과거 기록을 자동 삭제하지 않는다.
- 원본 업로드 사본과 대화에 민감 정보가 포함될 수 있으므로 앱 전용 로컬 저장소에서 보호하고 정적 서버로 제공하지 않는다. 백업/삭제 UI는 대상과 영향을 명확하게 표시한다.
- 프로젝트 이동·복사·삭제·동일 경로 재생성 시 기존 프로젝트와의 연결을 자동 확정하지 않는다. 실제 경로/사용자 확인을 통해 재연결하고 다른 프로젝트 데이터와 병합하지 않는다.

### 11.2 제안 API 계약

기존 loopback WebSocket을 확장한다. 아래 이름은 구현 시 사용할 수 있는 **제안**이며 현재 지원 API가 아니다. 모든 변경 요청에 `v`, `clientRequestId`, `projectId`, 필요한 `expectedRevision`과 멱등성 키를 둔다. 브리지는 서버 소유 프로젝트/활성 실행과 현재 실제 경로를 확인하고 길이·크기·허용 필드·속도·연결 한도를 검증한다.

| 요청 예시 | 서버 동작 |
| --- | --- |
| `issues.sources.list/add/remove` | 자료 목록, 선택된 입력 검증/사본 등록, 연결 해제 |
| `issues.analysis.start/interrupt/status` | 스냅샷 분석과 단계별 상태 |
| `issues.plan.read/chat/proposal.apply/edit` | 계획 읽기, 대화 제안, revision 확인 후 선택 적용/직접 편집 |
| `issues.validation.start/read/resolve` | 생성 검증, finding/범위/해결 사유 |
| `issues.document.import/export/diff` | 규격 검증·원자 등록·내보내기·충돌 비교 |
| `issues.list/read/update` | 필터·커서 목록 및 revision 검증 편집 |
| `issues.batch.preview/start/pause/interrupt` | 대상 미리보기·고정·순차 실행·정지 |
| `issues.status-refresh.start/apply` | 구현 검증 결과 제안 및 revision 기준 적용 |
| `issues.policy.read/update/revoke` | 정책 조회·명시적 설정·철회 |

모든 응답은 요청 ID와 `ok` 또는 안전한 오류 코드/메시지를 포함한다. 장시간 작업은 `operationId`를 반환하고 별도 상태 이벤트로 실제 진행을 보낸다. 흔한 오류: `INVALID_INPUT`, `UNSUPPORTED_FORMAT`, `VERSION_CONFLICT`, `STALE_INPUT`, `PATH_INVALID`, `BUSY`, `LIMIT_EXCEEDED`, `CLI_UNAVAILABLE`, `POLICY_DENIED`, `STORAGE_FAILED`, `INTERRUPTED`, `OUTCOME_UNKNOWN`. 모델·파일·명령 원문이나 스택을 오류로 노출하지 않는다.

WebSocket의 loopback Host/Origin 검증과 메시지 크기 제한을 유지한다. 민감한 프로젝트/정책 API는 기존 로컬 신뢰 모델을 재검토하고, Origin만을 인증으로 간주하지 않는다. 여러 로컬 창·비브라우저 클라이언트가 연결될 수 있는 경우 정책 변경·이슈 실행 권한을 어떻게 증명할지 구현 전에 명시하고 테스트한다. 기존 보안 수준을 낮추는 임시 우회는 허용하지 않는다.

### 11.3 구현 위치 제안

```text
src/features/issues/          탭, 트리/대화/검증/목록/실행/설정 UI
shared/issues/                버전·상태·요청/응답·스키마 계약
server/issues/                입력·분석·문서·검증·저장·실행·승인 정책
server/index.ts               기존 admission/프로젝트/승인·이벤트 연결
docs/                         운영·문서 규격·검증 기록
```

코드 배치는 구현 단계에서 조정 가능하다. 핵심은 브리지의 신뢰 경계와 분석/순서/검증 로직의 독립 테스트 가능성이다. `src/App.tsx`에 모든 비즈니스 로직을 몰아넣지 않는다.

## 12. 단계별 구현과 수용 기준

각 단계는 이전 데이터와 화면을 유지하고 테스트를 통과해야 한다. UI 목업만으로 완료 처리하지 않는다.

### 단계 1: 세 탭과 프로젝트 기반

- 세 최상위 탭, 공통 프로젝트/실행/승인, 기존 기능 접근 보존.
- 빈 상태·CLI 없음·폴더 없음·모바일·키보드·탭 전환 상태 유지.
- **수용:** 탭 전환만으로 실행이 시작/중단되지 않고 기존 대화·아뜰리에·활동·설정이 동작한다.

### 단계 2: 입력·요구사항·대화 초안

- 문서 선택·추가 프롬프트·스냅샷, 단계별 읽기 분석, 요구사항 출처·분류·이슈 초안, 대화형 변경 및 직접 편집.
- **수용:** 원문/추정/사용자 입력을 구분하고, 중단·오류·누락 구간과 revision 충돌을 표시하며 프로젝트 파일이 분석만으로 변경되지 않는다.

### 단계 3: 이슈 생성 검증

- 원문→요구사항→분류→이슈 연결, 기계/의미 검증, findings와 보류 사유, 변경 후 stale 처리.
- **수용:** 의도적으로 빠뜨린 요구사항/소분류 기능과 순환·중복을 찾고, 미처리 문서를 완전 처리로 표시하지 않는다. AI 검토의 불확실성을 구분한다.

### 단계 4: 규격 문서와 등록

- v1 내보내기/가져오기, 전체 검증 후 자동 등록, ID·revision·동기화 충돌 처리.
- **수용:** 새 문서는 유효할 때만 자동 등록되고 재가져와도 중복이 생기지 않는다. 사용자 변경·문서 동시 변경, 손상·참조 오류는 성공으로 숨기지 않는다.

### 단계 5: 완료 상태 갱신

- 현재 코드·완료 조건의 근거 및 상태 변경 제안, 검증 유형과 불확실성 표시.
- **수용:** 파일 존재/모델 완료 주장만으로 동작 확인 완료가 되지 않으며 읽기 분석은 명령 실행을 시작하지 않는다.

### 단계 6: 선택 및 자동 순차 실행

- 선택/N개/조건 기반 배치, numeric version·DAG 순서, 실제 이벤트·시도·중단·재시작.
- **수용:** 동시에 하나만 수정하고 최대 시작 수·선행 조건·중복 요청을 준수한다. 실패/중단 후 변경과 불확실한 결과가 보이며 자동 재생하지 않는다.

### 단계 7: 제한적 자동 승인

- 명시적 범위·만료·철회, 현재 App Server 요청과 정책 비교, 감사 기록.
- **수용:** 허용된 실제 요청만 승인하고 범위 밖/미확인/만료/취소/다른 실행의 요청은 수동 처리 또는 거부한다. 부분 권한 지원이 불명확하면 자동 승인하지 않는다.

각 단계의 미구현 항목은 숨기거나 `준비 중`으로 표시하며 실제 동작한다고 설명하지 않는다. 전체 작업 완료는 모든 단계와 13절 검증을 충족했을 때만 선언한다.

## 13. 테스트 계획과 최종 완료 기준

합성 문서와 격리된 프로젝트/fixture를 사용한다. 실제 운영 데이터·비밀·외부 서비스 없이 재현 가능한 검사를 우선한다.

### 13.1 단위·계약 테스트

- 버전: `1.2.0 < 1.10.0`, `9.99.99 < 10.0.0`, 큰 정수 정밀도, 정규화·잘못된 입력·동일 버전 순서.
- 분류/매핑: 여러 대분류·소분류, 원문 없는 AI 제안, 한 요구사항에 여러 이슈, 한 이슈에 여러 요구사항, 미연결·잘못된 참조·보류.
- DAG: 누락 선행 ID·자기 의존·순환·높은 버전 의존·미완료 선행, 다중 선택 및 같은 버전.
- 문서: 정상 왕복, 빈/복수 fenced 블록, 지원하지 않는 버전, 손상 JSON/UTF-8, 중복 ID, 크기 경계, 충돌, 전체 롤백, 외부 수정.
- 상태: 합법/불법 전이, 완료→재오픈, 실패/재시도, 결과 불명, 원본/완료 조건 변경 시 stale.
- 정책: 요청/정책의 정확한 교집합, 알 수 없는 필드, 경로·요청 범위 변경, 만료·철회·재전송, 다른 프로젝트/배치, 잘못된 pending ID, 부분 권한 미지원.

### 13.2 통합·장애 테스트

- 여러 문서/구간 중 하나의 AI 실패, 출력 잘림·잘못된 구조·인젝션 지시문, 손상/누락 자료가 부분 상태로 표시되는지.
- 경로 탈출, junction/symlink 변경, 읽는 도중 파일 교체, 프로젝트 삭제·이동, 업로드 파일과 프로젝트 경계.
- 같은 이슈의 중복 클릭·여러 창 경쟁·동일/상이 idempotency key, 기존 Codex/Atelier 실행 중 배치 시작, 프로젝트별 단일 writer.
- dispatch 직전/직후 종료, 승인 중 연결 끊김, 저장 실패·앱 재시작, 취소와 완료 경쟁, 불명확한 실행 결과의 자동 재실행 방지.
- 실제 변경 이벤트와 명령 결과를 구분하고 turn 완료만으로 이슈 완료가 되지 않는지. Git dirty 및 non-Git 작업공간에서 기존 변경을 보존하는지.
- 읽기 분석에서 파일 쓰기·권한 확대·네트워크를 요청한 경우 거부되는지. 자동 승인 밖 요청이 수동 대기/정지하는지.

### 13.3 UI·사용자 흐름

- 세 탭/기존 화면 기능 보존, 다양한 화면 크기·키보드·스크린리더·감소된 모션.
- 프로젝트 없음·CLI 없음·분석 중/중단·문서 오류·저장 실패·승인 대기·부분 검증·결과 불명.
- 대화 수정과 변경 비교, 원문까지 추적, finding 해결/보류, 규격 문서 가져오기/충돌, 선택 N개 순차 실행, 실패 후 재시도, 완료 상태 제안 및 적용.
- 대량 합성 이슈에서 검색·필터·페이지네이션, 부분 처리·재개, 사용자 선택이 다른 페이지에서도 유지되는지.

### 13.4 필수 검사와 보고

의미 있는 구현 변경은 `npm run typecheck`, `npm test`, `npm run build`를 최종 변경 후 실행한다. 관련 단위·통합 검사를 먼저 수행하고 UI 변경은 실제 관련 화면 크기와 핵심 흐름을 확인한다. 기존 Atelier/대화/승인 회귀도 영향을 받는 범위에서 실행한다. 검사의 환경·명령·결과와 미검증 한계를 기록한다. 실패하거나 실행하지 못한 검사를 통과로 표현하지 않는다.

완료 보고에는 변경·위험도(R2)·검증 결과·권한/호환성·저장과 복구·남은 위험·승인 대기 여부를 포함한다. 독립 보안 리뷰를 수행하지 않았다면 수행했다고 표현하지 않는다.

## 14. 구현 전 결정을 유지할 사항

다음은 이 명세의 기본 제품 결정이며 구현 시 임의로 축소하지 않는다.

- 세 탭의 이름과 `이슈 후보 만들기`, `완료 상태 갱신`은 사용자가 요청한 주요 진입점이다.
- 버전의 총 범위, 분류 개수, 이슈 개수에 임의의 제품 상한을 두지 않는다. 실행 가능한 처리 단위와 자원 한도는 정하고 부분 처리를 투명하게 표시한다.
- 일반 문서는 AI 후보로 분석하고 규격 문서는 검증 후 자동 등록한다. 둘 다 자동으로 코드 수정을 시작하지 않는다.
- 생성 검증과 구현 검증을 분리하고 원본 추적 및 불확실성을 유지한다.
- 이슈 수정은 순차 처리하고, 선택 실행과 미완료 순차 실행을 모두 제공한다.
- 자동 승인은 사용자가 선택한 실제 요청 범위에만 적용하며 판단 불가는 수동으로 전환한다. 기본 권한과 추가 승인 범위를 함께 표시한다.
- 완료·실패·재시도·검토 필요·중단·결과 불명을 구분한다. 기록·사용자 변경을 지우거나 작업을 몰래 재실행하지 않는다.
