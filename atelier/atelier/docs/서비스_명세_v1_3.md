용도: 개인용 로컬 서비스의 UX 설계 및 MVP 구현 기준

1.3 변경 요약: AI 직접 연동을 초기 구현의 필수 조건에서 제외했다. 내장 질문·예시·선택지, 사용자 작성과 비교, 규칙 기반 점검 및 템플릿 조립만으로 설계와 프롬프트 생성, 자가 진단과 수정을 완료한다. 이미 Codex와 연결된 외부 서비스와의 연결은 후속 확장으로 분리했다.

1.2 변경 요약: 사용자가 다음 할 일을 스스로 추측하지 않도록 현재 작업과 추천 행동, 전환 이유와 완료 결과를 연결했다. 자유로운 탭 이동과 상황별 진행 가이드를 함께 제공하고, 재접속, 대기와 오류, 외부 제작과 복귀, 진단과 수정의 연결을 구체화했다.

1.1 변경 요약: 고객과 제공 가치 및 해소할 의문을 필수 설계 맥락으로 강화했다. 생성 전 적합성 점검과 생성 후 증거 기반 자가 진단을 구분하고, 의도와 스타일이 어긋나면 수정과 재검토를 거치도록 필수 흐름을 추가했다.

## 1 서비스 정의

### 1.1 목적

사용자가 만들고 싶은 제품과 좋아하는 이미지에서 출발해, 제품 정의·콘텐츠 준비·사용자 흐름·레퍼런스 분석·컨셉 선택·스타일 규칙을 자연스럽게 정리하도록 돕는다. 그 결과를 외부 AI 디자인 도구나 코딩 에이전트에 전달할 수 있는 하나의 완성된 디자인 프롬프트로 만든다.

사용자는 모든 디자인 용어나 필요한 입력을 미리 알 필요가 없다. 서비스는 사용자가 모르는 내용을 질문과 예시, 비교 가능한 제안으로 구체화하며, 어떤 선택이 어떤 결과를 만드는지 학습하도록 돕는다. 생성된 디자인은 실제 결과를 등록해 의도와 스타일을 자가 진단하고, 필요한 수정과 재검토를 거쳐 원하는 방향에 접근한다.

### 1.2 핵심 사용자 가치

- 원하는 분위기와 스타일을 설명 가능한 디자인 기준으로 바꾼다.
- 서비스 전체 경험과 화면별 역할을 연결한다.
- 레퍼런스의 관찰 사실과 해석, 실제 적용 결정을 구분한다.
- 사용자 요구와 공통 작업 기준을 빠짐없이 반영한 디자인 프롬프트를 생성한다.
- 결과와 수정 이유를 기록해 다음 작업에서 판단과 지시 능력을 높인다.
- 현재 상황에서 무엇을 왜 해야 하는지와 완료 후 이어질 작업을 직관적으로 알 수 있게 한다.

### 1.3 첫 번째 제품의 범위

첫 번째 제품은 AI 연결 없이 프로젝트를 설계하고 최종 프롬프트를 내보내는 가이드 도구다. 내장 가이드에 따라 사용자가 관찰과 결정을 작성하고 프로그램이 템플릿으로 조립한다. 기본 결과는 하나의 통합 프롬프트다. AI API 키, 모델 선택, Codex 설치 또는 외부 연결 성공을 사용 시작과 완료의 전제 조건으로 두지 않는다.

컨셉 비교를 위한 색상·서체·버튼 등 간단한 시각 샘플은 제공한다. 완성된 웹사이트, 게임, 프로덕션 에셋을 서비스 내부에서 자동 제작하는 기능은 후속 확장으로 둔다.

### 1.4 기본 운영 가정

- 개인 사용, 로컬 웹앱을 우선한다.
- 한국어 가이드와 한국어 프롬프트를 기본으로 한다.
- 프로젝트와 이미지 원본, 선택 기록은 로컬에 저장한다.
- 초기 버전은 외부 AI 호출 없이 실행한다. 가이드 내용, 비교용 예시와 기본 시각 샘플도 로컬에서 사용할 수 있게 제공한다.
- 향후 이미 Codex와 연결된 외부 서비스와 연동해 분석과 피드백을 보조받는다. 그 서비스의 현재 API나 인증 방식은 확인되지 않았으므로 본 명세에서 임의로 확정하지 않는다.
- 초기 사용자에게 디자인 전문 용어나 복잡한 설정을 요구하지 않는다.
- 게임, 제작 도구, 콘텐츠 서비스, 판매 서비스 등 제품 유형에 따라 질문과 산출물 구성을 바꾼다.

## 2 성공 기준과 설계 원칙

### 2.1 성공 기준

첫 프로젝트에서 다음을 완료할 수 있어야 한다.

1. 제품의 사용자와 전체 경험을 설명한다.
2. 핵심 활동과 화면 또는 상태를 연결한다.
3. 레퍼런스 또는 직접 입력한 취향을 적용 가능한 시각 규칙으로 정리한다.
4. 비교한 제안 중 사용할 방향을 선택한다.
5. 외부 도구에 전달할 통합 프롬프트와 필요한 참고 자료를 확보한다.
6. 결과를 보고 무엇을 조정할지 기록한다.

성공 여부는 프롬프트 길이나 AI가 매긴 종합 점수로 판단하지 않는다. 실제 작업에서 요구 누락, 레퍼런스 오해, 반복 설명이 줄었는지 확인한다.

### 2.2 설계 원칙

| 원칙 | 서비스에서 구현할 행동 |
|---|---|
| 모르는 상태에서 시작 가능 | 각 질문에 아직 모름과 예시 보고 고르기를 제공한다 |
| 전체 경험과 화면을 연결 | 전체 목표에서 흐름과 화면 또는 상태로 내려가고 다음 활동으로 이어지게 한다 |
| 시각 취향을 언어화 | 느낌을 색 관계·형태·재질·서체·구성으로 분석한다 |
| 선택을 확인 가능하게 제시 | 대안을 동일한 항목과 샘플로 비교한다 |
| 사실과 제안의 분리 | 사용자 입력, 직접 관찰, 내장 예시와 외부 제안 및 확정 결정을 구별한다 |
| 학습을 작업에 연결 | 질문 옆에 이유와 예시를 제공하고 선택 근거를 남긴다 |
| 하나의 데이터 원본 | 탭마다 같은 정보를 중복 저장하지 않는다 |
| 변경의 영향 표시 | 상위 결정이 바뀌면 영향을 받는 항목을 재검토 대상으로 표시한다 |
| 출력까지 연결 | 입력한 정보가 최종 프롬프트 어디에 반영됐는지 확인한다 |
| 다음 행동이 보이는 진행 | 현재 상태에 맞는 다음 행동과 그 이유 및 이어질 결과를 보여 준다 |
| 연결된 작업과 자유 탐색 | 추천 진행을 따르거나 탭을 탐색해도 입력과 현재 맥락을 유지한다 |

### 2.3 첫 버전에 포함하지 않는 기능

- 서비스 내부에서 AI API를 호출해 이미지를 해석하거나 문장과 피드백을 생성하는 기능
- AI 제공자 선택과 API 키 입력 및 모델 설정
- AI에게 바로 보내기, 자동 피드백 받기, 응답 스트리밍과 실행 상태 조회
- 외부 AI 도구의 실행을 자동 제어하는 기능
- 임의의 외부 스킬을 실행하거나 설치하는 기능
- 로그인과 결제, 다중 사용자 실시간 협업
- Pinterest 로그인, 수집 자동화, 전체 사이트 크롤링
- 에셋 마켓과 저작권 자동 판정
- 생성 결과의 상품성을 자동 보증하는 점수
- 모든 프로젝트에 동일한 화면 구조를 적용하는 자동 템플릿

## 3 사용자 유형과 시작 경로

### 3.1 사용자 유형

| 유형 | 시작 상태 | 필요한 도움 |
|---|---|---|
| 아이디어부터 시작 | 만들 서비스만 대략 안다 | 사용자와 목표, 기능과 흐름을 정리한다 |
| 이미지부터 시작 | 한 장의 느낌은 좋지만 설명하기 어렵다 | 이미지를 분석하고 서비스에 맞는 방향을 비교한다 |
| 컨셉이 정해짐 | 분위기와 스타일을 이미 선택했다 | 스타일을 구체적인 규칙과 화면으로 연결한다 |
| 기존 결과 개선 | 화면이 있으나 원하는 인상과 다르다 | 차이의 원인을 찾고 변경 범위를 정한다 |

### 3.2 프로젝트 생성

처음에는 다음 세 항목만 받는다.

1. 프로젝트 이름
2. 만들고 싶은 것에 대한 자유로운 설명
3. 현재 상태 선택

이미지는 선택 입력이다. 사용자는 상태를 나중에 바꿀 수 있다.

자유 입력 예시:

> 픽셀 리소스로 샌드박스 생존 게임을 만들고 싶다. 숲에서 탐험하고 거점을 만드는 느낌이면 좋겠지만 아직 화면과 색은 정하지 못했다.

입력 원문을 보관하고 사용자가 짧은 질문과 예시를 통해 제품 유형, 고객과 목표를 정리하게 한다. 초기 버전에서 자유 문장을 의미 분석해 필드를 자동 추출하지 않는다. 이미 입력한 내용은 다시 볼 수 있고 필요한 문장을 직접 선택하거나 편집해 사용할 수 있다. 원문에 없는 내장 예시는 참고용으로 표시하며 사용자 선택 없이 확정하지 않는다.

### 3.3 추천 경로

- 아이디어부터: 프로젝트 설계 → 사용자 흐름 → 컨셉 탐색 → 스타일과 리소스 → 디자인 브리프 → 프롬프트
- 이미지부터: 레퍼런스 연구 → 최소 프로젝트 설계 → 컨셉 탐색 → 사용자 흐름과 스타일 구체화 → 디자인 브리프 → 프롬프트
- 컨셉이 정해짐: 프로젝트 설계 → 확정 컨셉 등록 → 사용자 흐름 → 스타일과 리소스 → 디자인 브리프 → 프롬프트
- 기존 결과 개선: 프로젝트 설계 요약 → 자가 진단과 수정 → 차이 분석 → 관련 기준 수정 → 수정 프롬프트

추천 경로는 강제 순서가 아니다. 탐색 중 탭을 자유롭게 이동할 수 있다. 최종 출력 시 필요한 최소 정보만 점검한다.

### 3.4 진입 경로별 첫 행동

서비스가 사용자에게 시작 경로만 고르게 하고 빈 탭 목록에 남겨 두지 않는다. 선택 직후 관련 입력과 다음 행동을 같은 맥락에서 보여 준다.

| 시작 상태 | 처음 보여 줄 작업 | 직접 실행할 행동 | 이어질 결과 |
|---|---|---|---|
| 아이디어부터 | 사용자 원문의 제품 요약 | 이 설명으로 제품 방향 정리하기 | 확인할 사용자와 전체 목표 초안 |
| 이미지부터 | 원본 등록과 취향 메모 | 이미지 보며 느낌 정리하기 | 관찰 질문과 예시 및 직접 작성한 적용 후보 |
| 컨셉이 정해짐 | 기존 컨셉 입력 또는 확인 | 이 컨셉을 표현 규칙으로 정리하기 | 이미 정한 방향의 구체화 |
| 기존 결과 개선 | 원래 의도와 결과의 연결 | 이 결과에서 어긋난 부분 찾기 | 진단 항목과 수정 후보 |

첫 행동 전에 꼭 필요한 정보만 요청한다. 이미지가 없거나 분석을 원하지 않는 사용자는 직접 취향을 정리하는 경로로 이어진다.

## 4 정보 구조와 작업 화면

### 4.1 공통 화면

- 왼쪽: 프로젝트 목록과 프로젝트 전환
- 상단: 현재 프로젝트, 저장 상태, 현재 작업과 진행 상황
- 중앙: 현재 작업에서 이어질 다음 행동과 이유, 작업 탭 및 해당 편집 화면
- 오른쪽: 선택한 항목의 설명, 근거, 출처와 적용 관계
- 필요 시 하단 또는 별도 패널: 변경 내역과 프롬프트 반영 내용

앱의 기본 작업 화면은 프로젝트 간 비교와 읽기를 위한 중립적인 표현을 사용한다. 프로젝트 스타일은 시각 샘플과 설계 결과에 적용한다. 프로젝트마다 전체 작업 도구의 가독성이 바뀌지 않게 한다.

### 4.2 탭 구성

| 탭 | 질문 | 주요 입력 | 출력 |
|---|---|---|---|
| 프로젝트 설계 | 무엇을 누구를 위해 만드는가 | 제품, 사용자, 전체 목표, 기능, 콘텐츠, 범위 | 제품 브리프와 콘텐츠 목록 |
| 사용자 흐름 | 사용자는 어떻게 목적을 이루는가 | 활동, 단계, 화면, 상태, 분기와 복구 | 흐름과 화면 역할표 |
| 레퍼런스 연구 | 이 이미지의 무엇이 좋은가 | 이미지, 선택 영역, 취향 메모 | 관찰·해석·적용 후보 |
| 컨셉 탐색 | 어떤 방향으로 표현할 것인가 | 원하는 느낌, 레퍼런스, 확정 조건 | 비교 가능한 방향과 선택 기록 |
| 스타일과 리소스 | 선택한 방향을 무엇으로 구현할 것인가 | 색, 서체, 형태, 재질, 에셋과 적용 범위 | 스타일 규칙과 리소스 계획 |
| 디자인 브리프 | 결정들이 서로 맞는가 | 각 탭의 결과와 수정 | 통합 설계안과 문제 목록 |
| 프롬프트 스튜디오 | 외부 AI에 어떻게 전달할 것인가 | 출력 목적과 범위, 공통 기준 | 통합 프롬프트와 자료 묶음 |
| 자가 진단과 수정 | 의도와 스타일이 실제로 적용됐는가 | 실제 결과, 고정 기준, 사용자 확인 | 증거 기반 진단, 수정 계획과 재검토 |

각 탭은 필요한 상태를 표시한다.

- 시작 전
- 작성 중
- 선택 필요
- 사용 가능
- 변경으로 재검토 필요

이 상태는 입력과 선택의 진행 상태이며 디자인 품질 점수가 아니다.

### 4.3 초보자와 숙련자 보기

같은 데이터에 대해 두 가지 보기 밀도를 제공한다.

- 가이드 보기: 질문을 단계적으로 보여 주고 이유와 예시를 곁들인다.
- 빠른 편집: 표와 목록에서 여러 항목을 한 번에 편집한다.

보기 전환은 저장된 데이터와 프롬프트의 의미를 바꾸지 않는다.

### 4.4 공통 설정

작업 탭과 별도로 공통 설정 진입점을 제공한다.

- 가이드 보기의 기본 밀도
- 재사용할 공통 작업 기준과 버전
- 직접 등록한 작업 절차 또는 스킬 참조
- 기본 출력 언어와 형식
- 데이터 저장과 백업 상태
- 프로젝트 백업과 복원

프로젝트별 시각 취향은 공통 설정에 자동 등록하지 않는다. 사용자가 재사용하도록 선택한 원칙만 공통 기준 후보로 추가한다.


### 4.5 자연스러운 진행의 UX 계약

이 서비스의 핵심 UX 기준은 사용자가 이 다음에는 어떻게 해야 하지라고 추측하지 않아도 진행할 수 있는 것이다. 탭은 작업 자료를 찾아가고 편집하는 구조이며, 사용자는 상황별 진행 안내를 통해 작업을 이어갈 수 있다.

모든 주요 진입과 전환에서 다음 내용을 알 수 있게 한다.

1. 지금 무엇을 하고 있는가.
2. 현재 단계에서 사용자가 결정하거나 입력할 것은 무엇인가.
3. 다음 행동을 왜 하는가.
4. 행동 후 무엇이 준비되거나 어느 작업으로 이어지는가.
5. 모르는 경우, 실패한 경우, 나중에 하려는 경우 어떻게 계속할 수 있는가.

현재 작업에 붙은 짧은 설명과 실제 행동 버튼으로 전달한다. 긴 도움말을 읽어야 다음 단계의 위치를 찾을 수 있는 구조는 피한다.

### 4.6 추천 진행과 자유로운 탭 이동

초보자의 기본 진입은 현재 할 일을 중심으로 한 가이드 보기다. 프로젝트의 큰 진행을 의도 정리, 방향 구체화, 프롬프트 준비, 결과 진단과 수정으로 묶어 보여 줄 수 있다. 이미지부터 시작하는 등 경로가 다르면 필요한 작업 순서를 유연하게 연결한다.

사용자가 화면을 골라 편집하려면 기존 여덟 탭을 사용할 수 있다. 다른 탭을 열었다고 저장한 답과 선택 또는 추천 진행을 잃지 않는다. 탭 이동을 잠그거나 모든 탭을 순서대로 완료하게 강제하지 않는다.

이미 답한 정보와 확정한 컨셉은 재입력을 요구하지 않는다. 가이드 보기와 빠른 편집은 같은 상태와 데이터를 사용한다. 현재 할 일은 별도의 아홉 번째 필수 탭이 아니라 공통 작업 영역과 프로젝트 복귀 화면에서 제공한다.

### 4.7 다음 행동의 표시

현재 작업에는 다음 항목을 함께 제공한다.

| 항목 | 예시 |
|---|---|
| 현재 상태 | 레퍼런스에서 적용할 특징을 찾았습니다 |
| 필요한 선택 | 프레임에 사용할 재질을 선택하세요 |
| 다음 행동과 이유 | 선택한 재질을 실제 색과 버튼 조합에서 확인합니다 |
| 구체적인 버튼 | 이 방향으로 색과 서체 비교하기 |
| 완료 후 결과 | 선택한 방향의 시각 샘플이 준비됩니다 |
| 대안 | 아직 모르겠어요 또는 나중에 하기 |
| 현재 기준 | 어떤 프로젝트와 컨셉을 바탕으로 진행하는지 |

다음, 확인, 완료 같은 문구만으로 목적을 설명하지 않는다. 실제로 무엇을 하거나 어디로 이동하는지 버튼과 주변 문구에서 이해할 수 있게 한다.

진행 안내의 기본 추천 행동은 한 가지를 우선 보여 준다. 이는 편집기와 게임 등 제품 화면의 가능한 행동을 하나로 제한하는 규칙이 아니다. 현재 편집에 필요한 조작은 그대로 제공한다.

### 4.8 단계별 연결 표

| 현재 결과 또는 상태 | 기본 추천 행동 | 도착 위치와 이어받을 내용 |
|---|---|---|
| 제품 요약이 준비됨 | 사용자와 전체 목표 확인하기 | 해당 초안과 확인할 필드 |
| 고객의 의문이 미정임 | 고객이 망설릴 부분 정리하기 | 제품에 맞는 가설과 예시 |
| 레퍼런스 관찰 작성 완료 | 정리한 특징으로 방향 비교하기 | 사용자가 작성한 관찰과 내장 예시를 바탕으로 편집할 방향 카드 |
| 컨셉 방향 선택 | 이 방향의 색과 서체 구체화하기 | 선택한 방향과 유지할 특징 |
| 스타일 샘플 선택 | 화면별 적용 방식 정리하기 | 흐름과 화면 역할 및 스타일 범위 |
| 필요한 흐름이 정리됨 | 생성 전 브리프 점검하기 | 누락과 충돌 및 의도 요약 |
| 중요 충돌 발견 | 먼저 이 충돌 해결하기 | 관련 결정과 수정 후보 |
| 의도 확인 완료 | 통합 프롬프트 만들기 | 확정 결정과 첨부 자료 |
| 프롬프트가 준비됨 | 프롬프트와 참고 자료 가져가기 | 복사와 자료 묶음 및 외부 전달 안내 |
| 외부 제작을 기다리는 중 | 결과가 나왔어요 | 연결할 버전과 결과 등록 |
| 실제 결과 등록 | 이 결과가 의도와 맞는지 진단하기 | 고정 기준과 실제 결과 비교 |
| 진단에서 차이 발견 | 이 차이를 수정 계획으로 정리하기 | 문제와 근거 및 유지할 조건 |
| 수정 계획 선택 | 이 계획으로 수정 프롬프트 만들기 | 최신 통합 프롬프트 |
| 수정 결과 등록 | 이전 문제를 같은 기준으로 다시 확인하기 | 이전 판정과 새 관찰의 비교 |
| 해당 범위 확인 완료 | 전체 프롬프트와 결정 기록 보관하기 | 최종 자료와 남은 확인 범위 |

이 표는 고정 마법사 순서가 아니라 현재 상태에 따른 대표 규칙이다. 필요한 전제 정보가 없으면 가장 가까운 보완 작업으로 연결하고 완료 후 원래 목적 작업으로 돌아온다.

### 4.9 다음 행동 결정 규칙

추천 행동과 설명은 프로젝트 상태와 의존 관계, 미리 작성한 안내 문구로 결정한다. 다음 행동을 표시하기 위해 AI 호출을 요구하지 않는다.

1. 사용자가 직접 진행 중인 작업의 맥락을 유지한다.
2. 그 작업을 막는 필수 누락이나 실패가 있으면 복구 또는 최소 보완을 먼저 제안한다.
3. 검토가 필요한 중요 충돌과 사용자 미확인 의도를 연결한다.
4. 작업 결과가 준비됐으면 그 결과를 사용하는 다음 활동을 제안한다.
5. 필수 내용이 준비돼 있으면 반복 입력을 생략하고 프롬프트 또는 결과 진단으로 이어진다.
6. 전체 안내를 다시 선택한 경우 시작 경로와 미완료 필수 항목에서 이어갈 위치를 계산한다.

선택 항목을 미루더라도 진행 가능한 경우에는 보류와 이유를 기록하고 계속할 수 있게 한다. 필수 결정이 없으면 필요한 이유와 최소 질문 및 내장 예시를 고르는 경로를 보여 준다. 이유 없는 비활성 버튼으로 막지 않는다.

추천 행동은 행동 ID, 버튼 문구, 이유, 목적지 탭과 대상 항목, 필요한 조건, 완료 조건, 복귀할 원래 작업을 가진다. 필드 수정과 선택 이후 관련 추천을 갱신한다.

### 4.10 저장과 선택 및 이동의 연결

자동 저장과 사용자의 선택 확정은 구분한다. 내장 예시나 외부에서 가져온 제안이 저장됐다고 확정으로 처리하지 않는다.

사용자가 방향을 고르는 곳에는 이 방향을 선택하고 색 비교하기처럼 선택과 다음 결과가 드러나는 행동을 제공할 수 있다. 이때 수행되는 확정과 이동을 문구로 설명한다. 단순 저장 후 예상하지 못한 다른 탭으로 자동 이동시키지 않는다.

단계 전환 시 원본 입력과 선택, 작업 범위를 이어받고 대상 항목으로 직접 이동한다. 보완 작업으로 이동한 경우 원래 흐름으로 돌아오는 경로를 제공한다.

파일 처리나 자료 가져오기가 다른 탭을 보는 동안 완료되어도 현재 편집 화면을 강제로 바꾸지 않는다. 완료한 자료를 볼 수 있는 연결을 표시한다. 향후 외부 분석 결과도 같은 전환 원칙을 적용한다.

### 4.11 재접속과 중단 후 재개

프로젝트를 다시 열면 마지막 탭만 표시하지 않고 진행 중이던 작업과 남은 다음 행동을 보여 준다.

예시:

> 공주풍 방향은 선택했습니다. 아직 프레임에 적용할 재질을 비교하지 않았습니다.

이어서 프레임 재질 비교하기를 선택하면 저장된 후보와 선택 위치로 이동한다. 현재 작업이 이미 완료됐다면 상태를 재계산해 다음 미완료 작업을 안내한다. 보류한 항목은 보류 상태를 유지하고 매번 처음부터 반복 질문하지 않는다.

### 4.12 대기와 실패에서의 연결

- 원본 이미지 또는 크롭 파일 처리 중: 수행 작업과 완료 후 이어질 행동을 표시한다.
- 파일 저장이나 가져오기 완료: 실제 자료 확인과 후속 편집으로 연결한다.
- 파일 처리 실패: 입력을 유지하고 다시 선택 또는 재시도를 제공한다.
- 관찰하기 어려움: 색과 형태 및 재질의 비교 예시와 아직 모름을 제공한다.
- 의도 판단 어려움: 기준과 결과를 나란히 보며 항목별로 비교하도록 돕는다.
- 같은 문제가 반복됨: 원인 질문과 기존 기준을 다시 확인하는 작업으로 연결한다.

초기 버전에는 AI 요청 중, 모델 연결 실패, AI 응답 대기 같은 상태를 표시하지 않는다. 외부에서 사용자가 작업하는 동안은 결과 대기 상태로 유지하며 서비스가 직접 실행하거나 진행률을 아는 것처럼 표현하지 않는다.

### 4.13 외부 제작과 복귀

MVP는 외부 제작을 자동 실행하지 않으므로 내보내기를 막연한 완료 화면으로 끝내지 않는다.

외부 전달 화면은 다음을 설명한다.

1. 프롬프트를 외부 도구에 붙여 넣는다.
2. 첨부 목록에서 필요한 이미지와 에셋을 함께 전달한다.
3. 결과가 나오면 이 프로젝트에 등록해 의도와 스타일을 비교한다.

프롬프트 복사, 참고 자료 내려받기, 결과가 나왔어요를 명확히 제공한다. 실제 복사나 파일 생성이 실패했으면 성공으로 표시하지 않는다. 외부 제작이 완료됐는지 스스로 알 수 없는 경우 계속 결과 대기 상태로 둔다.

복귀 시 프롬프트 버전을 기본 연결하되 사용자가 다른 실행을 선택할 수 있게 한다. 결과 등록을 마치면 같은 화면에서 진단 실행으로 이어진다.

### 4.14 완료 후에도 이어지는 행동

해당 범위가 확인됐으면 확인한 결과, 보류된 부분과 기록된 자료를 보여 준다. 기본 후속 행동은 최종 자료 보관이며, 다른 화면 확장과 새 프로젝트는 선택 행동으로 제공한다. 추가 과제나 학습을 강제로 시작하지 않는다.

다른 화면으로 확장할 때에는 고객과 컨셉 및 공통 스타일을 이어받고 새로 필요한 흐름과 상태만 보완한다.

## 5 공통 가이드와 결정 모델

### 5.1 입력 필드의 기본 구조

모든 중요한 필드는 다음을 기록한다.

| 속성 | 설명 |
|---|---|
| 값 | 직접 입력하거나 예시와 외부 자료에서 선택한 내용 |
| 상태 | 미정, 제안, 확정, 제외 |
| 출처 | 사용자 직접 입력, 내장 예시, 사용자 레퍼런스 관찰, 직접 등록한 외부 자료와 제안 |
| 근거 | 왜 이 내용을 선택했는지 |
| 적용 범위 | 프로젝트 전체, 특정 흐름, 화면, 컴포넌트 또는 리소스 |
| 수정 이력 | 언제 무엇에서 바뀌었는지 |
| 재검토 표시 | 관련 상위 결정이 바뀌었는지 |

상태와 출처를 섞지 않는다. 내장 예시나 외부 도구에서 가져온 제안도 사용자가 확정할 수 있으며, 그 출처는 유지한다. 외부 자료가 AI 결과인지 사용자가 표시할 수 있지만 현재 서비스가 생성했다고 기록하지 않는다.

### 5.2 질문의 표시 방식

각 주요 질문은 아래 구성을 가진다.

- 쉬운 질문
- 필요한 이유 한 문장
- 현재 제품 유형에 맞는 예시
- 직접 작성, 예시 보고 고르기, 아직 모름
- 다른 결정에 미치는 영향

예시:

질문: 사용자는 이 서비스를 이용하고 무엇을 얻으면 만족할까요?  
이유: 전체 목표를 알아야 화면별 역할을 연결할 수 있습니다.  
사진 서비스 예시: 사진 네 장을 꾸며 저장하고 싶다.  
게임 예시: 직접 만든 거점을 키우며 새로운 지역을 탐험하고 싶다.

### 5.3 제안과 확정

- 내장 예시와 외부에서 가져온 결과는 기본적으로 제안 상태다.
- 사용자는 전체 제안 또는 개별 항목을 선택, 수정, 제외할 수 있다.
- 비교 가능한 내용은 항목별로 선택할 수 있다.
- 선택 이유는 간단한 문장이나 선택형 이유로 남길 수 있다.
- 이유 입력은 권장하되 모든 작은 선택에 강제하지 않는다.
- 충돌이 있는 제안을 확정하려면 충돌 내용을 먼저 보여 준다.
- 제외된 내용은 최종 프롬프트에 요구사항으로 포함하지 않는다.

### 5.4 모름과 건너뛰기의 연결

아직 모름을 선택하면 빈 필드에 그대로 남겨 두지 않는다. 직접 비교할 수 있는 내장 예시와 비교 선택지를 제공하고 선택 후 원래 작업을 이어가게 한다.

선택 입력을 건너뛰면 왜 보류했는지 기록할 수 있다. 필수 입력이 필요하면 최종 준비 상태와의 관계를 설명하며 최소한의 결정으로 이어지게 한다. 모름, 보류, 제외를 같은 상태로 취급하지 않는다.

## 6 프로젝트 설계 탭

### 6.1 하위 영역

제품 정의 / 사용자와 전체 경험 / 기능과 범위 / 콘텐츠 준비

### 6.2 제품 정의

| 필드 | 설명 | 필수 시점 |
|---|---|---|
| 제품 한 문장 | 무엇을 만드는지 | 최종 출력 |
| 제품 유형 | 게임, 제작 도구, 판매, 콘텐츠 등 | 최종 출력 |
| 주요 사용자 | 역할과 사용 상황 | 최종 출력 |
| 전체 목표 | 사용자에게 남길 결과나 경험 | 최종 출력 |
| 사용 환경 | 기기, 입력 방식, 언어 | 최종 출력 |
| 대표 사용 상황 | 언제 어떻게 사용하는지 | 권장 |
| 사업 모델 | 무료, 판매, 구독 등 | 관련 프로젝트만 |
| 차별점 | 이 제품에서 중요한 고유 요소 | 권장 |
| 확정 조건 | 반드시 유지할 기능과 제약 | 해당 내용이 있을 때 |

게임에 구매 흐름이나 결제를 필수로 요구하지 않는다. 판매 서비스에는 구매 대상과 구매 전 의문을, 작업 도구에는 수행 과제와 실패 시 부담을, 게임에는 플레이 동기와 반복 경험을 우선 질문한다.

### 6.3 사용자와 전체 경험

사용자 역할이 여러 개면 역할별 목표를 나눈다. 목표는 기능 이름만으로 작성하지 않게 예시를 제공한다.

- 기능 이름: 사진 편집
- 사용자 목표: 마음에 드는 네 장을 꾸며 저장한다
- 게임 기능: 건설
- 플레이 경험: 직접 만든 거점이 점점 발전하는 모습을 경험한다

### 6.4 기능과 범위

기능마다 목적, 사용자 행동, 필요한 정보, 우선순위, 관련 흐름을 기록한다.

우선순위는 이번 범위 / 후속 범위 / 미정으로 구분한다. 내장 예시나 외부 제안에 있는 회원가입, 결제, 공유 등은 자동으로 이번 범위에 추가하지 않는다.

### 6.5 콘텐츠 준비

콘텐츠와 리소스를 목록으로 관리한다.

| 필드 | 내용 |
|---|---|
| 종류 | 문구, 사진, 제품 화면, 일러스트, 게임 에셋, 아이콘, 데이터 |
| 용도 | 어느 화면에서 무엇을 설명하는지 |
| 확보 상태 | 보유, 제작 필요, 제공 예정, 미정 |
| 실제 내용 | 문구, 파일 또는 데이터 |
| 제작 조건 | 크기, 비율, 배경, 형식 등 필요한 조건 |
| 표시 상태 | 실제 자료, 임시 샘플, 제안 문구 |
| 연결 | 관련 화면, 스타일 규칙, 레퍼런스 |

실제 자료가 없으면 필요한 제작 계획을 남길 수 있다. 임시 샘플을 실제 고객 사례, 실제 기능 화면, 실제 성과로 표현하지 않는다.

### 6.6 수용 기준

- 자유로운 아이디어 문장으로 시작할 수 있다.
- 사용자 원문과 직접 정리한 항목 및 내장 예시의 출처를 구별할 수 있다.
- 게임 유형에는 반복 플레이 질문이, 사진 제작 도구에는 완성 결과 질문이 나타난다.
- 콘텐츠가 없는 프로젝트도 필요한 자료를 계획하며 진행할 수 있다.

### 6.7 기본 가이드 질문 카탈로그

질문을 한 화면에 모두 나열하지 않는다. 선택한 제품 유형과 입력 상태에 맞는 질문을 규칙으로 표시한다. 한 번에 보완을 요청하는 핵심 질문은 기본 세 개 이내로 제한하고, 내장 예시와 아직 모름을 함께 제공한다.

| ID | 쉬운 질문 | 답변이 정하는 것 | 모를 때의 지원 |
|---|---|---|---|
| Q01 | 어떤 것을 만들고 싶나요 | 제품의 한 문장과 유형 | 유형별 제품 설명 예시와 직접 수정 |
| Q02 | 누가 어떤 상황에서 쓰나요 | 사용자와 사용 환경 | 역할과 상황의 예시를 보고 선택 |
| Q03 | 이용한 뒤 무엇을 얻으면 만족할까요 | 전체 목표 | 제품 유형별 완성 경험 예시 |
| Q04 | 그 결과를 얻기 위해 무슨 일을 하나요 | 핵심 활동 | 제품 유형별 활동 목록에서 선택과 편집 |
| Q05 | 이 제품에서 특히 중요하거나 다른 점은 무엇인가요 | 시각적 주인공과 우선순위 | 내장 강조 방향 예시 비교 |
| Q06 | 사용자가 무엇을 이해하지 못하거나 망설릴까요 | 설명과 근거 및 복구 | 내장 의문 예시에서 선택하고 가설로 기록 |
| Q07 | 어떤 기능은 이번에 꼭 필요하고 어떤 것은 나중인가요 | 출력 범위 | 범위 선택 질문과 유형별 최소 예시 |
| Q08 | 실제로 가진 문구나 이미지 및 리소스가 있나요 | 콘텐츠 준비 상태 | 필요한 자료 목록으로 전환 |
| Q09 | 어느 화면에서 어떤 조작으로 사용하나요 | 기기와 입력 방식 | 플랫폼별 차이와 선택 예시 |
| Q10 | 어떤 느낌이면 좋고 어떤 느낌은 피하고 싶나요 | 감정과 컨셉의 기준 | 이미지 또는 대비되는 느낌의 쌍 제시 |
| Q11 | 이 이미지 전체가 좋나요 아니면 특정 부분인가요 | 레퍼런스 분석 모드 | 전체 느낌 분석을 기본 제안 |
| Q12 | 이미지의 어떤 특징을 어느 곳에 적용할까요 | 구체적 적용 결정 | 관찰 질문과 적용 문장 틀 제공 |
| Q13 | 두 방향 중 어느 쪽이 의도에 더 가깝나요 | 선택 컨셉 | 차이와 필요한 리소스를 쉬운 말로 설명 |
| Q14 | 색과 글자 및 재질은 화면에서 어떤 역할을 하나요 | 스타일 규칙 | 실제 한글과 컴포넌트 샘플 제공 |
| Q15 | 어떤 순서와 배치에서 내용을 보기 쉽나요 | 레이아웃과 정보 위계 | 같은 콘텐츠의 구성 후보를 비교 |
| Q16 | 어느 장면을 보면 이 방향이 맞는지 알 수 있을까요 | 대표 검토 대상 | 제품 유형별 대표 장면 예시 |
| Q17 | AI에게 이번에 무엇을 만들어 달라고 할까요 | 산출물과 실행 범위 | 전체 설계와 시안 및 코드의 차이 안내 |
| Q18 | 결과에서 무엇이 기대와 달랐나요 | 수정 지시와 학습 | 원본 기준과 결과를 나란히 비교 |

조건별 추가 질문:

- 판매 서비스: 무엇을 구매하고, 구매 전 어떤 근거와 조건을 확인해야 하는가.
- 게임: 무엇을 반복하며, 세계와 플레이어에게 어떤 변화가 남는가.
- 편집 도구: 원본과 편집 상태를 어떻게 유지하고, 실수를 어떻게 되돌리는가.
- 촬영 서비스: 촬영이 불가능하거나 다시 찍고 싶을 때 어떤 경로를 제공하는가.
- 계정이 필요한 제품: 로그인 전후 어떤 활동이 달라지는가. 계정 필요 여부 자체가 미정이면 확정 질문을 먼저 한다.

### 6.8 질문 응답의 진행 규칙

한 답변에 여러 내용을 쓴 경우 원문을 유지하고 관련 필드의 설명과 예시를 옆에서 제공한다. 사용자가 해당 문장을 직접 연결하거나 항목을 편집한다. 초기 버전에서 의미를 자동 추출했다고 표시하지 않는다. 이미 입력한 필드는 재사용하고 아직 모름을 선택하면 내장 예시와 비교 문장으로 연결한다.

필수 결정을 대신 정해 숨기지 않는다. 선택이 필요한 상태와 현재 단계에서 미정으로 두어도 되는 상태를 구분한다. 질문의 목적은 빈칸을 모두 채우는 것이 아니라 현재 설계와 출력에 필요한 판단을 돕는 것이다.


### 6.9 고객과 제공 가치 및 해소할 의문

최종 디자인 프롬프트를 만들기 전에 아래 맥락을 작성한다. 시작 단계에서 모두 알 필요는 없으며, 모르는 항목은 가설과 제안으로 구체화한 뒤 적용 여부를 확인한다.

| 항목 | 가이드 질문 | 필요한 설계 연결 |
|---|---|---|
| 주요 사용자 | 누가 어떤 상황에서 사용하는가 | 용어, 설명 수준, 조작과 환경 |
| 구매자 또는 의사결정자 | 누가 비용을 내거나 사용을 결정하는가 | 판단에 필요한 근거와 조건 |
| 구매 또는 제공 대상 | 사용자는 무엇을 구매하거나 어떤 결과를 얻는가 | 핵심 콘텐츠와 보여 줄 장면 |
| 원하는 변화 | 사용 전후에 무엇이 달라져야 하는가 | 전체 경험과 완료 조건 |
| 의문과 망설임 | 무엇을 이해하지 못하거나 걱정하는가 | 설명, 실제 증거, 피드백과 복구 |
| 사용할 수 있는 근거 | 그 의문에 실제로 답할 자료나 기능이 있는가 | 콘텐츠와 리소스 준비 |
| 적합한 분위기 | 선택한 분위기가 이 고객과 경험에 어떻게 어울리는가 | 컨셉의 선택 이유와 적용 범위 |

사용자와 구매자가 같지 않을 수 있으므로 별도 역할을 허용한다. 구매가 없는 제품에는 구매 대상을 억지로 만들지 않는다. 대신 제공 결과와 사용을 결정할 때의 의문을 기록한다. 게임의 과금이 미정이면 그 상태를 보존한다.

의문 항목은 조사로 확인한 내용, 사용자 가설, 내장 예시에서 선택한 내용과 직접 가져온 외부 제안을 구분한다. 가설과 예시를 실제 고객 조사 결과로 표현하지 않는다.

의문마다 다음 연결을 작성한다.

고객의 의문 → 답할 정보나 기능 → 보여 줄 실제 근거 → 해당 화면 → 적합한 표현 → 확인 기준

예시:

- 네컷 사진 서비스: 사진을 바꾸면 꾸민 내용이 사라질까 → 편집 유지와 실행 취소 → 실제 동작 또는 확인된 정책 → 선택과 꾸미기 화면 → 상태와 결과를 분명히 안내 → 교체와 복구를 실행해 확인.
- 리소스 판매: 내 작업에 사용할 수 있을까 → 규격과 사용 범위 → 실제 파일 정보와 조건 → 상품 상세 → 미리보기와 사양을 함께 제시 → 필요한 정보를 찾는지 확인.
- 생존 게임: 다음에 무엇을 할 수 있을까 → 상호작용과 제작 가능성 → 플레이 중의 표시와 피드백 → 월드와 제작 패널 → 탐험 분위기와 구별되는 행동 신호 → 실제 플레이에서 발견 가능한지 확인.

### 6.10 고객 맥락의 변경

고객, 제공 대상, 핵심 의문이 바뀌면 관련 기능과 콘텐츠, 분위기의 적합성, 화면별 정보 위계를 재검토 대상으로 표시한다. 전체 데이터를 자동 초기화하지 않고 영향받는 결정과 수정 후보를 보여 준다.

## 7 사용자 흐름 탭

### 7.1 구조

전체 목표 → 핵심 활동 → 사용자 흐름 → 화면 또는 상태 → 행동과 시스템 반응

사이트맵은 화면의 구성 관계를, 흐름은 활동 순서와 분기를 나타낸다. 두 정보를 연결하지만 같은 것으로 취급하지 않는다.

### 7.2 사용자 흐름

각 흐름은 아래 항목을 가진다.

- 흐름 이름과 연결된 사용자 목표
- 사용자 역할
- 시작 조건
- 주요 단계
- 선택 분기
- 반복 또는 되돌아가기
- 실패와 복구
- 완료 조건
- 관련 화면 또는 상태

목록 편집과 간단한 연결도 보기를 제공한다. MVP에서는 고급 자유 배치 캔버스를 필수로 구현하지 않는다.

### 7.3 화면 또는 상태

| 필드 | 내용 |
|---|---|
| 이름과 종류 | 페이지, 패널, 모달, 게임 상태, 모드 등 |
| 역할 | 전체 경험에서 맡는 일 |
| 진입 조건 | 어디에서 어떤 데이터로 들어오는지 |
| 정보 위계 | 먼저 확인할 내용과 보조 내용 |
| 가능한 행동 | 여러 행동과 상황별 우선순위 |
| 시스템 반응 | 행동 시 상태와 데이터 변화 |
| 다음 연결 | 다음 단계, 이전 단계, 반복 |
| 예외 처리 | 비어 있음, 실패, 권한, 취소 등 필요한 상태 |
| 데이터 유지 | 뒤로 이동하거나 실패했을 때 보존할 내용 |
| 연결 자료 | 콘텐츠, 리소스, 스타일과 레퍼런스 |

모든 화면에 버튼 하나만 두도록 강제하지 않는다. 게임과 편집기에서는 여러 행동이 공존한다. 모든 활동을 새 페이지로 분리하지 않는다.

### 7.4 가이드

제품 유형별 확인 질문과 분기 예시를 제공한다. 예: 카메라를 쓸 수 없을 때, 사진을 다시 선택할 때, 제작 재료가 부족할 때. 사용자가 해당 여부와 복구 방식을 선택한다. 미연결 단계와 완료 조건 누락은 데이터 관계로 점검하고, 정책의 적합성은 사용자 확인으로 남긴다.

### 7.5 수용 기준

- 반복 루프와 순차 완료 흐름을 모두 표현할 수 있다.
- 하나의 화면이 여러 흐름에 연결될 수 있다.
- 완료되지 않는 분기와 연결이 없는 화면을 안내한다.
- 서비스 전체 목표와 각 화면의 역할을 함께 확인할 수 있다.

## 8 레퍼런스 연구 탭

### 8.1 시작 방식

- 이미지 한 장의 전체 느낌이 좋다.
- 특정 부분이나 소재가 좋다.
- 여러 자료의 요소를 조합하고 싶다.
- 피하고 싶은 예시가 있다.

이미지 한 장으로 시작할 수 있다. 어떤 부분이 좋은지 반드시 사용자가 먼저 설명할 필요는 없다.

### 8.2 이미지 등록

MVP는 PNG, JPEG, WebP 업로드와 출처 URL 기록을 제공한다. URL만 저장한 상태를 이미지 분석 완료로 표시하지 않는다. 페이지에 접근할 수 없으면 이미지 파일 등록을 안내한다.

원본을 보존하고 표시용 이미지와 선택 영역을 별도로 만든다. 이미지에 출처, 사용자 메모, 역할을 기록한다. Pinterest 원본 창작자를 확인할 수 있으면 출처 정보에 함께 기록한다.

### 8.3 전체 느낌을 정리하는 관찰 가이드

사용자 초기 문구:

> 이 이미지의 전체적인 느낌이 마음에 든다. 내가 어떤 부분을 좋아하는지 아직 정확히 설명하기 어렵다.

초기 버전의 처리 순서:

1. 원본 이미지를 보여 주고 색, 형태, 재질, 글자와 구성을 한 항목씩 관찰하게 한다.
2. 예를 들어 넓은 연한 바탕과 작은 강한 포인트처럼 관계를 설명하는 내장 문장과 비교 예시를 제공한다.
3. 사용자가 실제 이미지에서 보이는 항목을 선택하거나 직접 작성한다.
4. 그 특징이 주는 느낌을 사용자 해석으로 기록한다.
5. 어떤 화면이나 리소스에 사용할지 적용 문장 틀에 연결한다.
6. 작성한 특징을 보며 컨셉 카드 두 개를 직접 구성하거나 내장 방향 예시를 복제해 비교한다.

내장 예시는 해당 이미지를 읽은 결과가 아니라 관찰을 돕는 자료임을 표시한다. 사용자 입력 없이 사진의 재질, 분위기, 서체나 서비스 적합성을 자동 판정하지 않는다.

전문 용어를 모르면 시각 예시와 쉬운 표현으로 선택할 수 있게 한다. 모르는 항목은 남겨 두고 먼저 아는 특징부터 적용할 수 있다.

향후 외부 연결이 추가되면 같은 관찰 항목의 초안을 전달받을 수 있으나, 초기 버전의 진행과 완료는 그 연결을 요구하지 않는다.

### 8.4 분석 항목

| 차원 | 관찰 대상 | 적용 후보 |
|---|---|---|
| 색의 관계 | 면적, 대비, 강조와 보조색의 관계 | 배경, 텍스트, 강조, 상태 |
| 형태 | 곡선, 각, 테두리, 장식 모티프 | 프레임, 버튼, 그래픽 |
| 재질 | 광택, 질감, 투명감과 깊이 | 이미지, 표면, 장식 |
| 글자 표현 | 굵기, 크기 차이, 곡선, 밀도 | 제목, 본문, 레이블 |
| 구성 | 정렬, 대칭, 중심, 여백, 겹침 | 화면과 이미지의 배치 |
| 밀도 | 정보와 장식의 양 | 화면별 표현 강도 |
| 이미지 언어 | 사진, 픽셀, 일러스트, 3D 등 | 리소스 제작 방식 |
| 정서 | 관찰을 바탕으로 해석한 느낌 | 프로젝트 컨셉 후보 |

사용자가 해석한 정서는 관찰 사실과 구분한다. 실제 확인하지 않은 서체명, 기능, 성과와 제작자의 의도를 확정적으로 기록하지 않도록 안내한다. 색은 직접 선택하거나 내장 팔레트에서 고를 수 있다. 이미지에서 값을 읽는 색상 도구를 제공하는 경우 픽셀의 색값과 의미 해석을 구분한다.

### 8.5 영역 지정 모드

사용자는 사각형 영역을 지정하고 아래 항목을 직접 작성하거나 내장 문장과 예시에서 선택한다.

- 무엇을 참고하는가: 색, 재질, 형태, 구성, 서체, 인터랙션 아이디어 등
- 선택 영역에서 관찰한 특징
- 왜 좋은가
- 적용할 화면, 컴포넌트 또는 리소스
- 유지할 특징
- 바꿔야 할 특징
- 참고하지 않을 요소
- 시각 원리 참고인지 실제 파일 사용인지

영역은 원본 크기에 대한 0~1 비율 좌표로 저장한다. 크롭 이미지와 원본을 함께 확인할 수 있다.

### 8.6 레퍼런스 적용 문장

최종 적용은 다음 구조로 저장한다.

> 레퍼런스 R1의 영역 A2에서 보이는 [관찰 특징]을 [제품 목적]을 위해 [적용 대상]에 사용한다. [유지할 관계]는 유지하고, [변경 요소]는 프로젝트에 맞춰 조정한다.

예시:

> R1의 하단 장식에서 보이는 리본과 진주의 재질 대비를 네컷 사진의 공주풍 인상을 위해 프레임과 스티커에 적용한다. 사진을 둘러싸는 구성은 유지하고, 장식 크기는 얼굴을 가리지 않게 조정한다.

이 문장은 사용자가 확인하면 확정 결정이 된다.

### 8.7 자료 분리

- 관찰: 이미지에 직접 보이는 내용
- 해석: 그 특징이 만드는 인상에 대한 추정
- 제안: 서비스에 적용하는 방법
- 결정: 사용자가 선택한 적용 방식

외부 이미지나 문서 안의 문구는 분석 자료로 처리한다. 실행 지시로 편입하지 않는다.

### 8.8 수용 기준

- 이미지 한 장과 좋다는 메모로 시작해 쉬운 관찰 질문과 예시를 따라 분석 초안을 직접 완성할 수 있다.
- 실제 사용자 작성이나 등록 자료 없이 내장 예시를 해당 이미지의 분석 결과로 표시하지 않는다.
- 관찰과 해석 및 제안이 구분되어 보인다.
- 원본과 선택 영역, 적용 대상을 함께 확인할 수 있다.
- 이미지가 없는 상태에서 이미지의 색이나 재질을 만들어 내지 않는다.
- 하나의 레퍼런스를 프로젝트 전체 또는 특정 리소스에만 적용할 수 있다.

## 9 컨셉 탐색 탭

### 9.1 두 가지 작업 모드

A. 방향 찾기: 분위기, 색, 컨셉이 아직 미정인 사용자  
B. 정한 컨셉 구체화: 방향을 이미 정한 사용자

두 모드는 같은 결정 데이터에 연결한다. 정한 컨셉을 다시 탐색하거나 제안에서 일부만 가져올 수 있다.

### 9.2 방향 찾기

사용자 입력:

- 원하는 느낌 또는 설명하기 어려운 취향
- 참고 이미지
- 반드시 유지할 조건
- 피하고 싶은 인상
- 제품의 전체 경험

모르는 항목은 비워 둘 수 있다. 비교할 방향 카드 두 칸을 기본 제공하고, 사용자가 직접 작성하거나 내장 컨셉 예시를 복제해 편집한다. 내장 예시는 제품 유형과 사용자가 고른 취향에 따라 필터링하며 이미지에서 자동 도출한 맞춤 결과로 표시하지 않는다. 한 방향이 이미 정해졌으면 억지로 두 안을 채우지 않아도 된다.

### 9.3 방향 카드

각 방향은 아래 내용을 같은 순서로 보여 준다.

1. 컨셉 이름과 핵심 문장
2. 사용자에게 전달할 경험
3. 가장 크게 보여 줄 대상
4. 색의 관계
5. 서체의 역할
6. 이미지와 재질
7. 구성과 정보 밀도
8. 화면별 적용 강도
9. 필요한 리소스와 제작 부담
10. 원본 레퍼런스에서 유지하거나 다르게 해석한 부분
11. 확인이 필요한 가정

대안은 색만 바꾼 변형에 그치지 않게 한다. 시각적 주인공, 구성, 타이포그래피, 리소스 방식 중 최소 두 항목에서 의미 있는 차이를 설명한다.

### 9.4 시각 샘플

MVP는 선택을 돕는 작은 샘플을 제공한다.

- 배경과 텍스트 및 강조색의 실제 조합
- 실제 한글 제목과 본문
- 버튼과 선택 상태
- 프레임 또는 패널
- 레퍼런스의 연결된 소재
- 대표 장면의 배치 설명 또는 간단한 구성 스케치

게임 프로젝트에는 아이템 슬롯과 상태 표시, 사진 서비스에는 사진 프레임과 편집 도구처럼 제품 유형에 맞는 샘플을 제공한다. 샘플은 컨셉을 비교하기 위한 것이며 최종 아트나 완성 UI로 표시하지 않는다.

### 9.5 정한 컨셉 구체화

사용자는 픽셀아트, 모던, 코튼, 공주풍 Y2K 같은 단어를 입력할 수 있다. 서비스는 내장 스타일 설명과 질문을 제공해 사용자가 아래 항목을 구체화하도록 돕는다.

형태 / 서체 / 이미지 / 재질 / 색 관계 / 밀도 / 모션 / 적용 대상

모호한 용어는 뜻을 직접 설명하거나 내장 예시에서 선택하게 한다. 코튼을 천 질감과 부드러운 촉감으로 정의하는 예시는 후보임을 보여 주고 사용자가 뜻을 확인한다. 단어 하나로 전체 UI를 자동 확정하지 않는다.

### 9.6 선택 방식

- 방향 전체 선택
- 방향의 일부 요소 선택
- 선택한 요소로 새 조합 만들기
- 선택한 항목 직접 수정
- 둘 다 맞지 않음과 이유 기록

서로 다른 요소를 조합하면 팔레트 역할과 적용 범위 같은 명시적 값의 충돌을 점검하고, 인상과 일관성은 비교 질문으로 사용자가 확인한다. 새 조합의 샘플을 확인한 뒤 확정한다.

## 10 스타일과 리소스 탭

### 10.1 하위 영역

색 / 타이포그래피 / 레이아웃과 컴포넌트 / 형태와 표면 / 이미지와 재질 / 모션 / 리소스 계획

### 10.2 규칙의 형식

스타일은 값, 역할, 적용 범위, 이유, 예외를 가진다. 모든 규칙을 전역에 적용하지 않는다.

예시:

| 항목 | 값과 역할 | 적용 범위 | 이유와 예외 |
|---|---|---|---|
| 픽셀 표현 | 제한된 색과 선명한 픽셀 형태 | 월드와 아이템 및 브랜드 그래픽 | 본문은 실제 한글 가독성을 별도 검토 |
| 진한 핑크 | 선택 상태와 주요 행동 강조 | 버튼과 선택 테두리 | 모든 넓은 면에 반복하지 않음 |
| 천 질감 | 부드러운 재질감 | 배경 이미지와 브랜드 리소스 | 텍스트 위에서는 읽기 방해 여부 검토 |

### 10.3 색 가이드

- 색상 이름 선택에서 역할 지정까지 연결한다.
- 배경, 본문, 보조 정보, 강조, 선택, 오류 등 필요한 역할을 정한다.
- 색을 모르면 선택한 내장 컨셉에 연결된 팔레트 예시를 비교하고 직접 수정한다. 팔레트는 이미지의 자동 해석 결과가 아니다.
- 실제 문구와 컴포넌트 위에서 조합을 미리 본다.
- 화면에서 텍스트 대비와 선택 구분을 확인할 수 있게 한다.
- 상태 의미를 색에만 의존하는 경우 보조 레이블이나 형태를 제안한다.
- 색상 값과 선택 이유를 함께 저장한다.

### 10.4 타이포그래피 가이드

제목, 본문, 숫자, 레이블의 역할을 먼저 정하고 서체와 크기 및 간격을 연결한다. 한글 프로젝트는 실제 한글 콘텐츠로 샘플을 제공한다. 특정 서체가 AI스럽다는 이유만으로 금지하지 않는다.

사용자나 외부 자료가 서체를 추정한 경우 확정 이름과 구분한다. 내장 서체 예시는 샘플로 표시하며 원본 이미지의 글꼴을 자동 식별한 것으로 표현하지 않는다. 실제 사용 파일과 로딩 조건은 리소스 계획에 연결한다.

### 10.5 리소스 계획

| 필드 | 내용 |
|---|---|
| 리소스 이름과 종류 | 프레임, 배경, 스프라이트, 타일, 아이콘 등 |
| 용도 | 보여 줄 내용과 사용할 화면 |
| 제작 방식 | 기존 파일, 직접 제작, 구매 검토, 생성 요청 |
| 기준 자료 | 레퍼런스와 기준 에셋 |
| 제작 규칙 | 비율, 크기, 재질, 광원, 팔레트 등 |
| 확보 상태 | 보유, 제작 필요, 확인 필요 |
| 출처와 사용 정보 | 원본과 실제 에셋 사용 조건 기록 |
| 검토 방법 | 프로젝트에서 확인할 사항 |

게임은 타일 규격, 캐릭터 비율, 외곽선, 명암과 애니메이션 일관성을 질문한다. 사진 서비스는 프레임, 스티커, 사진 비율, 최종 결과물과 편집 미리보기의 관계를 질문한다.

### 10.6 수용 기준

- 전체 분위기와 기능 UI의 적용 범위를 다르게 설정할 수 있다.
- 색을 모르는 상태에서 역할이 있는 조합을 선택할 수 있다.
- 선택한 소재를 특정 리소스에만 연결할 수 있다.
- 보유하지 않은 에셋이 보유한 파일처럼 프롬프트에 들어가지 않는다.

### 10.7 레이아웃과 컴포넌트 가이드

색과 소재에 더해 정보의 배치와 실제 상태를 구체화한다.

- 주요 콘텐츠와 보조 콘텐츠의 관계
- 화면의 영역 구분과 읽는 순서
- 제목과 이미지 및 작업 영역의 비율
- 정렬, 여백과 반복 간격의 기준
- 모바일에서의 재배치와 축소 및 숨김 기준
- 필요한 컴포넌트와 기본, 선택, 비활성, 로딩 및 오류 상태
- 기능을 식별하는 레이블과 조작 결과의 피드백
- 키보드, 포커스와 터치 등 선택한 사용 환경에서 필요한 조작 조건

픽셀 게임에는 월드, HUD, 패널과 상호작용 표시의 관계를, 사진 서비스에는 사진 미리보기, 편집 도구와 단계 이동의 관계를 우선 설명한다. 모든 제품을 같은 카드 그리드로 변환하지 않는다.

초기 탐색에서는 구성 관계를 먼저 고른다. 방향이 정해진 뒤 크기와 간격을 구체화할 수 있다. 값을 지정하면 역할과 적용 범위를 함께 기록한다.


### 10.8 서비스와 분위기의 적합성 매핑

픽셀아트, 모던, 코튼 등의 이름과 함께 전달하려는 정서, 시각적 근거, 적용 대상, 서비스에 적합한 이유를 작성한다. 스타일이 적용됐는지와 서비스 목적에 적합한지는 서로 다른 항목으로 진단한다.

| 주된 분위기의 예 | 구체화할 내용 | 서비스 목적과 연결해 확인할 내용 |
|---|---|---|
| 픽셀아트 | 픽셀 형태, 기준 에셋, 팔레트, 외곽선과 명암 | 게임 세계와 조작 정보의 구분, 아이템 식별과 한글 읽기 |
| 모던 | 정렬, 타이포그래피 위계, 여백, 대비와 피드백 | 고객이 중요 정보를 비교하고 주요 작업을 수행하는지 |
| 코튼 | 사용자가 의도한 천의 결, 부드러운 형태와 빛 등 | 재질이 제품 경험을 전달하며 정보와 상태를 방해하지 않는지 |
| 공주풍 Y2K | 핑크의 역할, 리본과 진주, 광택과 장식 구성 | 사진이 주인공으로 보이고 촬영 및 편집을 이해할 수 있는지 |

이 표는 제안 예시이며 스타일의 고정 정의가 아니다. 코튼처럼 뜻이 모호한 단어는 사용자의 의도를 확인한다. 익숙한 스타일 이름만으로 고객층이나 기능을 추정해 확정하지 않는다.

확정할 스타일마다 다음을 저장한다.

- 전달하려는 인상과 유지할 핵심 특징
- 색, 서체, 형태, 소재, 구성과 모션의 표현 규칙
- 프로젝트 전체와 화면 및 컴포넌트별 적용 범위
- 고객과 제공 가치 및 핵심 활동에 맞는 이유
- 조정 가능한 요소와 유지할 요소
- 실제 결과에서 확인할 수 있는 관찰 기준
- 비교할 레퍼런스 또는 확인한 시각 샘플

예시 기준:

- 좋은 기준: 꾸미기 화면의 프레임에 리본과 진주 재질 대비가 보이고, 사진 속 얼굴과 편집 도구가 구별된다.
- 보완이 필요한 기준: 핑크색이면 공주풍 Y2K가 적용된 것이다.

색상이나 아이콘 하나의 존재만으로 전체 분위기가 적용됐다고 판정하지 않는다.

## 11 디자인 브리프 탭

### 11.1 역할

여러 탭의 결정을 읽기 쉬운 통합 설계안으로 보여 준다. 원본 데이터와 연결된 요약이며 별도의 복제 데이터로 관리하지 않는다.

구성:

제품과 사용자 / 전체 경험 / 기능과 흐름 / 화면과 상태 / 콘텐츠 / 선택한 컨셉 / 스타일과 적용 범위 / 레퍼런스 적용 / 리소스 계획 / 미정과 가정 / 검토 기준

### 11.2 누락 확인

출력 목적에 필요한 항목과 미정 항목을 구분한다.

최종 통합 프롬프트의 최소 조건:

- 제품 유형과 설명
- 주요 사용자와 전체 경험
- 구매자 또는 의사결정자와 구매 또는 제공 대상의 해당 여부
- 고객의 핵심 의문과 답할 정보 및 근거 또는 확인할 가설
- 선택한 분위기가 고객과 서비스에 적합한 이유
- 출력 대상과 범위
- 주요 사용 환경
- 이번 범위의 핵심 기능과 최소 한 개의 흐름
- 필요한 화면 또는 상태와 역할
- 선택한 시각 방향 또는 확인한 직접 작성 규칙
- 구체적인 적용 규칙
- 사용할 콘텐츠와 필요한 리소스의 상태
- 요구사항 간 미해결 중요 충돌이 없음

레퍼런스 이미지는 필수가 아니다. 직접 작성한 시각 규칙으로도 생성할 수 있다. 기획 단계에 실제 에셋이 없어도 제작 계획과 미정 상태를 명시하면 진행할 수 있다.

### 11.3 충돌 확인

다음 유형을 구분한다.

- 기능과 흐름 충돌
- 스타일 규칙 간 충돌
- 레퍼런스 적용 대상 충돌
- 보유 자료와 제작 요구의 불일치
- 확정 요구와 제안의 불일치
- 선택한 출력 범위와 요구사항 범위의 불일치

충돌 항목은 관련 결정, 문제 설명, 영향, 해결 후보, 사용자 선택을 가진다.

예시:

> 모든 설명에 작은 픽셀 서체를 적용한다는 규칙과 긴 한글 도움말을 쉽게 읽게 한다는 요구가 충돌할 수 있습니다. 제목과 짧은 레이블에 픽셀 표현을 적용하고 본문을 분리하는 안을 검토하세요.

프로그램이 사용자 요구를 조용히 변경하지 않는다. 의미나 취향에 관한 충돌은 내장 질문으로 사용자가 점검하고, 자동 점검은 누락·참조·버전·명시적 값의 충돌 범위로 한정한다.

### 11.4 상태 표시

- 초안 생성 가능: 미정 내용을 명시한 설계 초안
- 최종 생성 가능: 필수 정보, 선택, 중요 충돌 검토와 생성 전 사용자 의도 확인이 완료됨
- 재검토 필요: 관련 원본이 바뀌었거나 참조 자료가 누락됨

완성은 지시문이 실행에 필요한 맥락을 갖췄다는 뜻이다. 디자인 품질의 자동 보증을 의미하지 않는다.

### 11.5 생성 전 의도와 적합성 진단

프롬프트 생성 전에 프로그램이 누락과 연결 및 명시적 충돌을 점검하고 사용자가 가이드 질문으로 의미와 적합성을 확인한다. AI 판정을 요구하지 않는다. 이 단계는 실제 디자인 결과의 검증을 대체하지 않는다.

검토 항목:

1. 고객과 제공 결과를 정확히 이해했는가.
2. 고객의 의문을 관련 화면과 실제 정보 또는 기능으로 연결했는가.
3. 전체 행동과 화면의 역할이 연결되는가.
4. 주된 분위기와 스타일이 서비스의 경험에 적합한가.
5. 레퍼런스에서 적용할 특징과 범위가 구체적인가.
6. 미정과 가정 및 확인하지 못한 근거가 구별되는가.

사용자에게 서비스 목표, 주된 분위기, 중요한 적용 특징, 대표 화면의 역할을 짧은 요약으로 보여 준다. 사용자 선택은 의도와 맞음 / 일부 수정 / 방향 다시 검토다. 프로그램이나 외부에서 가져온 피드백이 사용자 대신 의도 확인을 완료하지 않는다.

일부 수정이면 관련 필드와 제안을 편집하고 다시 점검한다. 방향 다시 검토면 기존 입력을 유지한 채 컨셉 탐색과 관련 레퍼런스로 이동한다. 모든 미정 항목을 막지는 않되 이번 출력의 목적을 결정할 핵심 의도가 미확인인 경우 최종 프롬프트 준비 완료로 표시하지 않는다.

### 11.6 생성 준비와 결과 확인의 구분

프롬프트 준비 상태와 실제 디자인 확인 상태를 별도 관리한다.

- 프롬프트 준비 완료: 생성에 필요한 맥락, 선택과 충돌 검토 및 사용자 의도 확인이 완료됨.
- 결과 대기: 프롬프트는 내보냈지만 실제 결과를 아직 받지 못함.
- 진단 또는 수정 중: 결과를 기준과 대조하고 수정 중임.
- 해당 범위 확인 완료: 요청한 검토 범위에서 증거와 사용자 확인이 확보됨.

프롬프트를 내보낸 것만으로 원하는 디자인이 구현됐다고 표시하지 않는다.

## 12 프롬프트 스튜디오 탭

### 12.1 기본 산출물

기본 버튼은 완성된 디자인 프롬프트 만들기다. 내부 분석 단계를 여러 개의 필수 프롬프트로 사용자에게 떠넘기지 않는다.

최종 프롬프트는 구조화된 하나의 문서로 제공한다. 범용 Markdown을 기본으로 하고 복사와 파일 내보내기를 지원한다.

외부 AI의 분석과 자가 점검을 요청하는 문장이 출력 프롬프트에 포함될 수 있다. 이는 사용자가 별도 도구에서 실행할 지시문이며, 현재 가이드 서비스가 그 AI를 호출하거나 피드백을 수신하는 기능은 아니다.

### 12.2 출력 목적

- 서비스 전체 UI UX 설계
- 특정 흐름 또는 화면 설계
- 기존 디자인 조정
- 리소스 제작 요청

첫 기본값은 서비스 전체 UI UX 설계다. 특정 화면을 선택해도 전체 서비스의 목표와 관련 흐름을 필요한 범위로 포함한다.

산출 형식도 함께 선택한다.

- UI UX 설계 문서
- 편집 가능한 화면 시안
- 코드로 구현한 UI
- 시각 방향 확인용 이미지
- 리소스 제작 지시

코드 구현을 선택하면 알려진 기술 환경을 입력받고 미정이면 별도로 표시한다. 이미지 시안을 선택하면 이미지가 표현할 수 있는 시각적 장면과 추후 구현할 동작을 구분한다. 특정 도구에서 사용할 기능과 실제 첨부 방식은 내보내기 단계에서 확인한다.


### 12.3 입력 계층

| 계층 | 내용 |
|---|---|
| 공통 작업 기준 | 사실과 가정 구분, 실제 콘텐츠, 검토 방식 등 |
| 작업 절차 | 분석, 설계, 제작, 검토에 필요한 반복 절차 |
| 프로젝트 맥락 | 제품, 사용자, 전체 목표, 기능과 흐름 |
| 시각 결정 | 선택한 컨셉과 스타일 규칙 |
| 레퍼런스 적용 | 관찰 특징, 적용 대상, 유지와 조정 |
| 현재 작업 | 산출물, 범위, 환경, 완료 기준 |

공통 기준은 설정에서 편집하고 버전으로 관리한다. 프로젝트별 예외를 기록할 수 있다.

스킬 이름을 적는 것과 스킬을 실제 실행 환경에 제공하는 것은 다르다. MVP의 스킬 연결은 사용자가 등록한 작업 절차와 이름을 출력에 참조하는 기능으로 한정한다. 설치와 실행을 자동 보장하지 않는다.

### 12.4 앱 내부 조정 순서

1. 사용자가 명시적으로 확정한 요구
2. 프로젝트에서 선택한 디자인 규칙
3. 현재 작업의 절차와 산출물 조건
4. 컨셉 프리셋의 기본값
5. 레퍼런스에서 추정한 특성

이 순서는 디자인 자료 조정을 위한 내부 기준이다. 외부 모델의 시스템 지침과 실행 권한을 변경하지 않는다. 요구 간 충돌이 남으면 우선순위만으로 숨기지 않고 검토 대상으로 표시한다.

### 12.5 생성 처리

1. 현재 프로젝트의 결정과 출력 범위를 읽는다.
2. 제외 항목과 확인되지 않은 제안을 걸러 낸다.
3. 관련 참조와 첨부 파일의 존재를 확인한다.
4. 누락과 충돌, 고객 맥락과 분위기의 적합성을 점검한다.
5. 서비스 목표와 디자인 방향의 요약을 사용자가 확인한다.
6. 확정 내용과 명시적으로 허용한 가정을 템플릿에 조립한다.
7. 내장 문장과 사용자 입력을 템플릿으로 조립하고 원본 결정과의 연결을 검증한다. 문장 정리를 위한 AI 호출은 수행하지 않는다.
8. 입력 결정과 프롬프트 문단을 연결한다.
9. 생성 후 자가 진단 기준과 수정 및 재검토 절차를 포함한다.
10. 입력 버전과 템플릿 버전을 스냅샷으로 저장한다.
11. 미리보기와 내보내기를 제공하고 실제 결과는 대기 상태로 둔다.

프롬프트 조립은 프로그램이 수행한다. 동일한 확정 입력과 템플릿 버전은 동일한 기본 조립문을 재현한다. AI 없이도 초안과 최종 통합 프롬프트, 수정 통합본을 모두 만들 수 있어야 한다.

### 12.6 프롬프트의 필수 구성

1. 작업의 목적과 산출물
2. 제품과 주요 사용자 및 구매자 또는 의사결정자
3. 구매 또는 제공 대상과 고객의 핵심 의문 및 답할 정보
4. 전체 경험과 핵심 활동
5. 기능 범위와 전체 흐름
6. 화면 또는 상태별 역할
7. 선택한 디자인 컨셉
8. 색, 서체, 형태, 이미지, 재질과 모션 규칙
9. 레퍼런스별 구체적 적용 지시
10. 실제 콘텐츠와 리소스 사용 또는 제작 계획
11. 주요 상호작용, 반응형과 필요한 예외
12. 유지할 조건과 미정 내용의 취급
13. 생성 후 실제 결과를 기준과 대조할 자가 진단 기준
14. 의도 및 스타일 불일치 시 수정과 재검토 절차

제품에 필요 없는 항목은 억지로 채우지 않는다. 예를 들어 게임에는 세계와 HUD 및 반복 플레이를 포함하고, 랜딩 페이지의 히어로·가격표 구조를 자동 삽입하지 않는다.

### 12.6.1 출력 대상 서비스의 자연스러운 연결

통합 프롬프트에는 대상 제품의 주요 진입과 상태 전환에서 사용자가 가능한 행동과 결과를 이해하도록 설계하는 기준을 포함한다.

- 시작, 완료, 빈 상태, 실패와 대기에서 현재 상황과 가능한 다음 행동을 제시한다.
- 단계 이동과 뒤로 가기 및 복구에서 필요한 입력과 선택을 유지한다.
- 버튼은 실제 행동과 이어질 결과를 이해할 수 있게 표현한다.
- 제공하지 않는 자동 실행이나 저장 및 복구를 있는 것처럼 안내하지 않는다.

모든 제품에 선형 마법사를 강제하지 않는다. 편집 도구에는 현재 상태와 가능한 조작을, 샌드박스 게임에는 상호작용 가능성과 피드백을 제공해 선택의 자유를 유지한다.


### 12.7 생성 문장 규칙

모호한 표현은 구체적인 관계와 적용 위치로 보완한다.

| 입력 | 출력에 필요한 보완 |
|---|---|
| 이 분위기로 만들어 줘 | 관찰 특징과 전달할 인상, 적용 대상 |
| 프리미엄하게 | 표현하려는 신뢰와 필요한 근거, 정보와 시각 위계 |
| 미니멀하게 | 유지할 정보와 생략할 장식, 읽는 순서 |
| 픽셀로 | 월드와 그래픽 및 UI의 적용 범위와 리소스 기준 |
| 리본을 참고 | 형태, 재질, 배치 관계와 사용할 프레임 또는 그래픽 |
| 더 예쁘게 | 현재 문제와 변경 대상 및 유지할 조건 |

레이아웃과 기능이 이미지에서 관찰되지 않았다면 서비스 목적에 따른 설계 제안으로 표현한다. 실제 성과, 고객 증언, 가격, 기능 지원을 만들어 넣지 않는다.

### 12.8 미리보기와 추적

각 주요 문단에서 원본 결정을 확인할 수 있다. 사용자가 디자인 브리프를 수정하면 관련 프롬프트 문단이 변경되었음을 보여 준다.

프롬프트만 직접 수정한 내용은 덮어쓰지 않는다. 별도 사용자 추가 지시로 저장하고 재생성 시 포함 여부와 충돌을 확인한다. 구조화된 데이터와 어긋난 수정은 사용자에게 알려 준다.

### 12.9 내보내기

- 통합 프롬프트 복사
- 통합 프롬프트 Markdown 파일
- 프로젝트 데이터 JSON 백업
- 선택 시 참고 자료 묶음 ZIP

자료 묶음에는 통합 프롬프트, 레퍼런스 원본과 크롭 이미지, 참조 목록, 실제 전달할 에셋을 포함한다. 파일 이름만 적고 이미지가 전달된 것으로 표시하지 않는다.

출력 미리보기에서 다음을 구분한다.

- 텍스트에 포함됨
- 파일로 첨부할 자료
- 외부 도구에서 별도 제공할 자료
- 아직 확보하지 못한 자료

### 12.10 스냅샷

프롬프트 스냅샷에는 프로젝트 버전, 확정 결정 ID와 버전, 레퍼런스 파일 식별값, 공통 기준 버전, 템플릿 버전, 선택한 출력 범위, 생성 시점을 저장한다.

사용자가 외부 실행의 도구나 모델 정보를 직접 남긴 경우 출처 메모로 보관할 수 있다. 현재 서비스의 모델 선택이나 실행 설정으로 취급하지 않는다. 기록은 외부 실행의 맥락을 추적하는 용도다.

### 12.11 출력 프롬프트의 필수 진단 및 수정 지시

다음 취지의 지시를 프로젝트의 실제 기준으로 구체화해 통합 프롬프트에 포함한다.

~~~text
설계와 결과를 다음 순서로 점검한다.

생성 전에는 고객 또는 사용자, 구매하거나 얻는 대상,
해소해야 할 핵심 의문과 전체 경험을 요약한다.
선택한 주된 분위기와 스타일이 그 목적에 어떻게 연결되는지 설명한다.
확인하지 않은 사용자 의도와 정책은 확정 사실로 표현하지 않는다.

생성 후에는 실제 산출물을 확정한 의도와 스타일 규칙에 대조한다.
각 항목에 기대한 표현, 실제 관찰, 확인한 화면 또는 영역,
일치 여부와 수정 필요성을 기록한다.
자료가 없거나 직접 확인할 수 없으면 확인 불가로 표시한다.

분위기를 스타일 이름이나 색상 하나로 판단하지 않는다.
색의 관계, 서체, 형태, 소재와 배치의 적용 범위를 함께 점검한다.
고객이 필요한 정보를 이해하고 활동할 수 있는지도 별도로 확인한다.

불일치가 있으면 원인과 수정 범위 및 유지할 조건을 정한다.
수정 후 같은 기준으로 다시 비교하고 이전에 맞았던 항목도 확인한다.
수정본과 관찰 근거 없이 해결됐다고 선언하지 않는다.

사용자가 의도를 바꾸면 기준의 새 버전을 기록한다.
관찰할 수 없는 동작은 별도의 실행 확인 대상으로 남긴다.
~~~

외부 도구가 이 지시를 따랐다고 해서 서비스의 검토 상태를 자동 완료하지 않는다. 실제 결과와 진단 기록을 받아 확인하는 절차를 유지한다.

기본 출력은 매 회차 전체 맥락과 최신 수정 의도가 반영된 하나의 통합 프롬프트다. 변경 요약이나 범위가 좁은 수정 지시를 추가로 제공할 수 있으나, 서로 충돌하는 지시를 뒤에 계속 덧붙이는 방식으로 관리하지 않는다.

## 13 자가 진단과 수정 탭

### 13.1 목적과 필수 반복 흐름

실제 결과가 사용자의 의도, 고객의 목적과 선택한 스타일을 충족하는지 확인하고, 어긋난 경우 수정과 재검토를 반복한다. 이 절차는 MVP 필수 흐름이다.

가이드에 따른 의도 확인 → 템플릿으로 프롬프트 조립 → 사용자가 외부에서 제작 → 결과 직접 등록 → 기준표로 사용자 자가 진단 → 수정 내용 작성 → 수정 프롬프트 조립 → 수정 결과 등록 → 같은 기준으로 재검토

요청한 범위에서 기준을 충족하고 사용자가 확인하면 해당 범위 확인 완료로 표시한다. 프롬프트 조립과 수정 문서 저장 또는 외부 결과의 성공 문구만으로 완료하지 않는다.

### 13.1.1 AI 없는 자가 진단 방식

프로그램은 비교할 기준, 원본과 결과 이미지, 관찰 질문과 판정 선택지를 보여 준다. 사용자가 일치·부분 일치·불일치·확인 불가·해당 없음을 선택하고 근거와 수정할 영역을 남긴다.

불일치 항목에는 기대한 표현, 실제 차이, 바꿀 대상과 유지할 부분을 작성하는 틀을 제공한다. 선택한 내용을 수정 프롬프트에 연결하고 새 결과에서 같은 항목을 다시 보여 준다.

원인 분류는 내장 질문과 예시에서 사용자가 선택한다. 프로그램이 이미지를 보지 않고 스타일 적용 여부나 원인을 진단한 것처럼 표시하지 않는다. 외부 피드백을 직접 붙여 넣을 수 있으나 선택 입력이며 자기 점검과 완료 조건을 대신하지 않는다.

### 13.2 입력과 검토 기준 고정

진단 회차를 시작할 때 기준 스냅샷을 만든다.

- 제품과 고객 및 전체 경험
- 구매 또는 제공 대상과 해소할 의문
- 사용자에게 확인받은 의도
- 선택한 주된 분위기와 구체적인 스타일 규칙
- 레퍼런스와 영역 및 적용 범위
- 화면 역할과 필요한 활동
- 사용할 실제 콘텐츠와 에셋 상태
- 이번 검토 범위와 중요한 조건

이 기준을 연결된 프롬프트 버전과 함께 저장한다. 진단 결과를 좋아 보이게 만들기 위해 기준을 자동 변경하지 않는다. 사용자 의도가 바뀐 경우에는 기준 변경 이유를 기록하고 새 버전에서 진단한다.

### 13.3 실제 결과 등록

MVP는 외부 도구에서 만든 결과의 이미지와 메모를 사용자가 등록한다. 다음을 지정한다.

- 연결할 프로젝트와 프롬프트 버전
- 결과 버전과 생성에 사용한 지시
- 화면이나 상태의 이름과 사용 환경
- 확인할 이미지 또는 직접 확인한 실행 기록
- 사용자가 느끼는 문제와 원하는 변화
- 유지할 요소
- 실제 사용자에게 확인한 내용이 있는 경우 그 기록

필요한 화면의 이미지가 없으면 해당 항목을 확인 불가로 둔다. 스크린샷만으로 동작, 성능, 키보드 조작을 검증했다고 표현하지 않는다. 다른 프롬프트에서 나온 결과는 별도 연결로 구별한다.

### 13.4 두 축의 진단

| 진단 축 | 핵심 질문 | 근거 예시 |
|---|---|---|
| 서비스와 의도 | 고객이 원하는 결과를 얻는 흐름인가 | 전체 활동과 화면 역할 |
| 고객의 판단 | 구매 또는 사용에 필요한 의문을 해소하는가 | 실제 설명, 파일 정보, 피드백과 복구 |
| 분위기의 적합성 | 이 고객과 서비스 경험에 선택한 분위기가 맞는가 | 사용자에게 확인한 선택 이유 |
| 스타일 적용 | 선택한 스타일의 구체적인 표현이 보이는가 | 색 관계, 서체, 형태, 소재, 구성 |
| 적용 범위 | 지정한 곳에 필요한 강도로 적용됐는가 | 프레임과 HUD 및 본문 등의 구분 |
| 레퍼런스 해석 | 선택한 특징이 유지되고 조정됐는가 | 원본 영역과 결과 영역의 비교 |
| 정보와 조작 | 필요한 정보를 찾고 활동을 이해할 수 있는가 | 위계, 선택 상태, 실제 실행 확인 |
| 일관성 | 여러 화면과 리소스가 같은 제품으로 읽히는가 | 대표 화면과 다른 상태의 비교 |

스타일 적용이 일치해도 서비스 목적에 어울리지 않을 수 있다. 반대로 기능이 이해되어도 사용자가 원하는 인상이 아닐 수 있다. 이 둘을 하나의 종합 점수로 합쳐 숨기지 않는다.

### 13.5 진단 항목과 증거

각 항목은 다음 내용을 가진다.

| 필드 | 내용 |
|---|---|
| 기준 ID와 버전 | 어떤 요구와 스타일을 검사하는가 |
| 기대한 결과 | 어디에서 무엇이 보여야 하는가 |
| 실제 관찰 | 결과에서 확인한 내용 |
| 관찰 근거 | 이미지, 화면과 영역 또는 실행 기록 |
| 판정 | 일치, 부분 일치, 불일치, 확인 불가, 해당 없음 |
| 중요도와 영향 | 전체 경험 또는 일부 표현에 미치는 영향 |
| 원인 가설 | 왜 차이가 생겼는지와 불확실성 |
| 수정 대상 | 브리프, 흐름, 스타일, 리소스, 구현 중 어느 계층인가 |
| 유지할 조건 | 이미 적합한 부분 |
| 사용자 확인 | 직접 관찰한 판정과 외부 피드백이 있는 경우의 별도 판단 |

확인 불가를 일치로 취급하지 않는다. 해당 없음은 적용 대상이 아님을 설명해야 하며 불일치를 회피하는 용도로 쓰지 않는다. 시각적 의도 판정은 사용자의 관찰과 확인으로 남긴다. 외부 피드백을 붙여 넣은 경우에도 출처와 사용자 확인을 구분한다.

### 13.6 사용자 의도 확인

사용자가 원본 기준과 실제 결과를 나란히 보며 다음 질문에 답한다.

1. 처음 만들고 싶었던 서비스의 경험과 맞는가.
2. 원하는 주된 분위기가 느껴지는가.
3. 스타일이 기대한 위치와 강도로 적용됐는가.
4. 유지할 부분과 바꾸고 싶은 부분은 무엇인가.

응답은 의도와 맞음 / 일부 다름 / 방향이 다름 / 아직 판단 어려움으로 제공한다. 이유를 자유롭게 작성하거나 이미지 영역을 지정할 수 있다.

사용자가 다르다고 답한 핵심 의도를 점수나 미리 작성된 예시로 무시하지 않는다. 판단이 어려우면 기준 이미지와 결과를 나란히 보여 주고 색 관계, 서체, 소재와 구성 등 항목별로 비교하도록 돕는다.

### 13.7 원인 분류와 수정 계획

| 원인 | 수정할 위치 | 처리 |
|---|---|---|
| 처음 의도가 충분히 설명되지 않음 | 제품 또는 컨셉 브리프 | 필요한 질문과 예시로 의도 보완 |
| 스타일 해석이 다름 | 컨셉과 스타일 규칙 | 원하는 특징과 적용 강도 재정의 |
| 레퍼런스 적용이 다름 | 관찰과 적용 결정 | 실제 원본 영역과 결과 영역 비교 |
| 리소스가 맞지 않음 | 에셋과 제작 조건 | 기준 리소스와 수정 또는 교체 계획 |
| 지시가 구현되지 않음 | 외부 결과와 구현 | 기존 기준을 유지하고 실행 범위 수정 |
| 요구 자체가 변경됨 | 결정의 새 버전 | 변경 이유와 영향 기록 후 기준 갱신 |

수정 계획은 문제, 근거, 변경 목표, 변경 범위, 유지할 조건, 필요한 자료, 확인 방법을 포함한다. 사용자에게 계획을 보여 주고 선택 또는 편집하게 한다. 이미 적합한 영역을 불필요하게 다시 설계하지 않는다.

### 13.8 수정 프롬프트 생성

수정 계획을 원본 결정과 연결해 최신 통합 프롬프트를 생성한다.

- 서비스와 고객 맥락 및 전체 목표
- 유지할 주된 분위기와 확정 스타일
- 해당 결과 버전과 관련 화면
- 현재 불일치와 관찰 근거
- 바꿀 대상과 기대 결과
- 유지할 조건
- 수정 후 다시 검사할 기준
- 확인하지 못한 사항

기본 산출물은 전체 맥락이 있는 통합본이며, 사용자가 필요하면 변경 부분만 담은 보조 지시를 함께 받을 수 있다. 자료가 없는 결과를 보았다고 표현하지 않는다.

### 13.9 재검토와 회귀 확인

수정한 결과를 등록하면 같은 기준과 같은 검토 범위로 다시 비교한다. 변경으로 영향받을 수 있는 기존 일치 항목도 함께 확인한다.

수정 회차마다 해결됨 / 남아 있음 / 다른 문제 발생 / 확인 불가를 기록한다. 계획을 만들었거나 프롬프트를 바꾼 것만으로 해결됨으로 전환하지 않는다.

동일한 문제가 반복되면 단순히 더 예쁘게와 같은 지시를 반복하지 않고 원인 분류를 다시 확인한다. 자가 진단 한 번은 한 회차의 사용자 관찰과 수정 계획 작성으로 기록하며 외부 제작을 자동 반복하지 않는다. 후속 자동 실행을 붙여도 회차와 중단 조건을 명시해야 한다.

### 13.10 완료와 보류

- 중요 불일치가 남으면 수정 필요 상태다.
- 판단에 필요한 자료가 없으면 확인 대기 상태다.
- 사용자가 핵심 의도에 동의하지 않으면 확인 완료로 표시하지 않는다.
- 미해결 문제를 의도적으로 보류하면 문제와 보류 이유를 기록하고 검토 완료와 구분한다.
- 시각 검토만 완료했으면 시각 확인 완료로 표시한다.
- 동작을 포함한 범위는 해당 실행 근거가 있어야 그 범위 확인 완료로 표시한다.

선택한 화면만 확인한 경우 서비스 전체가 검증됐다고 표시하지 않는다. 새로운 변경으로 영향을 받은 항목은 재검토 대상으로 돌아간다.

### 13.11 학습 기록

학습 기록은 다음 내용을 연결한다.

- 기대했던 경험과 시각 방향
- 실제로 확인한 차이와 증거
- 영향을 준 선택과 원인 가설
- 이번 수정과 유지한 부분
- 재검토에서 확인한 변화
- 다음 작업에 재사용할 원칙

일회성 선호를 모든 프로젝트의 공통 규칙으로 자동 승격하지 않는다. 반복되는 사례를 사용자가 확인한 뒤 공통 기준에 추가한다.

## 14 AI 없는 핵심 동작과 후속 연동 경계

### 14.1 현재와 후속 기능의 구분

| 작업 | 초기 버전의 수행 방식 | 후속 연결에서 보조할 수 있는 작업 |
|---|---|---|
| 제품 정리 | 질문, 내장 예시와 사용자 편집 | 자유 입력에서 브리프 초안 추출 |
| 흐름 구성 | 활동 예시와 목록 및 분기 편집 | 빠진 단계와 복구 경로 제안 |
| 레퍼런스 분석 | 이미지와 관찰 질문 및 직접 작성 | 실제 이미지를 읽은 관찰 초안 |
| 컨셉 비교 | 내장 방향 카드 복제와 사용자 수정 | 프로젝트에 맞는 새 대안 제안 |
| 스타일 구체화 | 팔레트와 서체 및 컴포넌트 샘플 편집 | 맥락에 맞는 표현 제안 |
| 생성 전 점검 | 필수 입력과 관계 검사 및 사용자 확인 | 의미 충돌과 적합성 분석 보조 |
| 결과 자가 진단 | 기준별 비교 질문과 사용자 판정 | 실제 결과와 기준의 차이 제안 |
| 수정 프롬프트 | 선택한 문제와 수정 계획의 템플릿 조립 | 수정 후보 작성 보조 |

후속 기능의 부재가 현재 동작의 오류나 미완료로 표시되지 않게 한다.

### 14.2 내장 가이드 콘텐츠

질문, 이유, 예시, 선택지, 분기와 다음 행동을 버전 있는 로컬 콘텐츠로 제공한다.

각 가이드 항목은 다음을 가진다.

- 질문 ID와 적용 제품 유형
- 쉬운 질문과 필요한 이유
- 선택지와 사용자 직접 작성
- 예시 문장과 시각 비교 자료
- 모름과 보류의 후속 경로
- 관련 필드와 완료 조건
- 다음 행동 규칙
- 콘텐츠 버전과 출처 구분

가이드는 일반 예시임을 표시한다. 현재 프로젝트나 이미지를 읽고 만든 맞춤 답변처럼 표시하지 않는다. 초기 콘텐츠에는 픽셀 게임, 모던 작업 도구, 재질 중심 브랜드와 공주풍 사진 서비스의 예시를 포함한다.

### 14.3 규칙과 사람의 판단 구분

자동 처리하는 것:

- 필수 필드와 연결 자료 존재 여부
- 선택 범위와 실제 참조의 연결
- 유효하지 않은 좌표와 중복 식별자
- 확정되지 않은 제안의 출력 혼입
- 명시적으로 서로 다른 값과 적용 범위의 충돌
- 입력 버전과 스냅샷 및 첨부 일치
- 현재 상태에 맞는 다음 행동
- 프롬프트 조립과 파일 패키징

사용자가 가이드를 따라 판단하는 것:

- 서비스 목적에 분위기가 맞는지
- 이미지가 어떤 인상을 주는지
- 레퍼런스의 어느 특징이 좋은지
- 결과가 원하는 스타일을 표현하는지
- 고객의 의문이 실제로 해소되는지
- 수정이 개선됐는지

이 두 범위를 UI와 검토 기록에서 구분한다.

### 14.4 외부 자료의 수동 전달과 등록

초기 버전은 프롬프트 복사, Markdown 내보내기와 참고 자료 묶음을 제공한다. 사용자가 외부에서 작업한 뒤 결과 이미지와 피드백을 직접 등록한다.

선택적으로 외부 텍스트를 붙여 넣어 제안으로 보관할 수 있다. 원문을 보존하며 사용자가 필드와 연결한다. 자유 텍스트를 의미 분석해 자동 분배하지 않는다. 서비스가 직접 보낸 요청이나 자동 응답이라고 기록하지 않는다.

자체 형식의 JSON 백업 가져오기는 형식, 파일 참조와 버전을 검증한다. 임의 형식의 외부 응답을 모두 자동 지원한다고 명세하지 않는다.

### 14.5 후속 확장의 기본 방향

연결 대상은 이미 Codex와 연결된 외부 서비스다. 이 서비스가 모델 제공자에 직접 연결하는 것을 기본 전제로 삼지 않는다.

현재 핵심 기능과 저장 모델을 유지하고 외부 전달과 결과 수신을 보조하는 연결 계층을 나중에 붙인다. MVP에는 활성 커넥터, AI SDK, 인증 화면, 토큰 저장, 작업 큐와 상태 폴링 구현을 요구하지 않는다.

확장 전 확인할 사항:

- 연결 대상 서비스가 제공하는 실제 인터페이스
- 인증과 실행 권한 및 사용자 확인 방식
- 이미지와 파일 전달 방법
- 작업 식별자와 프로젝트 및 스냅샷의 연결
- 결과 형식과 오류 및 취소 처리
- 외부 피드백을 제안으로 가져오는 방법

확인되지 않은 엔드포인트, 호출 문법과 자동 제어 가능성을 만들어 넣지 않는다.

### 14.6 연결을 위한 데이터 계약

초기 버전에서는 자료와 식별자를 확장 가능하게 기록한다. 다음은 후속 전달 형식의 개념이며 현재 실행 API가 아니다.

요청 맥락:

- 계약 형식 버전
- 프로젝트 ID와 프롬프트 스냅샷 ID
- 요청 목적과 검토 범위
- 사용자에게 확인받은 결정과 기준
- 실제 첨부 파일의 식별자와 역할
- 사용자가 외부 작업을 요청했는지
- 실제 연동 시 부여할 요청 식별자

수신 맥락:

- 연결된 프로젝트와 원본 스냅샷 및 요청
- 외부 서비스가 기록한 출처와 결과 버전
- 결과 파일과 피드백 원문
- 관찰, 해석과 수정 제안의 구분
- 처리 상태와 오류
- 사용자 검토와 적용 여부

수신 내용은 확정 결정이 아니라 검토할 제안으로 취급한다. 프로젝트와 스냅샷이 맞지 않는 결과는 자동 적용하지 않는다.

### 14.7 향후 실행 경계

현재 프로그램의 프롬프트 조립, 파일 내보내기, 결과 등록과 진단 기록을 각 독립 동작으로 구성한다. 나중에 외부 전달과 수신을 연결해도 같은 동작을 사용한다.

연결하지 않았을 때도 수동 전달과 등록 경로는 유지한다. 향후 연결 실패를 프로젝트 작업 전체의 실패로 처리하지 않는다. 커넥터 구현과 실제 서비스별 변환 코드는 연결 규약을 확인한 뒤 추가한다.

### 14.8 현재 화면에서 보이지 않을 것

초기 버전에는 다음을 실행 버튼이나 차단 조건으로 노출하지 않는다.

- AI에게 바로 보내기
- 자동 분석 또는 자동 피드백 받기
- 모델과 API 키 설정
- AI 연결을 해야만 다음 단계 진행
- 실제 요청이 없는 AI 처리 중 화면

향후 연동을 소개한다면 설정의 간단한 안내에 한정한다. 사용자가 현재 수행할 수 있는 행동을 우선 보여 준다.

### 15.2 핵심 관계

- 한 프로젝트에 여러 흐름과 화면이 있다.
- 한 화면은 여러 흐름에서 사용될 수 있다.
- 한 레퍼런스에 여러 영역과 관찰이 있다.
- 한 관찰은 여러 적용 대상으로 연결될 수 있다.
- 한 스타일 규칙은 전체 프로젝트 또는 일부 대상에만 적용될 수 있다.
- 한 프롬프트는 생성 당시의 확정 결정과 첨부 파일에 연결된다.
- 리뷰는 특정 프롬프트 스냅샷과 결과에 연결된다.

### 15.3 변경 전파

예시:

- 주요 사용자 변경 → 전체 목표, 흐름, 설명 수준 재검토
- 제품 기능 범위 변경 → 흐름과 화면, 콘텐츠, 출력 범위 재검토
- 컨셉 변경 → 스타일과 리소스, 관련 적용 결정 재검토
- 레퍼런스 교체 → 해당 관찰과 적용 결정 재검토
- 오탈자 수정 → 관련 출력 갱신, 다른 컨셉을 무조건 무효화하지 않음

확정 값을 자동 삭제하지 않고 영향 표시를 남긴다. 기존 프롬프트 스냅샷은 수정하지 않고 새 버전을 생성한다.

### 15.4 자가 진단의 버전 관계

한 진단 회차는 하나의 기준 스냅샷과 하나의 실제 결과 버전에 연결한다. 수정 계획에서 생성한 프롬프트, 새 결과와 재검토를 순서대로 추적한다.

사용자 확인과 판정은 해당 회차에 귀속한다. 이전 결과에 대한 확인을 새 결과에 자동 복사하지 않는다. 변경으로 영향받지 않은 기준은 재사용할 수 있지만 새 결과의 관찰 근거는 별도로 기록한다.

### 15.5 최소 진행 상태

- 설계 작성 중
- 생성 전 진단 중
- 사용자 의도 확인 필요
- 프롬프트 준비 완료
- 실제 결과 대기
- 결과 진단 중
- 수정 필요
- 수정 결과 대기
- 재검토 중
- 해당 범위 확인 완료
- 보류

상태 전환 이유와 연결 자료를 기록한다. 시각 확인과 동작 확인의 범위는 별도 속성으로 저장한다.

### 15.6 작업 진행과 재개

진행 상태는 마지막 방문 탭과 별도로 저장한다. 현재 작업, 추천 행동, 보완 후 돌아올 작업과 외부 전달 상태를 구분한다.

진행 기록은 실제 데이터와 검토 상태에서 계산한다. 탭을 열었다는 이유로 해당 작업을 완료 처리하지 않는다. 프로젝트를 복원하거나 상위 결정을 변경하면 필요한 추천을 다시 계산한다.

## 16 권장 구현 구조

### 16.1 초기 구조

- 화면: TypeScript 기반 웹 UI
- 로컬 서버: 프로젝트와 파일 저장, 내보내기와 복원 처리
- 저장: SQLite와 프로젝트별 파일 디렉터리
- 가이드: 버전이 있는 로컬 질문, 문장, 선택지와 시각 샘플
- 점검: 필수 입력과 참조 및 명시적 값의 규칙 검사
- 프롬프트 조립: 확정 데이터와 내장 템플릿
- 결과 비교: 원본과 결과를 나란히 표시하고 사용자 판정 저장

특정 프레임워크나 모델에 종속하지 않는다. MVP는 AI SDK와 AI 제공자 어댑터 없이 구현한다. 검색 엔진과 벡터 데이터베이스도 필수로 두지 않는다.

기본 시각 샘플은 로컬 자산과 사용 가능한 시스템 글꼴로 동작한다. 필수 글꼴과 샘플을 외부 CDN에서 불러와야만 진행할 수 있는 구조를 피하고 대체 글꼴을 제공한다.

### 16.2 주요 프로그램 동작

| 동작 | 책임 |
|---|---|
| 프로젝트 저장 | 필드와 변경 버전 및 결정 저장 |
| 가이드 표시 | 제품 유형과 현재 상태에 맞는 질문과 예시 |
| 이미지 등록 | 형식 확인, 원본과 표시용 파일 저장 |

| 사용자 진단 기록 | 기준별 판정과 근거 및 수정 계획 |
| 프롬프트 조립 | 확정 데이터에서 통합 문서 생성 |

### 16.3 기본 데이터 취급

- 현재 버전은 입력과 이미지를 외부 AI로 전송하지 않는다.
- 외부 스킬 문서와 레퍼런스는 자료이며 자동 실행하지 않는다.
- 프로젝트 간 파일과 결정의 참조를 구분한다.
- 백업과 복원은 데이터와 이미지 연결을 함께 유지한다.
- 프로젝트 삭제와 연결 파일 처리 범위를 보여 준다.
- 스냅샷에서 필요한 파일이 사라졌으면 참조 불가로 표시한다.
- 내장 샘플은 초기 로컬 사용에 필요한 범위로 제공한다. 선택적인 외부 링크 접근은 핵심 진행의 전제 조건이 아니다.

### 16.4 후속 연결 코드의 위치

외부 서비스별 전송과 인증, 응답 해석을 추가할 때 핵심 도메인 데이터와 템플릿을 직접 변경하는 방식으로 결합하지 않는다. 연결용 모듈이 실제 외부 형식과 내부 자료를 변환하게 한다.

MVP에서는 이 경계와 데이터 계약을 문서로 정의하면 된다. 동작하지 않는 연결을 가짜 구현으로 제공하거나 미리 외부 SDK를 설치하지 않는다.

| 재접속 | 저장한 작업과 다음 행동 복구 |
| 결과가 아직 없음 | 외부 작업 대기와 결과 등록 안내 |
| AI 미연결 | 정상 기본 상태이며 모든 핵심 기능 사용 가능 |

### 17.1 전환 확인 원칙

완료, 실패, 빈 상태와 대기 화면은 현재 상황과 가능한 다음 행동을 설명한다. 기본 버전에는 실제로 수행하지 않는 AI 분석과 요청 실패 상태를 표시하지 않는다. 외부 작업의 진행률을 알 수 없으면 사용자가 결과를 등록할 때까지 대기로 둔다.

## 18 학습 경험 명세

### 18.1 학습 방식

별도 이론 강의보다 현재 작업에서 이해할 수 있는 가이드를 제공한다.

예시:

- 전체 목표를 묻는 이유
- 스타일 이름과 실제 표현 규칙의 차이
- 레퍼런스의 관찰과 해석을 구별하는 이유
- 화면을 추가하기 전에 패널이나 모드로 처리할 수 있는지
- 이미지에서 알 수 없는 기능을 따로 설계하는 이유

### 18.2 맥락형 도움말

각 도움말은 한 번에 한 가지 판단을 설명한다. 더 보기를 선택하면 현재 프로젝트와 연결한 예시를 보여 준다.

예시:

> 공주풍이라는 단어만으로 버튼과 촬영 화면의 모습이 정해지지는 않습니다. 리본의 형태, 진주의 재질, 색의 대비를 어느 영역에 쓸지 선택해 보세요.

### 18.3 선택 이유와 결과 연결

선택한 규칙을 자가 진단과 수정에서 다시 보여 준다.

> 리본 장식을 프레임에만 적용하기로 했습니다. 결과물에서 도구 버튼까지 장식이 확장되었는지 확인해 보세요.

### 18.4 학습 기록의 출력

프로젝트 종료 시 다음을 정리할 수 있다.

- 선택한 방향과 이유
- 도움이 된 레퍼런스 해석
- 효과가 있었던 지시
- 반복된 문제와 수정
- 다음 프로젝트에서 재사용할 후보

기록의 양이나 입력 개수만으로 디자인 능력 점수를 만들지 않는다.

### 18.5 진행 중 학습

이유 설명은 현재 행동의 목적을 이해할 수 있는 한 문장을 기본으로 한다. 이론 자료를 먼저 읽어야 작업을 계속할 수 있게 만들지 않는다.

예시:

> 이 색을 실제 버튼 위에서 비교하면 원하는 느낌과 글자의 읽기 쉬움을 함께 확인할 수 있습니다.

사용자가 익숙해지면 설명을 접을 수 있지만 현재 행동과 다음 연결은 유지한다.

## 19 MVP와 확장 우선순위

### 19.1 MVP 필수

1. AI 설정 없이 프로젝트 생성과 로컬 저장
2. 현재 상태에 맞는 내장 가이드와 다음 행동
3. 제품 유형별 질문과 콘텐츠 계획
4. 전체 흐름과 화면 역할 및 분기 직접 편집
5. 이미지 업로드와 영역 지정 및 출처 기록
6. 관찰 질문과 예시를 이용한 레퍼런스 직접 분석
7. 내장 방향 카드와 사용자 컨셉의 편집 및 비교
8. 팔레트와 서체 및 컴포넌트의 로컬 시각 샘플
9. 스타일 적용 범위와 리소스 계획
10. 규칙 기반 누락 검사와 사용자 적합성 확인
11. 하나의 통합 프롬프트를 템플릿으로 조립
12. 복사와 Markdown 및 참고 자료 묶음 내보내기
13. 프롬프트 스냅샷과 결정 추적
14. 실제 결과 직접 등록과 기준별 사용자 자가 진단
15. 수정 계획과 최신 통합 프롬프트 및 같은 기준의 재검토
16. 선택 이유와 학습 기록
17. 중단 후 재개와 백업 및 복원
18. 선택적인 외부 피드백 원문 직접 등록

AI 연결 없이 위 과정을 처음부터 끝까지 수행하는 것이 MVP의 완료 조건이다. 외부에서 실제 디자인을 만드는 일은 사용자의 별도 작업이며, 이 서비스의 프롬프트 준비와 학습 기능은 외부 실행 성공을 요구하지 않는다.

### 19.2 다음 확장

- 여러 프로젝트의 레퍼런스와 결정 검색
- 재사용할 가이드와 스타일 규칙 라이브러리
- 내장 비교 자료와 대표 화면 샘플 확대
- 작업 절차와 스킬 참조의 내보내기 개선
- 이미 Codex와 연결된 외부 서비스의 실제 인터페이스 확인

### 19.3 외부 서비스 연동 단계

실제 연결 규약을 확인한 뒤 별도 범위로 구현한다.

- 사용자 선택에 따른 프롬프트와 자료 전달
- 기존 외부 서비스의 작업 식별자 연결
- 실제 결과와 피드백 수신
- 수신 제안의 원문과 버전 및 근거 표시
- 사용자 확인 후 내부 필드에 적용
- 실패와 취소 및 중복 결과 처리
- 연결하지 않아도 사용할 수 있는 수동 경로 유지

이 서비스의 자체 모델 제공자 연동은 별도 요구가 있을 때 검토한다. 기존 Codex 연결 서비스의 역할을 중복 구현하는 것을 기본 범위로 두지 않는다.

### 19.4 이후 검토

협업과 동기화, 전문 리뷰, 팀 디자인 시스템, 외부 리소스 제작 연결 등은 실제 사용 결과를 확인한 뒤 검토한다.

## 20 예시 프로젝트 A 픽셀 생존 게임

### 20.1 입력과 가정

사용자 입력:

> 픽셀 리소스를 사용한 샌드박스 생존 게임을 만들고 싶다. 낮에는 숲을 탐험하고 밤에는 직접 만든 거점으로 돌아오는 느낌이면 좋겠다.

예시를 위해 데스크톱 2D 게임을 선택했다고 가정한다. 아래 시각 요소는 실제 첨부 이미지를 분석한 내용이 아닌 시나리오 예시다.

### 20.2 제품과 흐름

- 사용자: 탐험과 건설을 즐기는 플레이어
- 전체 경험: 세계를 발견하고 직접 만든 거점을 발전시킨다.
- 핵심 루프: 탐험 → 채집 → 제작 → 더 넓은 탐험
- 연결 루프: 채집 → 건설 → 정비와 생존 → 탐험
- 화면과 상태: 타이틀, 월드 선택, 플레이, 인벤토리 패널, 제작 패널, 건설 모드, 중단과 실패 상태
- 미정: 전투 강도, 사망 손실, 협동 여부와 과금

### 20.3 가이드를 따른 레퍼런스 관찰과 방향 선택 예시

사용자가 관찰 질문을 보며 가상 이미지에서 차가운 숲과 따뜻한 실내 조명의 대비를 기록했다고 가정한다. 프로그램이 이미지를 자동 해석한 내용이 아니다.

방향 A: 거점의 생활감과 낮의 편안함을 강조한다.  
방향 B: 어둠 속 작은 불빛과 탐험의 긴장감을 강조한다.

사용자가 A를 선택하고 밤의 조명 대비 일부를 유지한다.

### 20.4 적용 규칙

- 픽셀 기준은 선택할 기준 에셋 팩의 규격에 맞춘다.
- 월드와 아이템의 외곽선과 명암을 통일한다.
- 플레이 화면에서 세계와 상호작용 대상을 구분한다.
- 인벤토리에서는 실제 아이템과 수량을 읽을 수 있게 한다.
- 제작 화면은 보유 재료와 부족한 재료를 보여 준다.
- 본문 서체는 실제 한글 문장으로 별도 확인한다.

### 20.5 최종 프롬프트 예시

~~~text
탐험·채집·제작·건설이 연결되는 데스크톱 2D 픽셀 생존 게임의
전체 UI UX를 설계한다.

사용자는 직접 발견하고 만든 거점을 발전시키는 경험을 원한다.
핵심 루프는 탐험, 채집, 제작과 더 넓은 지역의 탐험이다.
거점 건설과 정비는 이 루프에 연결되며 플레이 순서를 하나로 강제하지 않는다.

화면과 상태는 타이틀, 월드 선택, 기본 플레이, 인벤토리 패널,
제작 패널, 건설 모드, 중단과 실패 상태를 포함한다.
플레이 화면은 세계의 관찰과 상호작용을 중심으로 구성한다.
제작 패널은 제작 가능 여부와 부족한 재료를 구분한다.
건설 모드에서는 설치 위치와 가능 여부를 확인할 수 있게 한다.

선택한 방향은 낮의 탐험과 손수 만든 거점의 생활감을 강조한다.
첨부한 R1에서 확인할 차가운 실외와 따뜻한 조명의 대비를
거점과 야간 장면에 적용한다.
R1의 화면 구조나 조작법은 관찰된 것으로 가정하지 않는다.

픽셀 월드와 아이템은 기준 에셋의 규격과 외곽선 및 명암에 맞춘다.
기준 팩은 아직 미정이므로 필요한 리소스와 선택 조건을 먼저 정리한다.
한글 설명과 수량 표시는 실제 화면에서 읽히도록 조정한다.

산출물은 전체 흐름, 화면별 역할, 주요 상태,
월드와 UI의 시각 규칙, 대표 플레이 장면과 리소스 계획이다.
전투 강도와 사망 손실 및 과금은 미정으로 표시한다.
결과는 반복 플레이 지원, 상호작용 구분, 정보 위계와 에셋 일관성으로 검토한다.
실제 산출물을 확정 기준과 대조해 기대, 관찰 근거와 일치 여부를 기록한다.
의도나 픽셀 스타일이 어긋나면 유지할 부분과 변경 범위를 정해 수정하고,
수정 결과를 같은 기준으로 다시 확인한다. 없는 자료와 동작은 확인 필요로 남긴다.
~~~

예시의 R1은 실제 파일을 등록한 경우에만 내보내기에 포함한다. 첨부가 없으면 해당 부분을 미정 자료와 향후 적용 계획으로 바꾼다.

## 21 예시 프로젝트 B 공주풍 Y2K 네컷 사진 서비스

### 21.1 입력과 가정

사용자 입력:

> 핑크빛 공주풍 Y2K 네컷 사진 서비스를 만들고 싶다. 이 사진의 느낌은 좋지만 어떤 부분이 좋은지 모르겠다.

모바일 웹에서 촬영하거나 사진을 가져온다고 가정한다. 시각 분석 내용은 가상 예시다.

### 21.2 제품과 흐름

- 사용자: 사진을 꾸며 간직하고 싶은 사람
- 전체 목표: 마음에 드는 네 장을 자신의 분위기로 꾸며 저장한다.
- 흐름: 진입 → 촬영 또는 가져오기 → 네 장 선택 → 꾸미기 → 완성 확인 → 저장
- 화면: 시작, 촬영, 선택, 꾸미기, 완성
- 복구: 카메라 사용 불가 시 가져오기, 사진 교체, 편집 상태 유지, 다시 편집
- 미정: 유료 범위, 계정, 서버 보관, 인쇄 지원

### 21.3 레퍼런스와 방향 선택 예시

사용자가 관찰 가이드와 내장 예시를 보며 연한 핑크 바탕, 진주 장식, 매끈한 리본과 중앙을 둘러싼 구성을 기록했다고 가정한다. 자동 이미지 분석 결과가 아니다.

해석 A: 부드럽고 로맨틱한 드레스룸.  
해석 B: 광택과 작은 그래픽을 강조한 디지털 포토부스.

사용자는 A의 부드러운 분위기와 B의 버튼 질감을 조합해 확인한다.

### 21.4 적용 규칙

- 연한 핑크는 넓은 바탕, 진한 핑크는 선택과 주요 행동에 사용한다.
- 리본과 진주의 재질 대비는 프레임과 스티커에 적용한다.
- 버튼은 선택 여부와 문구가 읽히는 범위에서 광택을 적용한다.
- 시작 화면은 세계관을, 촬영 화면은 얼굴과 촬영 상태를 강조한다.
- 꾸미기 화면은 실제 사진과 완성 미리보기를 중심에 둔다.
- 사진을 교체하거나 이전 단계로 돌아갈 때 편집 데이터의 보존 규칙을 명시한다.

### 21.5 최종 프롬프트 예시

~~~text
모바일 웹용 공주풍 Y2K 네컷 사진 서비스의 전체 UI UX를 설계한다.

사용자는 사진 네 장을 고르고 자신의 분위기로 꾸며 저장한다.
전체 경험은 핑크빛 디지털 드레스룸에서 사진을 완성하는 느낌이다.

흐름은 시작, 촬영 또는 사진 가져오기, 네 장 선택,
프레임과 장식 편집, 완성 확인, 이미지 저장으로 연결한다.
시작 화면에는 만들 수 있는 실제 결과 예시와 시작 방법을 보여 준다.
촬영 화면은 얼굴과 카운트다운 및 촬영 상태를 먼저 읽히게 한다.
꾸미기 화면은 결과 사진을 중심으로 프레임과 장식 도구를 배치한다.
카메라를 사용할 수 없는 경우 사진 가져오기로 이어지게 한다.
사진 교체와 이전 단계 이동 시 보존할 편집 내용을 설명한다.

선택한 방향은 부드러운 핑크빛 드레스룸이다.
첨부한 R1의 리본과 진주에서 보이는 재질 대비,
중앙의 주인공을 둘러싸는 구성을 프레임과 스티커에 적용한다.
원본 이미지의 레이아웃을 전체 서비스 구조로 가정하지 않는다.

연한 핑크는 바탕에, 진한 핑크는 선택과 주요 행동에 사용한다.
버튼에 광택을 적용하되 문구와 선택 상태가 구별되게 한다.
장식적 글자는 로고와 짧은 제목에 적용하고
촬영 안내와 편집 설명은 실제 한글 콘텐츠로 읽기 쉬움을 확인한다.

필요 리소스는 프레임, 스티커, 조작 아이콘과 배경 그래픽이다.
확보하지 않은 리소스는 제작 계획으로 표시한다.
계정, 유료 범위, 서버 보관과 인쇄는 아직 정하지 않은 내용이다.

산출물은 전체 흐름, 페이지별 역할과 상태,
선택한 방향의 적용 규칙, 시작과 꾸미기 대표 화면 및 리소스 계획이다.
사진의 존재감, 조작 이해, 방향 일치, 편집 복구와 최종 결과의 일관성으로 검토한다.
고객이 사진 선택과 교체 및 저장을 이해할 수 있는지도 확인한다.
실제 결과의 색 관계, 리본과 진주, 버튼과 프레임의 적용을 근거와 함께 진단한다.
사용자가 의도나 스타일이 다르다고 판단하면 변경 범위를 정해 수정하고,
수정 결과를 같은 기준으로 재검토한다. 실행하지 않은 복구 동작은 확인 필요로 남긴다.
~~~

| AC02 | 이미지 한 장만 좋아함 | 관찰 질문과 내장 예시를 따라 특징과 적용 초안을 직접 정리한다 |
| AC03 | 이미지에 화면 구조가 없음 | 제안한 흐름을 이미지에서 관찰한 사실로 쓰지 않는다 |

| AC08 | 게임 프로젝트 | 구매가 필수가 아니며 반복 루프와 게임 상태를 표현한다 |

추가 사람 검토는 세 종류의 시작 상태로 수행한다.

- 무엇을 원하는지 설명하기 어려운 사용자
- 컨셉을 이미 정한 사용자
- 기존 결과를 수정하려는 사용자

입력 누락 수, 확정 요구 누락, 잘못된 레퍼런스 적용, 프롬프트 재작성 이유를 기록한다. 시각적 적절성은 실제 결과와 사람의 비교 판단을 함께 확인한다.

### 22.1 자연스러운 흐름의 사용성 검토

첫 진입부터 실제 결과와 수정까지 시나리오를 수행한다.

- 이미지 한 장만 등록하고 방향을 고르는 경우
- 컨셉을 이미 정한 사용자가 프롬프트를 준비하는 경우
- 외부에서 제작한 결과를 가져와 수정하는 경우
- 작업 도중 나갔다가 다시 이어가는 경우

관찰할 내용은 다음 행동의 발견, 버튼 의미의 이해, 불필요한 탭 왕복, 막힌 위치, 중복 입력과 복구 성공이다. 탭 이동 횟수만으로 혼란을 단정하지 않고 사용자의 실제 목적과 행동을 함께 확인한다.

검토자는 작업 목적을 제시하되 다음 탭을 대신 알려 주지 않는다. 사용자가 주요 전환에서 위치나 절차를 계속 질문해야 한다면 문구, 연결 또는 필요한 정보의 표시를 수정하고 같은 시나리오로 다시 확인한다. AC54는 구현 완료를 위해 검증할 기준이며 현재 달성한 측정 결과가 아니다.

## 23 구현 순서

### 단계 1 가이드와 프로젝트 저장

AI 없이 작동하는 질문, 내장 문장, 보기, 상태와 다음 행동을 먼저 구현한다. 제품 유형과 사용자 입력에 따른 분기, 저장과 재개 및 콘텐츠 계획을 구성한다.

### 단계 2 레퍼런스와 시각 비교

이미지와 영역 등록, 관찰 워크시트, 사용자 해석과 적용 문장, 컨셉 카드 편집 및 로컬 시각 샘플을 구현한다. 이미지 이해와 문장 제안은 내장 예시와 사용자 작성으로 진행한다.

### 단계 3 프롬프트와 전달 자료

필수 필드와 참조 검사, 사용자 적합성 확인, 템플릿 조립, 하나의 통합 프롬프트와 파일 패키지 및 스냅샷을 구현한다.

### 단계 4 자가 진단과 수정

실제 결과 직접 등록, 기준별 사용자 판정과 근거, 원인 선택, 수정 계획과 통합 프롬프트 재조립, 재검토와 학습 기록을 구현한다.

### 단계 5 후속 연결 준비

현재 데이터의 버전과 식별자 및 파일 역할을 확인하고 연결 경계를 문서화한다. 활성 AI 연결을 구현하는 단계가 아니다. 이미 Codex와 연결된 외부 서비스의 규약을 확인한 뒤 별도 구현 범위를 정한다.

두 예시 프로젝트를 외부 AI가 연결되지 않은 상태에서 처음부터 프롬프트 출력과 사용자 진단 및 수정까지 검토한다. 실제 디자인 결과는 사용자가 준비한 샘플로 등록해 흐름을 검증할 수 있다.

## 24 구현 완료의 정의

- 사용자가 모르는 상태와 정한 상태 모두에서 시작할 수 있다.
- 전체 경험과 화면별 역할이 연결된다.
- 이미지 한 장의 느낌이 구체적인 관찰과 적용 결정으로 변환된다.
- 선택한 방향을 시각 샘플로 비교할 수 있다.
- 확정, 제안, 미정과 제외가 출력까지 유지된다.
- 확정한 정보가 하나의 통합 프롬프트에 추적 가능하게 반영된다.
- 실제 전달할 참고 자료와 미확보 자료가 구별된다.
- 고객과 제공 가치 및 핵심 의문을 주된 분위기와 연결해 생성 전 진단한다.
- 사용자에게 확인받은 의도와 실제 결과를 기준별 증거로 대조한다.
- 불일치 시 수정 계획, 최신 통합 프롬프트, 수정 결과와 같은 기준의 재검토가 이어진다.
- 수정으로 영향받는 기존 일치 항목을 확인하고 검토 범위와 보류를 구분한다.
- 결과를 입력해 수정 이유와 다음 지시를 기록할 수 있다.
- 픽셀 생존 게임과 공주풍 네컷 서비스에서 같은 데이터 구조가 서로 다른 경험과 표현을 지원한다.
- 각 주요 진입과 전환에서 다음 행동과 이유 및 결과가 보이며 자유로운 탐색과 재개를 지원한다.
- 외부 제작과 결과 등록 및 진단과 수정이 끊기지 않고 연결된다.
- AI 연결과 외부 모델 설정 없이 핵심 흐름을 사용할 수 있다.
- 자동 의미 분석과 실제 사용자 작성 및 내장 예시를 구분한다.
- 초기 핵심 기능과 후속 외부 서비스 연결 범위가 분리되어 있다.
- AC01부터 AC64까지 검증하고 발견한 중요한 문제를 해결했다.
